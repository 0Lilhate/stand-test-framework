План раскладывает BRD на поставки: пулл-реквесты, каждый из которых собирается зелёным
(`./gradlew build`, анализ в режиме `strict`) и не ломает потребителей. Ссылки вида BR-xx, AC-xx,
D-xx, OQ-xx ведут в BRD.

## 1. Сквозные правила

Эти правила действуют для всех поставок и в задачах не повторяются.

- **TDD.** Сначала тест, который падает, потом реализация. У каждого требования с номером есть тест,
  в имени или `@DisplayName` которого этот номер виден (`AC-4`, `Г-2`). На этом строится трассировка
  (§9).
- **Сборка.** `--release 17`: никаких API новее Java 17 (sequenced collections, `Math.clamp`,
  virtual threads, pattern-switch). `LineLength` 140, перенос с оператором в начале строки.
  Checkstyle и SpotBugs — гейт: одна находка роняет `build`. **Пороги оверлея не поднимать.**
  `ClassFanOutComplexity`, `ClassDataAbstractionCoupling`, `ExecutableStatementCount` и соседи стоят
  ровно над худшим текущим случаем, чтобы новый код хуже худшего был пойман. Класс, упёршийся в
  порог (кандидат — исполнитель с бэкендами, очередью и пробой), разбивается.
- **Граф модулей** (BR-17). `core` — сток. `http → core`. `rest → http, await`. `eq → http, await`.
  `http` не зависит ни от одного адаптера и не содержит `StepExecutor`. Адаптеры друг от друга не
  зависят. Машинной проверки графа нет: на ревью каждого PR сверяются `build.gradle.kts` и заглушки
  `Planned internal dependencies`.
- **В core нет знаний об EQ** (D-18, AC-11). Допустимы только wire-константы маршрутизации в
  `StepParameterKeys`: префикс `eq.`, ключ параметра `backend`, имя секции `eq-backends` — по образцу
  `UI_LOGIN_TYPE`. Никаких типов, полей и правил про EQ.
- **Без глобального состояния для конфигурации.** Всё, что определяет поведение (типы секций,
  каталоги, пулы, очереди), передаётся через конструктор; статический доступ допустим только как
  значение по умолчанию (урок `UiAccountPools`). Намеренно JVM-широкое состояние — очередь шлюза,
  кеш фазы юнита, счётчики уникальности и журнал `SeedJournal` (§4, §5), и у каждого из них есть
  инстанцируемая реализация для тестов.
- **Граница очереди.** Сериализация `gateway` действует только в одной JVM на пару
  `(base-url, unit)` после разрешения ссылок. Перед пилотом фиксируются `maxParallelForks = 1` и
  отсутствие одновременных CI jobs на ту же пару; иначе нужен внешний координатор (BRD BR-26).
- **Значения — неизменяемые `record`** с защитными копиями (`List/Set/Map.copyOf`).
- **Провалы.** **Любой провал `eq.seed` — `StandTestException` (`BROKEN`)**, включая таймаут пробы
  видимости и непроверяемый ответ шлюза (BRD BR-36). Раннер записывает `AssertionError` как `FAILED`,
  а подготовка данных — предусловие, а не проверяемое поведение TKS: сломанный сид не должен
  выглядеть в Allure как дефект продукта и не должен смешиваться с ним при сравнении «до/после» по
  классу причины. Этим `eq` сознательно отличается от `rest.expectEventually`, где ожидание и есть
  проверка. **Всё, что `eq` бросает после начала цепочки, несёт журнал цепочки**: раннер на брошенном
  исключении строит диагностику только из причины, а сверх неё до отчёта доходит лишь то, что
  исключение отдаёт через `FailureAttachments`. В диагностику попадают только метаданные (алиас,
  option, номер шага, PIN), не тела ответов и не секреты. Вложения собираются по allowlist NFR-05:
  маскирование Allure не делает произвольный ответ EQ безопасным.
- **JSON в `stand-test-eq`** (BRD NFR-01). Jackson 3 (`tools.jackson.core:jackson-databind`, версия из
  BOM Spring Boot, который configurer импортирует в каждый POM) — сборка тел запросов и разбор
  ответов. `json-path` — только пути `expect-body`, тем же диалектом `$.…`, что в `RestStep`.
  Незадекларированная транзитивная `json-smart` не используется; сборка тел строковыми шаблонами
  запрещена — наименования идут в реальный EQ, экранирование не должно зависеть от удачи.
- **Тестовые дублёры HTTP** (`RecordingHttpServer`, `FakeHttpCaller`) живут в test fixtures модуля
  `stand-test-http` (плагин `java-test-fixtures`). Копировать их между модулями или зависеть от
  `src/test` соседнего модуля нельзя.
- **Документация — часть поставки.** README модуля; `CLAUDE.md` (граф, число артефактов, описание
  модулей); корневой `README.md` (таблица модулей, пример реестра); `docs/publishing.md` (число
  артефактов).

### 1.1 Расширяемые секции реестра (D-18, BR-45)

**Дизайн.** Core хранит секцию без интерпретации: знает только её алиасы. Имя секции загрузчики
знают **явно**. Универсальный приём «любой незнакомый раздел — секция» невозможен: `StandTestProperties`
привязывается с `ignoreUnknownFields = false`, и поле-«ловушку» для произвольного ключа Spring не
допускает. Явное имя сохраняет и fail-closed: опечатка в `services` по-прежнему отвергается.

```java
// core, пакет core.environment
public record EnvironmentSection(String name, Map<String, SectionEntry> entries) { … }
public record SectionEntry(String alias, Map<String, Object> fields) { … }   // fields — глубоко неизменяемы

// core, StepParameterKeys — wire-константы маршрутизации (не EQ-логика)
public static final String EQ_PREFIX = "eq.";
public static final String EQ_BACKEND = "backend";
public static final String EQ_BACKENDS_SECTION = "eq-backends";
```

### 1.3 Модуль `stand-test-http` (D-17)

**Что переезжает** из `stand-test-rest` в `ru.alfa.stand.test.http` — **без переименования**, чтобы
дифф был поведенчески нулевым (R-15): `HttpCaller`, `WebClientHttpCaller`, `RestRequest`,
`RestResponse`, `BaseUrlResolver`, `EnvironmentBaseUrlResolver`, `AuthHeaderResolver`,
`EnvironmentAuthHeaderResolver`, внедрение `correlationId` (сейчас приватный
`RestStepExecutor.injectCorrelationId`, выносится в публичный помощник, который принимает **уже
вычисленное** решение «внедрять или нет»: флаг читает `rest` из `RestStepParameters`, иначе `http`
потянул бы параметры `rest`). Зависимость `spring-webflux`
переезжает в `http`. Переименования, если понадобятся, — отдельной поставкой.

**Что остаётся в `rest`:** `RestStep` и весь DSL, `RestStepExecutor`, `RestStepParameters`,
матчеры, capture, `PollProbe`.

**Совместимость.** Публичный API `RestStep` не меняется (AC-10). Меняется пакет `HttpCaller` и
записей запроса/ответа, а с ним сигнатура публичного конструктора `RestStepExecutor(…, HttpCaller)`.
Это допустимо: SDK не опубликован (DEP-8), потребитель Taksa этот конструктор не использует. Стартер
не затронут: `RestConfiguration` создаёт `new RestStepExecutor()`, типы `http` ему не нужны.
