# Prompt for opencode: EQ data provisioning

Ты работаешь в репозитории `stand-test-framework`. Твоя задача — довести реализацию
`docs/brd/eq-data-provisioning-brd.md` по
`docs/plans/eq-data-provisioning-implementation-plan.md` до полного выполнения всех
доступных задач, тестов, документации и критериев приёмки. Работай автономно и
поэтапно, пока остаётся работа, которую можно выполнить в текущем окружении.
Отвечай пользователю на русском; код, идентификаторы, Javadoc и комментарии
сохраняй на английском.

Сначала прочитай:

- `AGENTS.md` и `CLAUDE.md`;
- BRD и план целиком, включая трассировку требований, этапы 0–5 и приложения;
- `docs/plans/eq-stage-0-discovery-2026-09-28.md` и
  `docs/plans/eq-stage-0-closure-2026-09-28.md`;
- `README.md`, `stand-test-eq/README.md`, README затронутых модулей;
- текущие исходники и тесты, особенно `stand-test-eq`, `stand-test-http`,
  `stand-test-core`, `stand-test-config` и `stand-test-spring-boot-starter`.

## Важно о текущем состоянии

Рабочее дерево уже содержит много изменённых и новых файлов. Не делай `git reset`,
`git clean`, `checkout` поверх изменений и не удаляй чужую работу. Статусные таблицы
в старых документах могут отставать от кода: проверяй фактическую реализацию и
тесты. Этап 1 уже выполнялся. В этапе 2 есть DSL `eq.seed`, типизированная
конфигурация, матрица возможностей, генерация ID, исполнитель для `showcases`,
значения по умолчанию, номер шага из полного сценария, диагностика частичного
сбоя и `VisibilityProbe` с ограниченным ожиданием. Эти части проверь и доработай
только при выявленном дефекте. `README.md` и `docs/publishing.md` могут содержать
устаревшие утверждения об отсутствии исполнителя.

## Порядок работы

1. Сделай короткий аудит «пункт плана → код/тест → готово, пробел или внешний
   гейт». Особое внимание: остаток 2.2, пилот 2.3, этапы 3–5, BR/AC/NFR/SEC
   из таблицы трассировки. Не считай наличие класса доказательством выполнения
   требования.
2. Закрой остаток этапа 2: отдельный журнал операций и безопасные TEXT-вложения
   при успехе и сбое; общий `eq-seeded.jsonl` с корректной параллельной дозаписью;
   регистрацию `StepExecutor` через SPI и Spring Boot starter; проверки изоляции,
   BOM и документацию. Убедись, что ошибка после начала цепочки доходит до
   `StepEvent` как `BROKEN` вместе с журналом именно этого шага. Не включай сырые
   запросы, ответы, секреты или персональные данные в логи и вложения.
3. Реализуй этап 3 для `gateway` по плану: безопасный HTTP-клиент и таймауты,
   строгую проверку ответов, `write-allowed` и кассу по валюте, частичные сбои и
   состояние «неизвестно» после таймаута, генераторы ИНН/ДУЛ, маркировку
   `testRunId`, справедливую очередь по разрешённой паре `(base-url, unit)`,
   освобождение очереди до пробы видимости, чтение и кеш фазы юнита. Никаких
   автоматических повторов записывающих операций, кроме явно подтверждённого
   BRD случая. Не угадывай формат ответа `gateway` или неподтверждённые поля.
4. Выполни доступную часть этапа 4 для физических лиц по подтверждённым
   контрактам. Если `G0-FL` не пройден, не объявляй реальную поддержку ФЛ:
   оставь fail-closed отказ и точно укажи, какого доказательства не хватает.
5. Выполни этап 5: миграцию доступных тестов потребителя и обновление кита
   `.claude/` и `.opencode/`, guardrails, KB и оценочного кейса. Проверь общие
   фикстуры как одну группу и сохрани локальные правки потребителя. Если
   репозиторий потребителя недоступен, заверши всё возможное в SDK и запиши
   точный блокер, список затронутых файлов и команд для продолжения.

## Внешние гейты — не подменять догадками

Протокол закрытия этапа 0 прямо говорит, что `G0-EQ`, `G0-TEST`, `G0-JT400`,
`G0-FL`, `G0-LTR` и `G0-PUBLISH` ещё требуют доказательств или согласований.
Разрабатывай части, допускающие офлайн-тестирование, но не выдавай тестовые
дублёры за стендовую приёмку. Не запускай запись в реальный `gateway`, массовую
миграцию на стенде, публикацию артефактов или иной внешний эффект без уже
имеющегося явного разрешения и нужных учётных данных. Секреты бери только из
runtime environment; не помещай их в код, YAML, логи или отчёт. При отсутствии
гейта продолжай независимую работу и фиксируй, что именно блокирует приёмку.

## Неизменные технические правила

- Следуй графу модулей из `AGENTS.md` и плана; `core` не получает EQ-логики.
- Java 17 через `--release 17`; не повышай пороги Checkstyle/SpotBugs.
- Только реальные DEV/IFT стенды для приёмки; Testcontainers не основа SDK.
- `eq.seed` остаётся ленивым DSL. Guardrails и проверка возможностей действуют
  до записей. ID нельзя задавать из теста.
- Любой сбой `eq.seed` — `StandTestException`/`BROKEN`. Подтверждённые объекты
  отражаются в диагностике, переменные публикуются только после полного успеха
  и пробы видимости.
- Конфигурация реестра версии 6, паритет файлового и Spring загрузчиков,
  whitelist алиасов, ленивое разрешение ссылок и запрет встроенных секретов
  сохраняются.
- Соблюдай allowlist NFR-05 для журналов и вложений.
- Не возвращай удалённые `stand-test-agent-*` и `stand-test-ai-schema` модули.

## Проверки и отчёт

Для каждой поставки напиши тест, который проверяет поведение и соответствующий
BR/AC/Г номер, затем реализацию. Запускай профильные тесты, после завершения
связанной поставки — `./gradlew build --console=plain` и `git diff --check`.
Проверь параллельность, частичные сбои, таймауты, отсутствие утечек,
`ServiceLoader`, Spring starter, BOM и совместимость существующих адаптеров.
Не добавляй тесты, которые лишь повторяют строки реализации. Обновляй README
и документацию в той же поставке. Не утверждай «этап завершён», пока не
выполнены его критерии выхода из плана.

В конце каждого крупного участка сообщай: что изменено, какие требования
закрыты, команды и результаты проверки, оставшиеся пробелы и внешние гейты.
В финале дай матрицу всех этапов и `AC-1`…`AC-11` со статусом и доказательством.
Если полное закрытие BRD невозможно из-за внешнего гейта, не называй задачу
выполненной: заверши доступную реализацию и выдай конкретный список необходимых
входных данных, согласований и стендовых проверок.

Начинай с аудита текущего кода и затем сразу реализуй ближайший незакрытый
пункт плана.
