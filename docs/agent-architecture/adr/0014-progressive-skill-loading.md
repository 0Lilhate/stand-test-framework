# ADR-0014: Прогрессивная загрузка памяти и детерминированный отбор навыков

**Статус:** Accepted · **Дата:** 2026-07-27

## Контекст

Постановка запрещает загружать все skills в каждый prompt. Обычная мотивировка — стоимость
токенов, но она здесь вторична.

Главная причина — **качество отбора**. Список из тридцати процедур в контексте превращает выбор в
задачу для модели: она видит названия и краткие описания и берёт то, что звучит подходяще. Условия
применимости при этом читаются в лучшем случае мельком. Именно так процедура «увеличить таймаут»
оказывается применённой к дефекту системы: название совпало с симптомом.

Вторая причина — воспроизводимость. Отбор, сделанный моделью, невозможно повторить в режиме
`REPLAY`, а без него нельзя измерить эффект навыка (ADR-0011).

Существующие ограничения: `ExecutionPolicy.maxPromptTokens` = 400 000 на прогон, контекстное окно
модели неизвестно (открытый вопрос Q-1 плана), `ContextBundle` уже считает `approxContextTokens`.

## Решение

**1. Четыре уровня загрузки с жёсткими потолками.**

| Уровень | Что | Когда | Потолок |
|---|---|---|---|
| 0 | `essentials` Project Memory | всегда | 400 токенов |
| 1 | индекс навыков (id, `behaviourVersion`, kind, триггер, `successRate`) | только в `PLANNED`/`GENERATED`/`REPAIRING` | 2 000 |
| 2 | полные тела совпавших навыков | предикат совпал детерминированно | ≤ 3 навыка, 4 000 |
| 3 | примеры одного выбранного навыка | если бюджет позволяет | 1 500 |

Плюс условная загрузка `environmentLimitations` по совпадению `scope` с транспортами плана.

Суммарно память занимает **не более 8 % `maxPromptTokens`**. Превышение — **ошибка сборки
контекста, а не обрезка**: тихо усечённая память даёт прогон, о котором неизвестно, что модель
видела.

**2. Отбор выполняет код, а не модель.** `applicability` — декларативный предикат над полями
`RunSnapshot`/`FailureAnalysis`; он вычисляется, а не интерпретируется. Модель получает уже
отобранный набор.

**3. Ничья не разрешается выбором.** При равенстве по специфичности, успешности и родословной
записывается `SkillConflict`, прогон продолжается **без навыка**, конфликт уходит человеку. Это то
же правило, по которому `kb-lookup` при двух кандидатах даёт `AMBIGUOUS` вместо тихого выбора.

**4. Индекс генерируется, а не пишется руками** — иначе он разойдётся с телами навыков, и
несовпадение проявится как «навык не был предложен», что почти нечитаемо в trace.

## Рассмотренные альтернативы

**А. Загружать все навыки, полагаясь на способность модели отфильтровать.**
Отклонено по двум причинам выше: качество отбора и невоспроизводимость. Стоимость — третья.

**Б. Семантический поиск по навыкам (embeddings).**
Отклонено. Отбор навыка — это проверка условий (`failureCategory == TIMEOUT_TOO_SMALL`,
`attempts >= 2`), а не поиск похожего текста. Векторный поиск вернул бы ранжированный список без
объяснения, почему навык подошёл, и сделал бы невозможной проверку «предикат совпал». Плюс это
инфраструктура, которую ADR-0007 уже отклонил для базы знаний по тем же основаниям.

**В. Отдать выбор модели, но показывать только top-N по успешности.**
Отклонено: успешность — свойство навыка, а не текущей ситуации. Навык с успешностью 0.9 на
таймаутах не должен предлагаться при дефекте системы, а сортировка по успешности именно это и
сделает.

**Г. Один уровень: сразу полные тела совпавших навыков, без индекса.**
Отклонено частично — это почти и есть уровень 2. Индекс нужен отдельно, потому что человек, читающий
trace, должен видеть, ЧТО рассматривалось и было отвергнуто; без индекса в трассе остаётся только
выбранное, и «навык не подошёл» неотличимо от «навыка не существует».

**Д. Мягкое усечение при превышении бюджета.**
Отклонено: усечение молча меняет то, что видела модель, и делает прогон невоспроизводимым.
Превышение означает, что памяти накопилось больше, чем помещается, — это факт, требующий решения
человека, а не автоматического сглаживания.

## Последствия

**Положительные.** Отбор воспроизводим и объясним: в trace видно, какой предикат совпал.
`REPLAY` даёт тот же набор навыков. Стоимость памяти ограничена сверху и измеряется
(`memoryTokensPerRun`).

**Отрицательные.** Предикат нужно уметь выразить: процедура, чьё условие применения не
формализуется, не станет навыком. Это ограничение по сути, а не по форме — неформализуемое условие
и не проверить, — но часть полезных эвристик останется за бортом.

Потолок в 3 навыка уровня 2 иногда отсечёт четвёртый подходящий. Приемлемо: при трёх совпадениях
предикаты, скорее всего, слишком широки, и это сигнал к их сужению.

**Нейтральные.** Пороги (400/2000/4000/1500 токенов, 8 %) — параметры, а не архитектура; они
уточняются по метрике `memoryTokensPerRun` после первых прогонов, когда станет известно
контекстное окно модели (Q-1).

## Как проверить, что решение соблюдается

1. Тест: при пустом наборе совпавших навыков в контекст не попадает ни одного тела.
2. Тест: превышение потолка даёт ошибку сборки контекста, а не усечённый контекст.
3. Тест: два прогона с одинаковым `RunSnapshot` дают побайтово одинаковый набор навыков.
4. Тест: `SYSTEM_DEFECT` не приводит к загрузке ни одного `repair-strategy` — `forbiddenWhen`
   срабатывает до ранжирования.
5. Тест: ничья по всем трём правилам даёт `SkillConflict` и пустой набор, а не произвольный выбор.
6. Тест: `index.yml` совпадает с результатом генерации из тел навыков (по образцу `BundleParityTest`).
