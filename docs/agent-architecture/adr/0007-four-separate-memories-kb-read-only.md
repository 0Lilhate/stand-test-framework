# ADR-0007: Четыре раздельных хранилища; KB — read-only для агента; без vector DB

**Статус:** Accepted · **Дата:** 2026-07-27

## Контекст

Требование постановки: не создавать одну общую «agent memory». Сегодня персистентны только
`knowledge-base/mappings/*.yml` (трассировка кейс→тест) и `candidates/promotion-log.yml` (леджер
промоутов); памяти агента нет вовсе (Анализ §9: Память 1/5, Skills 2/5).

`knowledge-base/README.md:7-11` формулирует единственное предназначение KB: «The agent never
invents endpoints… A plausible-but-wrong path that compiles and reaches review is the exact failure
mode this KB closes».

Объём KB: 561 строка YAML, 3 сервиса, из них один с полным набором endpoint'ов.

## Решение

**Четыре хранилища с разными владельцами:**

| Хранилище | Носитель | Живёт | Агент пишет |
|---|---|---|---|
| Run Memory | `.agent-runs/<runId>/` | один прогон | ✅ полностью |
| Project Memory | `agent-project-memory.yml` | проект | ❌ только предлагает |
| Procedural Skills | `agent-skills/` | между проектами | ⚠ только статистику применений |
| Knowledge Base | `knowledge-base/` | жизнь системы | ❌ **read-only**, кроме `mappings/` |

**KB read-only — абсолютный запрет, не «выключено по умолчанию».** Единственное исключение —
`mappings/` (трассировка, не контракт), что уже является действующим правилом кита
(`kb-lookup/SKILL.md:88-92`).

**Retrieval — точный lookup по файлам, без vector DB.** `KbLookupTool` реализует уже описанную в
`kb-lookup/SKILL.md:38-69` детерминированную процедуру: services целиком → addressed-чтение
дочерних коллекций по конвенции `<collection>/<service-id>.yml` → резолвинг окружения.

**Навык создаёт человек, статистику ведёт агент.** Автоматически меняется только `status` —
и только в сторону ограничения (карантин при `successRate < 0.5`, `n ≥ 10`).

## Рассмотренные альтернативы

**А. Единая `AgentMemory`.**
Отклонено с конкретным сценарием отказа: агент не нашёл endpoint, LLM предположила
`/api/v1/orders`, тест позеленел на моке. При праве записи в общую память догадка сохраняется;
следующий прогон резолвит её как `matched` с `confidence = HIGH` — галлюцинация получает статус
подтверждённого контракта. Хранилище, куда агент пишет догадки, не может защищать от догадок.

**Б. Vector DB / semantic search для KB.**
Отклонено. При 3 сервисах точный lookup по `id`/`tags`/`domain` дешевле, детерминированнее и
объясним: можно показать, **почему** запись совпала. Semantic search вернул бы ранжированный
список без объяснения — это прямо противоречит модели `matched`/`missing`/`assumptions`.
Пересмотреть при KB > ~50 сервисов; тогда индекс, вероятно, всё равно будет точным (инвертированный
по `tags`/`domain`), а не векторным.

**В. Право агента писать в KB после safety-review.**
Отклонено: review — суждение модели. Механизм, где галлюцинация проходит проверку моделью и
становится контрактом, — усиление, а не ослабление проблемы.

**Г. Skills, создаваемые агентом автоматически при первом успехе.**
Отклонено: закрепляет разовую удачу как стратегию. Порог — 3 повторения плюс человеческое ревью.

**Д. Project Memory, редактируемая агентом.**
Отклонено: конвенции проекта — конфигурация; агент, самостоятельно переписывающий команду запуска
тестов после неудачи, приводит систему в неисправимое состояние.

## Последствия

**Положительные.** KB сохраняет роль источника истины. Отладочные данные прогона не смешиваются
с контрактами. Skills получают измеримую применимость. Retrieval воспроизводим.

**Отрицательные.** Наполнение KB остаётся ручным, человеко-ограниченным процессом — риск R-2
Анализа архитектурой не снимается. Это осознанно: автоматическое наполнение и есть тот самый
режим отказа.

Skills накапливаются медленно (порог 3 повторения + ревью) — в первые месяцы каталог будет пуст.

**Нейтральные.** `agent-skills/` и `agent-project-memory.yml` в фазе 0 не создаются: пустые
структуры не дают ничего, а поддерживать их придётся сразу.

## Как проверить, что решение соблюдается

1. Тест: `ArtifactWriteTool` отвергает любой путь в `knowledge-base/`, кроме `mappings/**`.
2. Тест: в `ToolRegistry` отсутствует tool записи в контрактные коллекции KB.
3. Тест: `SkillRegistry` не имеет публичного метода создания навыка — только
   `recordSuccess`/`recordFailure` и чтение.
4. Тест: `ProjectMemory` доступна оркестратору только на чтение; предложение изменения оседает
   в Run Memory как `ProjectMemoryProposal`.
