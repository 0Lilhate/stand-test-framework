# ADR-0006: Промты — единый версионированный источник для человека и оркестратора

**Статус:** Accepted · **Дата:** 2026-07-27

## Контекст

Анализ A-07: промты не версионированы вовсе. Frontmatter 16 скиллов содержит `{name, description}`,
12 команд — `{description}`; `grep '^version:'` по всему киту даёт 0 совпадений. Следствие:
сгенерированный тест невозможно связать с содержанием инструкции, по которой он создан, а
регрессия качества промта необнаружима.

Анализ A-09: кит существует в двух копиях (`.claude` и `.opencode`). Копии уже расходились —
javadoc `BundleParityTest` фиксирует: «the gRPC matcher set came to be current in one copy and
stale in the other for a whole release».

Одновременно Анализ §9 оценивает prompt engineering в 4/5 — это лучшая часть кита. Содержание
менять не нужно; нужны версии и один источник.

## Решение

**1. `version` в frontmatter каждого промта.** Инкремент при изменении, меняющем смысл инструкции
или контракт ответа. `PromptRegistry` дополнительно хранит `sha256` содержимого — правка файла без
инкремента версии обнаруживается.

**2. `outputSchema` в frontmatter** для промтов, возвращающих структуру. Закрывает пробел
«7 из 9 промежуточных артефактов не имеют контракта ответа».

**3. Один источник — два потребителя.** `PromptRegistry` читает те же файлы
`docs/ai-agent/.claude/skills/**`, что и Claude Code. Человек в интерактивном режиме и оркестратор
в автоматическом работают с одной инструкцией.

**4. `.opencode` генерируется из `.claude`** Gradle-таском. `BundleParityTest` превращается из
детектора расхождений в проверку свежести генерации.

**5. `promptSetVersion`** — хеш всего набора — пишется в `manifest.json` каждого прогона.
Позволяет утверждать «эти 40 прогонов выполнены одним набором промтов».

## Рассмотренные альтернативы

**А. Отдельный набор промтов для оркестратора.**
Отклонено — главная альтернатива и самая опасная. Два набора для одной задачи разойдутся; это
уже произошло с двумя копиями кита и потребовало отдельного теста. Кроме того, был бы утрачен
интерактивный режим: человек и агент перестали бы работать по одной инструкции.

**Б. Промты в Java-константах / ресурсах модуля агента.**
Отклонено: промты правит QA-инженер, а не Java-разработчик. Markdown в репозитории с git-историей —
подходящий носитель; перенос в код повысил бы порог изменения.

**В. Версионирование только через git-хеш файла.**
Отклонено: git-хеш меняется от правки опечатки и не выражает намерение автора «это ломающее
изменение». Нужны оба: `version` (намерение) и `sha256` (факт).

**Г. Внешний prompt-management сервис.**
Отклонено: внешняя зависимость и потеря атомарности изменения «промт + код + тест» в одном коммите.

## Последствия

**Положительные.** Артефакт связывается с версией инструкции. Изменение промта становится
измеримым (ADR-0011). Дублирование кита устраняется. Интерактивный и автоматический режимы не
расходятся.

**Отрицательные.** Дисциплина инкремента версии — человеческая. Смягчается тестом на `sha256`:
несовпадение содержимого при неизменной версии обнаруживается, хотя и постфактум.

Генерация `.opencode` из `.claude` лишает возможности править вторую копию напрямую — это и есть
цель.

**Нейтральные.** Единовременная правка frontmatter 32 файлов — механическая работа фазы 0.

## Как проверить, что решение соблюдается

1. Тест: каждый `SKILL.md` и каждая команда имеют `version` (целое ≥ 1) во frontmatter.
2. Тест: каждый промт, используемый оркестратором, имеет `outputSchema`, и файл схемы существует.
3. Тест: `.opencode` побайтово равен результату генерации из `.claude` (эволюция
   `BundleParityTest`).
4. Тест: `manifest.json` любого прогона содержит `promptSetVersion` и по одному
   `promptId@version+sha256` на каждый вызов LLM.
