# ADR-0004: Трек MVP — декларативный AI-формат, Java DSL откладывается

**Статус:** Accepted · **Дата:** 2026-07-27

## Контекст

В ките два трека авторинга. Java DSL объявлен треком по умолчанию
(`java-dsl-authoring/SKILL.md:8-9`) как покрывающий полную поверхность SDK. AI-формат
(JSON/YAML `steps/type`) — для сценариев внутри исполнимого подмножества.

Анализ R-8 зафиксировал противоречие: **трек по умолчанию — единственный, у которого нет
машинного контракта до исполнения**.

| Трек | Проверки до запуска |
|---|---|
| AI-формат | JSON Schema 2020-12 → `AiScenarioParser.parse` → `DefaultScenarioValidator.validate(scenario, registry)` — три гейта, все fail-closed |
| Java DSL | компилятор + checkstyle. Семантика не проверяется; `DefaultScenarioValidator` отработает только внутри `run()`, то есть уже на стенде |

Признание авторов кита (`safety-review/SKILL.md:43-48`): для Java-артефактов пункты 8, 10-15 и 17
«have **no runtime enforcement**… the review is the only net», где review — это модель, применяющая
grep-паттерны.

## Решение

MVP (фазы 1-3) генерирует **только AI-формат**. Java DSL — фаза 4, после того как `SafetyScanTool`
докажет способность ловить нарушения в Java-исходниках на негативном корпусе.

`TestPlan.track` остаётся полем модели, `AuthoringTrack.JAVA_DSL` — допустимым значением;
в фазах 1-3 планировщик обязан выбирать `AI_SCENARIO`, а `plan.validate` отвергает шаг вне
исполнимого подмножества кодом `TRACK_CAPABILITY_VIOLATION`.

Кейс, не укладывающийся в подмножество, — не провал: это `AWAITING_APPROVAL` с честной формулировкой
«вне автоматизируемого подмножества MVP», а не растягивание формата (действующее правило
`pipeline.md:67-69`: «never stretch the format»).

## Рассмотренные альтернативы

**А. Java DSL как трек MVP (сохранить текущий default).**
Отклонено. Пришлось бы одновременно строить оркестратор и статический анализатор Java-исходников
достаточной точности, чтобы заменить единственную защиту. Два риска в одной фазе.

**Б. Оба трека сразу.**
Отклонено: удваивает поверхность генерации, валидации, починки и evaluation при неизвестном
качестве базового цикла.

**В. Только Java DSL, а safety-review оставить за моделью.**
Отклонено прямо: это консервация R-8. Автоматизация неконтролируемой генерации увеличивает объём
непроверяемых артефактов пропорционально производительности агента.

## Последствия

**Положительные.** Каждый сгенерированный артефакт проходит три машинных гейта до касания стенда.
Ошибка генерации ловится схемой, а не человеком на ревью. Негативный корпус (12 невалидных
примеров) уже существует и работает.

**Отрицательные.** Покрываемая доля кейсов ограничена исполнимым подмножеством: нет
`db.seed`/`db.cleanup`/`db.query`, `rest.put`/`rest.delete`, кастомных gRPC-метаданных; на
`kafka.expect` только EQUALS. Часть реальных кейсов уйдёт в `AWAITING_APPROVAL` как
неавтоматизируемые в MVP.

Отсюда конкретное следствие для планирования: **метрика «доля кейсов, отклонённых по
`TRACK_CAPABILITY_VIOLATION`» становится приоритезатором фазы 4.** Если она мала — Java-трек
не срочен; если велика — известно, каких именно возможностей не хватает.

**Нейтральные.** Решение обратимо: смена значения по умолчанию в политике планировщика после
того, как `SafetyScanTool` пройдёт приёмку на Java-корпусе.

## Как проверить, что решение соблюдается

1. Тест: `plan.validate` отвергает план с `track = JAVA_DSL`, пока политика фазы это запрещает.
2. Тест: план с non-equals матчером на `kafka.expect` отвергается кодом
   `TRACK_CAPABILITY_VIOLATION` — согласовано с уже существующим
   `StepMatcherCapabilityCoverageTest`.
3. Метрика evaluation: доля прогонов, завершившихся `TRACK_CAPABILITY_VIOLATION`, публикуется в
   отчёте — она и есть критерий начала фазы 4.
