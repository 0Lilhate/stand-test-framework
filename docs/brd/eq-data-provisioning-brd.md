## 1. Резюме

Тесты Taksa готовят клиентские данные (клиент, счёт, пакет услуг / сделка) через **showcases** — мок
слоя **витрин** на стенде ift: TKS читает клиента из витрин, а showcases позволяет положить в них
проекции таблиц EQ (`ACLM`, `ACLN`, `UACM`, `UDLM`) напрямую. На стенде **test** мока нет: витрины
наполняются из реального EQ, а данные в EQ можно создать только бизнес-операциями через шлюз TAKSA.
Это умеет делать библиотека `aiagents-taksa-starter`.

Предлагается **один доменный шаг `EqSeed`** в новом модуле SDK `stand-test-eq` с двумя
взаимозаменяемыми бэкендами:

- `showcases` (ift) раскладывает шаг в записи `ACLM` / `ACLN` / `UACM` / `UDLM` и отправляет их в `POST /showcases/load/list`;
- `gateway` (test) выполняет цепочку операций EQ: `ONU|ONF → OKC → YFT2 → KP1|SPU`. Вызовы шлюза
  SDK сериализует внутри JVM, поэтому параллельный запуск классов у потребителя сохраняется.

Бэкенд выбирается **реестром окружения**, а не кодом теста. Окружение прогона задаётся одной
переменной через новый ключ `stand.test.default-environment`. Даты открытия счёта и начала сделки в
обоих режимах по умолчанию «сегодня», поэтому мигрируемым тестам не нужны атрибуты, которые test не
воспроизводит (§9.4), и тест без правок проходит на ift и на test.

Ключевое изменение в тестах: **PIN, номер счёта и другие идентификаторы EQ перестают быть
Java-константами и становятся переменными сценария** (`${client.pin}`, `${client.account}`). На ift
их генерирует SDK (сейчас это делает каждый тест сам, из `UUID.randomUUID()`), на test их выдаёт EQ.
Без этого режим test невозможен в принципе (§2.3). SDK уже разрешает `${…}` во время исполнения и в
телах REST, и в параметрах SQL, поэтому доработка адаптеров `rest`/`db` для миграции не нужна.

Саму библиотеку как зависимость **не подключаем**: она несовместима со стеком SDK (Spring Boot 4 /
Spring 7 / Jackson 3) и содержит дефекты, влияющие на данные. Протокол шлюза реализуется в
`stand-test-eq`, дефекты учтены (Приложение Г) и передаются авторам библиотеки.

## 2. Контекст и постановка проблемы

### 2.1 Что есть сейчас

- **Ключ реестра `ift` у потребителя указывает на хосты dev3** (`taksa-dev3`, `tksdev3mock1`,
  `tksdev3psg1`). Ниже «ift» означает ключ реестра, то есть стенд dev3; «test» — отдельный стенд (D-1).
- **showcases** (`http://tksdev3mock1:8080`, алиас `showcases` в реестре ift) — загрузчик **витрин**
  (data-mart projections). По реестру и KB потребителя он «не открывает ЮЛ/счёт/сделку и не
  возвращает id созданных сущностей; ответы 200 без тела, из которого можно что-то забрать».
  `POST /showcases/load/list` принимает список записей `{businessCode, version?, fields:[{type, value}]}`.
  Поля **позиционные**, их смысл закодирован порядком.
- В `taksa-service-autotests` сидирование есть в **16 тестах**: 15 в `lgot.*` и
  `temp.TksSubscriptionPilotTest`. Алиас `showcases` упоминают 17 файлов, но семнадцатый,
  `showcases.ShowcaseUnknownCodeSmokeTest`, проверяет сам мок и ничего не сидирует. Используются ровно
  четыре бизнес-кода, по 16 вхождений каждого (по одному на тест):

  | businessCode | Что сидирует | Поля (по коду тестов; контракта мока нет, см. OQ-3) |
  |---|---|---|
  | `ACLM` | клиент (мастер) | `[0]` clientCode (PIN), `[2]` тип клиента — во всех 16 тестах `U` (ЮЛ), `[3]` `GB`, `[4]` — 12 цифр: в 15 тестах одна и та же константа `618418411698`, в `SimpleServiceCopyAndApprove` — per-run значение `CLIENT_REG_NO` (из `RUN_HEX`, комментарий автора: «регистрационный атрибут витрины клиента, вторичный, per-run»); `[5]` `RU`. Смысл `[3]`, `[4]` не расшифрован |
  | `ACLN` | наименование клиента | `[0]` PIN, `[2]` полное наименование, `[3..5]` краткие |
  | `UACM` | счёт | `[0]` номер счёта, `[1]` PIN, `[4]` тип (`CA`), `[6]` валюта, `[7]` дата открытия. Предположительно: `[2]` отделение (`4101`), `[13]` балансовый (`40702`) |
  | `UDLM` | сделка пакета услуг | `[0]` id сделки (в `UlDiscountSchemeCancelTest` — `<PIN>_PU_NWA`), `[1]` PIN, `[2]` счёт, `[3]` код пакета (`PU_NWA` в 15 тестах, `PU_LST` в пилоте), `[4]` дата начала, `[5]` состояние `A` |

  У пилота два счёта (STS и PU), сделка привязана к счёту PU.
- **Даты в сидировании прошлые, но по смыслу кейсов не нужны** (D-15): 15 lgot-тестов открывают
  счёт `now().minusYears(1)` и начинают сделку `now().minusMonths(1)`, пилот зашивает литералы
  `2026-05-20` и `2026-03-17`.
- **Идентификаторы вычисляются в тесте** и используются как константы:
  `RUN_HEX = UUID.randomUUID()…toUpperCase()` (static-поле класса), `PIN = "T" + RUN_HEX.substring(0, 5)`,
  `ACCOUNT = "40702810" + …`. SDK-переменная `testRunId` для этого **не используется**. Дальше значения
  идут в три места:
  - в тела запросов к TKS через фикстуры: 12 файлов `fixtures/lgot/*.json`, 13 видов плейсхолдеров
    (`.replace("__PIN__", PIN)`). Из EQ приходят только `__PIN__` и `__ACCOUNT__`; `__NOW__`,
    `__DATE_BEGIN__`/`__DATE_END__`, `__DECISION__`, `__RATE__`, `__ID_TARIFF_DECISION__`,
    `__CLIENT_ID__`, `__ACCOUNT_ID__`, `__CREDIT_ORG__` — значения теста;
  - в SQL-параметры: `DbStep…param("pin", PIN)` по `prodprofile_u` в трёх тестах (четыре места вызова);
  - в тела, собранные в коде: у пилота фикстуры нет, 15 lgot-тестов делят 12 файлов.
- **`CLIENT_ID` / `ACCOUNT_ID` — не данные EQ и не id строк БД.** Это поля входящего ЛТР-сообщения
  (`clients[].id`, `clients[].accounts[].accountId`) рядом с `pinEQ` и `number`, то есть
  идентификаторы системы-источника решения. Сейчас они синтетические:
  `floorMod(RUN_HEX.hashCode(), 90_000_000) + 10_000_000` и `+1`.
- Сейчас все тесты сидируют **только ЮЛ**. ФЛ через showcases не сидирует ни один тест.
- Окружение сценария — литерал `.environment("ift")` (17 вхождений).
- **Классы тестов у потребителя исполняются параллельно**: `junit-platform.properties` —
  `mode.classes.default=concurrent`, `fixed.parallelism=10`, `maxParallelForks = 1`.
- Часть набора — **honest-red** по замыслу: тест фиксирует дефект стенда и падает. Это пять тестов
  и четыре кейса: 412402 (`BranchCodeCondition`, `BranchCodeUpdate`), 412553 (`BranchCodeUpdate`),
  409046 (`MultiRangeTariffAutoApprove`), 406943 (`ComplexServiceRangeSingleTierDiagnostic`).
  Критерий миграции поэтому — «тот же результат, что до неё», а не «зелёный».

### 2.2 Боль

1. На стенде test мока нет. Тесты, которым нужен клиент EQ, там не запускаются вовсе.
2. На ift тесты проверяют TKS против **мока** витрин. Интеграция с реальным EQ (как TKS видит
   клиента, счёт и сделку, созданные штатными операциями и доехавшие до витрин) не проверяется ничем.
3. Библиотека `aiagents-taksa-starter` умеет создавать клиентов в реальном EQ, но подключить её в
   SDK нельзя (§2.3, п. 4), и у неё другая модель данных (§2.3, п. 1).

### 2.3 Почему нельзя просто «подменить транспорт под `RestStep.post("showcases")`»

Первоначальная идея — оставить в тесте `RestStep.post("showcases", …)`, а в режиме test незаметно
перенаправлять запрос в библиотеку. Разбор показал, что это не работает, по четырём причинам.

1. **Противоположная семантика.** showcases декларативен: «положи записи с **моими** ключами». EQ
   императивен: «создай клиента, ключи **выдам я**». PIN, счёт и id сделки, которые тест вшил в
   последующие шаги, в EQ не появятся. Любой конвертер тела запроса отдал бы тесту другого клиента,
   а тест продолжил бы работать со старыми константами.
2. **Разная гранулярность.** Три шага теста (`seed-client`, `seed-account`, `seed-deal`)
   соответствуют одной неделимой цепочке EQ. Конвертеру пришлось бы держать состояние между шагами
   и разбирать позиционные `fields[]` чужого формата.
3. **Невоспроизводимые атрибуты.** Дату открытия счёта и начала сделки в прошлом, произвольный id
   сделки и конкретное отделение штатные операции EQ задать не позволяют. Для мигрируемого набора
   прошлые даты не нужны (D-15), но конвертер об этом не знал бы и молча переносил бы их.
4. **Нет шва.** `HttpCaller` получает `RestRequest(method, baseUrl, path, …)` без алиаса сервиса.
   Отличать showcases пришлось бы по URL.

Отсюда выбор доменного шага (§3, альтернатива Б; решение D-4).

### 3.1 Архитектурные развилки внутри SDK

Две развилки вытекают из правил самого SDK. Обе решены владельцем SDK 2026-09-24: вариант **а** в
обоих случаях (D-17, D-18).

**Развилка 1 (была OQ-12). Как `stand-test-eq` ходит по HTTP.** Бэкенду `showcases` нужен REST-вызов через алиас
`services` с его correlation и auth (BR-21), пробе видимости — REST-вызов в TKS (BR-36). Но правило
графа модулей — **адаптеры не зависят друг от друга**, а `stand-test-rest` — адаптер. Варианты:

| # | Вариант | Цена |
|---|---|---|
| 12-а | Вынести общий HTTP-слой (разрешение `base-url`/`*-ref`, `AuthConfig`, внедрение `correlationId`, маскирование) в нейтральный модуль, от которого зависят `rest` и `eq` | Рефакторинг `stand-test-rest`, новый артефакт в BOM |
| 12-б | Дублировать нужное подмножество в `stand-test-eq` | Две реализации auth/correlation, которые разойдутся; риск записывается в §15 |
| 12-в | Разрешить исключение `eq → rest` | Ломает инвариант графа; машинной проверки графа сейчас нет, нарушение будет незаметным |

Решение: **12-а** (D-17). Следствия:

- новый модуль `stand-test-http` (рабочее имя): разрешение адреса сервиса по алиасу (`base-url` /
  `base-url-ref`), `AuthConfig` BASIC/BEARER, внедрение `correlationId`, таймауты, маскирование
  секретов в диагностике. Это не адаптер: у него нет `StepExecutor` и типов шагов;
- `stand-test-rest` переводится на этот модуль без изменения своего публичного DSL и поведения;
  существующие тесты `rest` — критерий, что рефакторинг ничего не сломал (AC-10);
- граф модулей: `rest → http → core`, `eq → http → core`. Правило «адаптеры не зависят друг от
  друга» сохраняется: `http` — общий слой, а не адаптер. Описание графа в `CLAUDE.md` и заглушки
  `Planned internal dependencies` в `build.gradle.kts` модулей обновляются (BR-17);
- риск расхождения auth/correlation между адаптерами снят.

**Развилка 2 (была OQ-13). Где живёт знание о разделе `eq-backends`.** `EnvironmentDefinition` — record в core с
типизированными секциями. Типизированный `EqBackendDefinition` с полями `unit`, `branch`,
`cash-accounts`, `inn-region-code`, `unit-phase` означал бы предметку конкретной банковской
системы в core, а правило SDK запрещает тащить в core бизнес-логику. Прецедент `ui-applications`
не прямой: UI — это транспорт, EQ — бизнес-система. Варианты:

| # | Вариант | Цена |
|---|---|---|
| 13-а | Расширяемые секции реестра: core хранит непрозрачную карту секции и её алиасы, чтобы работал `checkAliasWhitelist`; типизированный разбор и все прочие проверки делает адаптер | Новая точка расширения в core и в обоих мапперах реестра |
| 13-б | Типизированный `EqBackendDefinition` в core, по образцу `UiApplicationDefinition` | EQ-предметка в core |

Решение: **13-а** (D-18). Следствия:

- `EnvironmentDefinition` получает **расширяемые секции**: имя секции → алиас → неизменяемая карта
  полей. О содержимом core знает только множество алиасов секции (для `checkAliasWhitelist`).
  Маршрутизация шага к секции — wire-константы в `StepParameterKeys`: префикс `eq.`, ключ параметра
  `backend`, имя секции `eq-backends` (как `UI_LOGIN_TYPE` для `ui.login`). Поля `kind`, `unit`,
  `cash-accounts`, `unit-phase`, `write-allowed` и прочие для core непрозрачны;
- типизированный разбор секции делает адаптер (`EqBackendConfig` в `stand-test-eq`). Он же проверяет
  секцию fail-closed: неизвестное поле, неверный тип или отсутствующее обязательное значение — ошибка
  на `prepare` с указанием окружения, алиаса и поля. Проверка «unknown field», которую сейчас делают
  загрузчики реестра, для содержимого расширяемой секции переезжает в адаптер;
- `*-ref` и value twins внутри секции разрешаются тем же механизмом ссылок core, что и у остальных
  секций; SDK-внутренний маркер `literal://` в пользовательской конфигурации по-прежнему отвергается;
- оба маппера реестра (файловый и стартерный) знают имя секции `eq-backends` **явно** и переносят
  её содержимое без интерпретации. Универсальный приём «любой незнакомый раздел — секция» невозможен:
  стартер привязывает `StandTestProperties` с `ignoreUnknownFields = false`, поэтому у
  `StandTestProperties.Environment` появляется поле `eqBackends` (`Map<String, Map<String, Object>>`),
  а незнакомый раздел по-прежнему отвергается. Стартер и так знает все адаптеры, а D-18 ограничивает
  только core. Отдельный риск стартера — привязка Spring к вложенной `Map`: ключи в kebab-case и
  вложенные карты должны доехать без искажений (R-14). Это покрывает тест паритета BR-45;
- секция объявляет версию формата, с которой появилась (6), по правилу `EnvironmentConfigFormat`.

## 4. Цели и результаты

### 4.1 Бизнес-цели

- **BG-1.** Тесты Taksa, которым нужен клиент EQ, запускаются на стенде test против реального EQ.
- **BG-2.** Один и тот же тест проходит на ift (showcases) и на test (EQ) **без правок кода**, если
  ему не нужны невоспроизводимые на test атрибуты (§9.4). Режим переключается одной переменной
  окружения.
- **BG-3.** Расхождение режимов по данным видно явно: тест падает до IO, а не проходит «зелёным» на
  других данных.
- **BG-4.** Подготовка данных EQ становится частью SDK с теми же гарантиями, что у остальных
  адаптеров: реестр, whitelist, отчёт в Allure, отсутствие адресов и секретов в тестах.

### 4.2 Результат (Definition of Success)

- Все 16 тестов с сидированием переведены на `EqSeed` и дают на ift тот же результат, что до
  миграции (зелёные остаются зелёными, honest-red — красными по той же причине).
- Пилотный набор (§16, фаза 3) зелёный на test. В тестах нет ни одной константы PIN или счёта.
- Прогон `APP_STEND=test ./gradlew test --tests <пилот>` не требует правок кода и не требует
  отключать параллельность классов.

### 4.3 Вне целей (Non-goals)

- Удаление созданных клиентов из EQ: штатного способа нет (D-9).
- Сидирование произвольных записей EQ, кроме клиента, счёта, пополнения и пакета услуг.
- Параллельные вызовы шлюза и одновременные прогоны на test из нескольких JVM или агентов:
  сериализация SDK действует внутри одной JVM (D-11).
- Замена showcases на ift: на ift остаётся мок.
- Проверка самого showcases: `ShowcaseUnknownCodeSmokeTest` остаётся на `RestStep` и только на ift.
- **AI-YAML-формат** (`stand-test-scenario-yaml`) в первой версии `EqSeed` не поддерживает.
  `AiScenarioParser` — закрытый мир: у каждого типа шага свой транслятор (`RestStepTranslator`,
  `DbStepTranslator`), и неизвестный узел валит разбор. Сценарий с EQ-данными пишется только на
  Java DSL. Нужна ли поддержка в YAML — OQ-10.

## 8. Пользовательские сценарии

**US-1. Автор теста пишет тест один раз.** Он описывает клиента через `EqSeed` и дальше использует
`${client.pin}` / `${client.account}` в телах запросов и в SQL-параметрах. Окружение и даты не
указывает. Ожидание видимости клиента выполняет сам `EqSeed` по пробе из реестра (§9.5), в тесте его нет.

**US-2. Прогон на ift.** `./gradlew test` (переменная `APP_STEND` не задана → `ift`). Бэкенд
`showcases` сам выбирает PIN и счёт из `testRunId`, ставит даты «сегодня», отправляет записи в мок и
публикует переменные. Проба видимости не объявлена, ожидания нет.

**US-3. Прогон на test.** `APP_STEND=test ./gradlew test`. Классы идут параллельно, как и раньше.
Перед первой цепочкой SDK читает фазу юнита и кеширует результат. Если юнит не в рабочей фазе, каждый
сценарий с `eq.seed` падает на фазе `prepare` одной и той же инфраструктурной ошибкой, и ни одного
вызова шлюза не происходит. Иначе бэкенд `gateway` по очереди, в пределах JVM, выполняет цепочки EQ.
Каждый сценарий после своей цепочки дожидается, пока клиент станет виден, и публикует выданные EQ
значения под теми же именами переменных.

**US-4. Тест требует невоспроизводимого.** Будущий тест задаёт `.openedAt(now().minusYears(1))`. На
ift шаг проходит. На test адаптер отвергает сценарий на фазе `prepare`, до первого сетевого вызова, с
перечнем атрибутов. Автор либо убирает требование, либо явно пишет `.allowApproximation(OPENED_AT)`;
тогда на test счёт открывается сегодняшней датой, а отчёт Allure фиксирует приближение. Мигрируемых
тестов это не касается (D-15).

**US-5. Тест только для ift.** Тест, который зовёт `RestStep.post("showcases", …)` напрямую, на test
отвергается валидатором: алиаса `showcases` в окружении `test` нет, срабатывает существующий
`NON_WHITELISTED_SERVICE`.

**US-6. Разбор мусора в EQ.** Сопровождение находит клиентов, созданных автотестами, по маркеру
`testRunId` в согласованном поле и по журналу `eq-seeded.jsonl` (BR-43). Поле и формат маркера
подтверждаются до пилота на test (G0-TEST).

## 9. Бизнес-требования

### 9.1 Режим и окружение

- **BR-01.** Ключ `default-environment` задаёт окружение сценария, у которого `.environment()` не
  вызван или пуст. Сейчас пустое окружение отвергается дважды: `DefaultScenarioValidator` (стр. 96) и
  конструктор `ScenarioContext` (стр. 37). Точка расширения: `EnvironmentRegistry` получает
  необязательное `defaultEnvironment()`, а `DefaultScenarioRunner` вычисляет фактическое окружение
  **до** валидации (сейчас `validate` и `ScenarioContext.start` идут в `run()` подряд). Тогда и
  валидатор, и `ScenarioContext` получают непустое значение, а их проверки не ослабляются. Поведение
  меняется только при заданном ключе.
- **BR-01a.** Ключ есть в обоих front-end'ах реестра: `stand.test.default-environment` в стартере и
  корневой `default-environment` в файловом `stand-test-environments.yml`. Файловый загрузчик
  разрешает `${VAR:умолчание}` сам. Потребитель Taksa работает через Spring, поэтому JUnit-путь
  (`StandTestExtension`) можно поставить позже Spring-пути, но в рамках фазы 1.
- **BR-02.** Порядок приоритета: явный `.environment("…")` → значение, которое тест получил из
  `@StandEnv` / `@StandTest(env=…)` (существующий механизм JUnit-пути; тест сам передаёт его в
  `.environment()`) → `default-environment`. Существующий механизм не ломается и не дублируется:
  `default-environment` становится значением по умолчанию и для `@StandEnv`, если `env` не задан
  (сейчас `StandTestExtension.resolveEnvironment` в этом случае бросает `ParameterResolutionException`).
  Своя аннотация потребителя `ru.alfa.taksa.StandTest` — это Spring-обёртка, её не трогаем.
- **BR-03.** Имя фактического окружения попадает в отчёт Allure каждого сценария (параметр прогона).
- **BR-04.** Если `default-environment` указывает на окружение, которого нет в реестре, контекст
  **не стартует**. Отказ на первом сценарии не допускается.

### 9.2 Доменный шаг `EqSeed`

- **BR-10.** DSL описывает клиента ЮЛ (`EqSeed.organisation(alias)`) и ФЛ
  (`EqSeed.individual(alias)`). У клиента от 1 до N счетов; у счёта — тип, валюта, сумма
  пополнения. **Пакет услуг** у ЮЛ задаётся на счёте (`KP1` привязан к счёту, `GZEAN`), у ФЛ — на
  клиенте (`SPU` привязан к клиенту, `GZCUS`). Пакет на счёте ФЛ — ошибка валидации до IO. В
  библиотеке пакет ФЛ лежал на счёте, и три счёта с T04/T05/T06 давали три подключения одному
  клиенту (Г-2).
- **BR-11.** Все атрибуты необязательны. Значения по умолчанию берутся из реестра окружения
  (`eq-backends.<alias>.defaults`), а не зашиты в код. Даты по умолчанию — «сегодня» (D-15).
- **BR-12.** Шаг публикует переменные сценария под префиксом `alias`:

  | Переменная | Значение |
  |---|---|
  | `${<alias>.pin}` | PIN клиента |
  | `${<alias>.inn}` | ИНН. Только бэкенд `gateway`; на `showcases` — «не поддерживается» (BR-30), пока не выяснено, что хранит `ACLM[4]` (OQ-3) |
  | `${<alias>.account}` | первый счёт |
  | `${<alias>.account.<i>}` | i-й счёт (с 0) |
  | `${<alias>.deal.<i>}` | id сделки пакета i-го счёта на `showcases`; на `gateway` не публикуется, пока не подтверждён способ получения id (OQ-4) |

  Имена одинаковы в обоих бэкендах (кроме `.inn`, см. выше). Ссылку другого шага на переменную,
  которую бэкенд окружения не публикует, заранее не поймать: `prepare` получает только свой шаг и
  не видит остальных. Такой сценарий падает на шаге-потребителе с `Unresolved variable`, поэтому
  список публикуемых переменных по бэкендам — в README модуля и в KB кита. Два шага `EqSeed` с одним
  алиасом в сценарии отвергаются на `prepare`: алиас резервируется в `ResourceScope` прогона, и
  вторая регистрация того же ключа бросает `StandTestException`, иначе вторая публикация молча
  перезаписала бы первую. Синтаксис совместим с `VariableResolver` (`${name}`, точка —
  часть имени). Переменные доступны везде, где SDK разрешает `${…}` во время исполнения: в inline-теле
  и в `bodyFromResource` REST-шага (`RestStepExecutor.resolveBody`), в параметрах SQL DB-шага
  (`DbStepExecutor.binds`).
- **BR-13.** Тип шага — `eq.seed`. Шаг — `GenericStep`, как у остальных адаптеров, и исполняется
  через SPI (`META-INF/services`) и бин стартера. Шаг **всегда** несёт параметр `backend` — алиас
  записи в `eq-backends` окружения: по умолчанию `eq`, иначе `EqSeed…backend("…")`. Префикс
  переменных (`EqSeed.organisation("client")`) и алиас бэкенда — разные вещи. Валидатор отвергает
  шаг `eq.*` без `backend`: общий `checkAlias` отсутствующий параметр пропускает молча, и без этого
  правила SEC-02 ничего бы не проверял.
- **BR-14.** Первая версия содержит только операцию создания. Изменение и закрытие счёта или
  пакета — вне области.
- **BR-15.** Модуль публикуется так же, как остальные адаптеры:
  - вносится в `settings.gradle.kts` и в `stand-test-bom`: у BOM есть проверка полноты («does not
    match the published modules»), без записи сборка упадёт;
  - в стартере получает вложенную `@Configuration` с `@ConditionalOnClass` (ограничение «do not
    flatten» в `StandTestAutoConfiguration`);
  - регистрирует исполнитель в `META-INF/services`, чтобы работать и на JUnit-пути
    (`StepExecutorDiscovery`);
  - обновляются счётчики артефактов в `CLAUDE.md`, `README.md` и `docs/publishing.md` (13 → 15:
    `stand-test-eq` и `stand-test-http`); `stand-test-http` тоже вносится в BOM.
- **BR-16.** Префикс типа `eq.` добавляется в `StepParameterKeys` рядом с `rest.` / `db.` / `ui.`.
- **BR-17.** Граф модулей (D-17): `rest → http → core`, `eq → http → core`, `eq → await`. `http` не
  зависит ни от одного адаптера и не содержит `StepExecutor`. Граф фиксируется в `CLAUDE.md` и в
  заглушках `Planned internal dependencies`; машинной проверки графа в репозитории нет, поэтому
  соответствие сверяется на ревью.

### 9.3 Бэкенды

- **BR-20.** Бэкенд выбирается **только реестром**: `eq-backends.<alias>.kind: showcases | gateway`.
  Код теста о бэкенде не знает: он ссылается на алиас записи (по умолчанию `eq`, BR-13), а какой
  `kind` за ним стоит, решает окружение.
- **BR-21.** Бэкенд `showcases`:
  - генерирует PIN (`T` + 5 символов `[A-Z0-9]`; префикс `T` сохраняет нынешний маркер тестового
    клиента), номер счёта (20 цифр, балансовый и валюта из атрибутов) и id сделки детерминированно из
    `testRunId` и порядкового номера шага. Сейчас тесты делают это сами из `UUID.randomUUID()`;
    перенос в SDK на `testRunId` делает значения воспроизводимыми по отчёту прогона. Формат id
    сделки повторяет нынешний (`<PIN>_<код пакета>`);
  - `ACLM[4]` (12 цифр) генерирует от `testRunId` для **всех** клиентов, а не константой
    `618418411698`: один тест намеренно делает его per-run, а общий на всех клиентов регистрационный
    атрибут — это случайная связь между тестами. Сравнение BR-51 покажет, если смена задела тест;
  - ставит дату открытия счёта и начала сделки «сегодня», если атрибут не задан (D-15);
  - строит записи `ACLM` / `ACLN` / `UACM` / `UDLM` (для ФЛ — коды из OQ-2) и отправляет их через
    REST-сервис, указанный в `eq-backends.<alias>.service` (алиас из `services` того же окружения,
    с его correlation и auth) через `stand-test-http` (D-17);
  - проверяет ответ: HTTP 200. Тела, из которого можно что-то забрать, у showcases нет (OQ-1
    частично закрыт); проверку тела на признак ошибки мока (R-9) уточняет фаза 0.
- **BR-22.** Бэкенд `gateway`:
  - ЮЛ: `ONU` → по каждому счёту `OKC` → `YFT2` → `KP1`;
  - ФЛ: `ONF` → `VAD` → по каждому счёту `OKC` → `YFT2`; `SPU` **один раз на клиента** (пакет ФЛ
    привязан к клиенту, а не к счёту; у библиотеки здесь дефект, Г-2);
  - протокол: `POST {base-url}` с телом `{unit, option, params}`. `correlationId` SDK внедряет в
    каждый запрос, если шлюз принимает заголовок (OQ-16); если не принимает, это исключение
    записывается в README модуля;
  - **каждый** ответ проверяется: PIN — `^[A-Z0-9]{6}$`, счёт — `^\d{20}$`, `KP1`/`SPU`/`YFT2`/`VAD`
    — по контракту успешного ответа (для `YFT2`/`VAD` контракт — OQ-5). Непроверяемый ответ считается
    ошибкой, а не успехом;
  - генерирует ИНН с корректными контрольными разрядами (10 для ЮЛ, 12 для ФЛ) и номер ДУЛ,
    уникальные в пределах прогона (BR-41).
- **BR-23.** Частичный сбой цепочки (клиент создан, счёт нет) — **ошибка шага** с перечнем уже
  созданных объектов (PIN, счета) в сообщении и в отчёте. Автоматического отката нет (D-9).
- **BR-24.** Счёт кассы для `YFT2` выбирается **по валюте счёта** из
  `eq-backends.<alias>.cash-accounts.<ccy>`. Если для валюты счёта кассы нет, это ошибка
  валидации до IO. Библиотека пополняла валютные счета из рублёвой кассы, Г-4.
- **BR-25.** **Записывающие операции шлюза не повторяются автоматически** (`ONU`, `ONF`, `VAD`,
  `OKC`, `YFT2`, `KP1`, `SPU`): повтор после неудачи может создать второго клиента или второе
  пополнение. Если ответ не пришёл за таймаут (NFR-04), шаг падает с отдельной ошибкой **«состояние
  неизвестно»**: операция, номер шага цепочки, уже подтверждённые объекты и маркер `testRunId`, по
  которому запись можно найти (BR-42). Единственный допустимый повтор — `ONU`/`ONF` с новым ИНН на
  явный ответ шлюза «ИНН уже существует» (BR-41), когда известно, что клиент не создан.
- **BR-26.** **Сериализация шлюза (D-11).** Бэкенд `gateway` держит в JVM одну очередь на пару
  `(base-url, unit)` после разрешения ссылок: два алиаса одного шлюза не обходят блокировку. Цепочка
  создания данных одного сценария выполняется целиком, прежде чем начнётся
  следующая. Ожидание видимости (§9.5) выполняется **вне** очереди, чтобы долгая проба одного
  сценария не задерживала создание данных других. Ожидание места в очереди ограничено
  (`eq-backends.<alias>.serialization.acquire-timeout`); по его истечении шаг падает
  инфраструктурной ошибкой с длиной очереди и временем ожидания. Время в очереди записывается в
  отчёт шага. Бэкенд `showcases` не сериализуется. Гарантия действует только внутри одной JVM:
  потребитель запускает тестовый набор с `maxParallelForks = 1`, а CI не запускает одновременно
  несколько JVM/jobs, пишущих в ту же пару `(base-url, unit)`. Если это ограничение невозможно,
  перед запуском на общем шлюзе нужен внешний координатор; локальный `Semaphore` его не заменяет.

### 9.4 Воспроизводимость атрибутов (D-6)

- **BR-30.** Каждый бэкенд объявляет **матрицу поддержки** атрибутов: поддерживается /
  приближается / не поддерживается. Первичная матрица:

  | Атрибут | showcases | gateway | Нужен мигрируемому набору |
  |---|---|---|---|
  | тип клиента, наименование, ФИО | да | да | да |
  | тип счёта, валюта | да | да | да |
  | сумма пополнения (баланс) | **нет** для подтверждённого `UACM` v1; другой формат не доказан | да (`YFT2`), после проверки контракта ответа | нет (в тестах не задаётся) |
  | пакет услуг | да (`UDLM`) | да (`KP1` / `SPU`) | да |
  | дата открытия счёта в прошлом | да | **нет** (только сегодня) | **нет** (D-15) |
  | дата начала сделки в прошлом | да | **нет** | **нет** (D-15) |
  | заданный PIN / счёт / id сделки | да | **нет** (выдаёт EQ) | нет (BR-33) |
  | ИНН клиента (переменная `.inn`) | **нет**: `ACLM[4]` помечен `INN`, но семантика тестового значения не подтверждена | да (генерирует SDK) | нет (тесты ИНН не используют) |
  | отделение счёта | да (`UACM[2]`) | частично: `GZAB` задаётся на уровне окружения, не шага | нет: текущие тесты используют `4101`; паритет test проверяется до пилота |
  | балансовый счёт (`40702` и т. п.) | да | нет, определяется типом счёта в EQ | нет, если тип `CA` на test даёт `40702` (OQ-9) |

- **BR-31.** Если сценарий требует атрибута, который бэкенд текущего окружения не поддерживает,
  адаптер отвергает его на фазе **`StepExecutor.prepare()`**, с перечнем атрибутов и именем бэкенда.
  Раннер вызывает `prepare` для всех шагов до первого `execute`, поэтому отказ происходит до любого
  сетевого вызова сценария. Валидатор core о матрице не знает и её не проверяет: это знание
  адаптера. Ошибка — `StandTestException` (несовпадение сценария и окружения, а не провал проверки).
- **BR-32.** `.allowApproximation(<атрибут>…)` разрешает приближение (например, дату «сегодня»
  вместо заданной). Каждое применённое приближение записывается в отчёт шага.
- **BR-33.** Задавать идентификаторы EQ (PIN, счёт) из теста запрещено в обоих режимах. Тест получает
  их только через переменные (D-5). Иначе тест, зелёный на ift, был бы заведомо невоспроизводим на
  test.

### 9.5 Видимость данных в TKS (D-14)

- **BR-35.** Ожидание видимости выполняет **сам шаг `EqSeed`** после создания данных и до
  публикации переменных. Отдельным шагом теста оно не делается. Причина: таймаут
  `rest.expectEventually` задаётся в коде теста (`RestStep.within` / `withinSeconds`, иначе
  `RestStepParameters.DEFAULT_TIMEOUT_MILLIS`), и реестр подставить его не может. Глобальный
  `stand.test.await.timeout` стартера создаёт общий бин `AwaitPolicy`, от окружения не зависит и
  значение по умолчанию для шагов не задаёт. Тест пришлось бы либо писать с таймаутом test-стенда и на
  ift, либо делать разным для двух режимов, а это нарушает BG-2.
- **BR-36.** Проба и её таймаут задаются в реестре окружения:
  `eq-backends.<alias>.visibility: { probe: { service, path, query, expect-status, expect-body }, timeout, poll-interval }`.
  - `expect-body` — проверка тела ответа: путь вычисляется `json-path` на том же диалекте `$.…`, что в
    проверках `RestStep`, извлечённое значение сравнивает матчер core (`AssertionMatchers`). Одного статуса мало: поисковый endpoint может отвечать 200 с пустым результатом на
    неизвестного клиента, и ожидание завершилось бы сразу и ложно;
  - вызов пробы идёт через `stand-test-http` (D-17) с correlation и auth сервиса `probe.service`;
  - в `probe.path`, `probe.query` и `expect-body` доступны `{seed.pin}` и `{seed.account}` — значения
    того шага `EqSeed`, который ждёт видимости, независимо от его алиаса в тесте. Синтаксис **без
    `$`** выбран намеренно: в `application.yml` Spring схлопывает `${…}` на старте, раньше, чем SDK
    увидит шаблон, а файловый загрузчик разрешает `${…}` сам. Это та же ловушка, что у полей `*-ref`
    реестра. В фазе 1 проверить, не решает ли задачу экранирование `\${…}` Spring 7 без нового
    синтаксиса;
  - значение `timeout` для test определяется замером перед пилотом (G0-TEST, OQ-6); без замера
    и настроенной пробы пилот на test не начинается. Если `probe` не объявлен,
    ожидания нет (ift). Опрос идёт через тот же `Awaiter`, что у `expectEventually`, но **таймаут
    пробы — это `StandTestException` (`BROKEN`), а не провал проверки**: невидимый клиент означает
    сломанное предусловие теста, а не дефект TKS, и в отчёте не должен выглядеть как красный тест.
    Диагностика (ключи `eq.*`, перечень созданных объектов) доходит до отчёта через
    `FailureAttachments`. То же правило — для любого провала `eq.seed`.
- **BR-37.** Что именно показывает клиента — знание потребителя: запись в его реестре и KB. Кандидаты
  — endpoint TKS или сама витрина, которую на test наполняет EQ (OQ-11). В коде SDK знаний о TKS и
  витринах нет. В KB это выражается типизированным разделом `eqBackends` окружения со ссылкой на
  endpoint пробы по его `id` и всеми полями, из которых рендерится runtime-раздел `eq-backends`.
  Схема KB закрыта (`additionalProperties: false` у `environment`), поэтому раздел добавляется
  в схему кита; его не дописывают вручную в реестр после `/stand-test-generate-env`.
  `ui-applications` сейчас не имеет источника в KB и сохраняется существующим merge-поведением
  генератора. Обещание «весь реестр только из KB» без отдельной модели UI здесь не даётся.

### 9.6 Предпроверка фазы юнита (D-10)

- **BR-38.** Для бэкенда `gateway` с объявленным `unit-phase` SDK читает фазу юнита программой
  `ALFAINSTAL/MONUNTSTS` через jt400 и **кеширует результат на время
  `unit-phase.cache-ttl`** (по умолчанию 5 минут). Кеш на всё время жизни JVM не годится: если юнит
  уйдёт в закрытие дня во время длинного прогона, кеш это скроет, и вместо одного понятного отказа
  будет серия непонятных (R-6). При ошибке шлюза фаза перечитывается, и её значение добавляется в
  сообщение об ошибке.
- **BR-39.** Проверка выполняется на фазе `prepare` шага `eq.seed`. Если фаза не входит в
  `unit-phase.allowed` (список значений — OQ-7), **каждый** сценарий с `eq.seed` падает на `prepare`
  одной и той же инфраструктурной ошибкой (`StandTestException`, не assertion) с текстом «юнит
  <unit> в фазе <фаза>». В пределах TTL обращение к AS/400 одно, вызовов шлюза — ни одного.
- **BR-40.** Учётные данные AS/400 задаются только в форме `username-ref` / `password-ref` (D-16) и
  не попадают в логи и отчёты.

### 9.7 Уникальность и маркировка

- **BR-41.** ИНН и номер ДУЛ уникальны в пределах прогона (счётчик в JVM) и между последовательными
  прогонами (соль из `testRunId`). Опора только на миллисекунды времени, как у библиотеки (Г-6),
  недопустима. **Ёмкость ИНН ЮЛ ограничена:** 10⁵ номеров на пару «регион + ИФНС». Клиенты на test
  не удаляются (D-9) и копятся от прогона к прогону, поэтому при фиксированной ИФНС вероятность
  коллизии достигает 50 % примерно на 370 клиентах. Отсюда два требования: код ИФНС выбирается из
  списка в реестре (`inn-tax-offices`), а не фиксируется; если EQ отвергает дубль ИНН (OQ-15),
  `ONU`/`ONF` повторяется с новым ИНН (BR-25).
- **BR-42.** Каждый созданный в EQ клиент маркируется `testRunId` (в наименовании или ином поле,
  которое можно найти поиском; поле и ограничения длины — OQ-8).
- **BR-43.** Общий список созданных объектов (окружение, `testRunId`, PIN, счета, ИНН, время)
  пишется в `eq-seeded.jsonl` в каталоге из системного свойства JVM
  `stand.test.eq.artifacts.dir` (не ключ `application.yml`). Формат — JSON Lines: одна строка
  на объект, дозапись под блокировкой для параллельных классов. Этот общий изменяемый файл
  **не прикладывается к отдельному шагу Allure**: он смешал бы сценарии и его путь по умолчанию
  лежит вне `RunArtifacts.directory`, откуда Allure разрешает FILE-вложения. Каждый `eq.seed`
  прикладывает отдельный неизменяемый TEXT-снимок собственного журнала операций через
  `StepResult.attachments()` или `FailureAttachments`; в снимок входят только поля NFR-05.
  Содержимое общего JSONL остаётся артефактом сопровождения набора, с отдельным правилом доступа
  и хранения, а не публичным вложением теста.

### 9.8 Конфигурация

- **BR-45.** Новый раздел реестра `eq-backends` в окружении — расширяемая секция (D-18). Формат реестра повышается до версии 6
  (сейчас `EnvironmentConfigFormat.SUPPORTED_VERSION = 5`). Реестр версии 5 без раздела продолжает
  загружаться. Раздел разбирают **оба** маппера, написанных руками (файловый в `stand-test-config` и
  стартерный), поэтому требуется тест паритета: один и тот же раздел, записанный для обоих
  front-end'ов, даёт одинаковую модель.
- **BR-46.** Форма записи значений раздела:
  - секреты — только `*-ref` (D-16);
  - адреса — `base-url` с `${VAR:умолчание}`, если умолчание известно, иначе `base-url-ref: VAR`;
  - прочие не-секретные параметры (юнит, отделение, кассовые счета, регион и коды ИФНС) —
    типизированное значение или `${VAR:умолчание}`, если умолчание известно; при отсутствии
    умолчания — объект `{ref: VAR}` на месте значения. Это применяется и к элементу карты
    `cash-accounts`, и ко всему списку `inn-tax-offices`; значение переменной для списка — JSON-массив.

  Правило для окружения `test` в общем `application.yml` потребителя: адрес или секрет без
  умолчания пишется как `*-ref`, прочее не-секретное поле — как `{ref: VAR}`. Парсер секции
  проверяет `ref` как голое имя переменной и разрешает его **лениво**, только для выбранного
  бэкенда; затем разбирает результат в объявленный тип и отвергает неверный тип. Иначе ift-прогон
  потребовал бы переменные test уже при Spring binding. Нельзя писать `${VAR}` без умолчания и
  рассчитывать на ленивость Spring. В коде SDK и тестов адресов и параметров стенда нет.
- **BR-47.** Пример реестра — Приложение В.

### 9.9 Миграция и кит

- **BR-50.** Все 16 сидирующих тестов потребителя переводятся на `EqSeed` и переменные:
  - константы `PIN`, `ACCOUNT` и `PILOT_*`, относящиеся к данным EQ, удаляются;
  - в фикстурах `__PIN__` / `__ACCOUNT__` заменяются на `${<alias>.pin}` / `${<alias>.account}`; прочие
    плейсхолдеры (`__NOW__`, `__DATE_*__`, `__DECISION__`, `__RATE__`, `__ID_TARIFF_DECISION__`,
    `__CLIENT_ID__`, `__ACCOUNT_ID__`, `__CREDIT_ORG__`) остаются значениями теста и подставляются, как
    сейчас, через `.replace(...)`. Форма «после» поэтому смешанная (Приложение А);
  - в SQL-параметрах `.param("pin", PIN)` заменяется на `.param("pin", "${<alias>.pin}")` (три теста,
    четыре места вызова, Приложение Д.4);
  - сидирование с прошлыми датами (`minusYears(1)`, `minusMonths(1)`, литералы пилота) удаляется
    без замены (D-15);
  - `CLIENT_ID` / `ACCOUNT_ID` — поля ЛТР-сообщения, а не данные EQ. Они остаются генерируемыми в
    тесте, если TKS не сверяет их с витринами или EQ (OQ-17).
- **BR-51.** До и после миграции тест даёт на ift одинаковый результат (включая honest-red).
  Проверка — три прогона набора до и три после, сравнение по тесту: исход, нормализованная причина
  и операция сбоя. Старые `seed-client`/`seed-account`/`seed-deal` сопоставляются с соответствующей
  операцией `EqSeed`; изменение статуса `FAILED` на `BROKEN` допускается **только при совпадении
  причины**, а не для любого сбоя сидирования. Причина извлекается из `exception.class`,
  HTTP-статуса и безопасного кода/категории ответа; новый адаптер пишет стабильный
  `eq.failure.category` и `eq.operation` в диагностику. Неопределённую причину и новое отличие
  разбирают отдельно и фиксируют как принятое изменение или дефект; автоматического «эквивалентно»
  для них нет. Этот же прогон проверяет D-15: чувствительность к дате сделки проявится здесь (R-12).
- **BR-52.** AI-кит учит `EqSeed`: скилл `java-dsl-authoring` (рецепт шага и список публикуемых
  переменных по бэкендам), полный типизированный раздел `eqBackends` окружения в схеме KB и его рендер скиллом
  `stand-test-env-generation`, правило guardrail «прямой `RestStep.post("showcases")` в новом тесте —
  только с тегом ift-only», оценочный кейс в `docs/agent-evaluation/dataset/`. Отдельной «KB-записи
  `eq-seed`» нет: в схеме KB нет типа для рецепта шага, и рецепт — знание авторинга, а не контракт
  системы.

## 10. Нефункциональные требования

- **NFR-01. Совместимость.** Модуль собирается на стеке SDK: toolchain по текущей JVM, `--release 17`,
  Spring Boot 4.1 / Spring 7, Jackson 3 (`tools.jackson.*`). Никаких Jackson 2 и Spring Boot 3 в
  транзитивных зависимостях. JSON-стек модуля: **Jackson 3** (`tools.jackson.core:jackson-databind`,
  версия — из BOM Spring Boot) для сборки тел запросов и разбора ответов; **`json-path`** — только для
  путей `expect-body`. `json-path` не сериализует, а его провайдер Jackson работает только с Jackson 2,
  поэтому библиотеки не взаимозаменяемы. Незадекларированная транзитивная `json-smart` не
  используется.
- **NFR-02. Изоляция.** Модуль не делает `@ComponentScan` и не кладёт `application.yml` на
  classpath. Бины регистрируются только автоконфигурацией стартера, у каждого есть
  `@ConditionalOnMissingBean`, имена с префиксом `standTest`.
- **NFR-03. Опциональность.** Потребитель без `stand-test-eq` на classpath стартует как раньше.
  jt400 нужен только при объявленном `unit-phase`: он подключается как optional-зависимость
  (`compileOnly` в модуле, версия — ограничением в BOM), чтобы IPL-лицензия (DEP-6) не уходила
  транзитивно всем потребителям.
- **NFR-04. Таймауты.** У `gateway` явно заданы connect / response таймауты в реестре. Бесконечного
  ожидания ответа быть не может. У библиотеки таймаут ответа не задан, Г-8. Истечение таймаута —
  «состояние неизвестно» (BR-25).
- **NFR-05. Диагностика.** По каждой операции EQ в отчёт шага попадает запись из разрешённых полей:
  `option`, номер операции, статус/категория результата, длительность и подтверждённые PIN/номера
  счетов. При ошибке добавляются `eq.failure.category`, `eq.operation` и номер шага цепочки.
  Полные request/response body, заголовки, `params`, ФИО, наименование, ИНН, ДУЛ и учётные данные
  в диагностике и вложениях Allure отсутствуют. Ответ проверяется по контракту, но в отчёте
  остаётся только классифицированный результат; маскирование Allure не считается защитой для
  неизвестной формы ответа. В первой
  версии это **вложение к шагу `eq.seed`**: событийная модель core (`StepEvent`, `ScenarioEvent`)
  вложенных шагов не поддерживает. Вложенные шаги Allure — доработка core и `stand-test-allure`,
  OQ-14.
- **NFR-06. Производительность.** Бюджет времени `EqSeed` на test определяется после замера цепочки на
  клиента и счёт). С учётом сериализации (BR-26) время создания данных всего набора на test растёт
  линейно по числу сценариев; бюджет задаётся и на сценарий, и на набор. На ift — не медленнее
  текущих трёх REST-вызовов.
- **NFR-07. Потокобезопасность.** Исполнитель без собственного состояния, как `RestStepExecutor`.
  Очередь шлюза, кеш фазы юнита, счётчики уникальности и журнал `eq-seeded.jsonl` — разделяемые
  объекты JVM, безопасные для параллельных классов потребителя. Это не координация между JVM;
  ограничение запуска задано в BR-26.

## 11. Безопасность и границы

- **SEC-01.** Бэкенд `gateway` пишет в реальный EQ. Он допускается только в окружении, где
  `eq-backends.<alias>.write-allowed: true`, по аналогии с `write-allowed` у datasource. Без флага
  сценарий отвергается на **`prepare` бэкенда `gateway`**, до первого вызова шлюза. Проверка живёт в
  адаптере, а не в валидаторе core: запись определяется `kind` бэкенда, который для core непрозрачен
  (D-18), а DSL бэкенда не знает (BR-20). Бэкенд `showcases` флага не требует: мок витрин —
  не запись в систему. Это код ошибки адаптера, а не константа `ForbiddenOperation`: правило
  репозитория требует, чтобы такую константу проверяли и валидатор, и guard, а здесь точка проверки
  одна (прецедент — коды `UI_LOGIN_ROLE_*`).
- **SEC-02.** Валидатор получает ветку `eq.` в проверке whitelist
  (`DefaultScenarioValidator.checkAliasWhitelist`). Сейчас неизвестный префикс там **молча не
  проверяется**, и новый адаптер без этой ветки остался бы без guardrail. Ветка покрывается тестом
  «срабатывает / перестаёт срабатывать при удалении», как остальные.
- **SEC-03.** Шлюз TAKSA сейчас доступен по HTTP без TLS и без аутентификации
  (`http://10.232.128.12:4567/api` у библиотеки). BRD фиксирует это как риск R-5. SDK поддерживает
  `auth` на `gateway` (схема как у services, учётные данные через `*-ref`), чтобы включить её без
  доработки, когда шлюз её получит.
- **SEC-04.** Учётка AS/400 — секрет и задаётся через `username-ref` / `password-ref` (D-16). В
  `application.yml` лежат только имена переменных. Значения не попадают в Spring Environment
  (actuator `/env`, дампы) и не остаются в git после ротации. Для ift учётка не нужна: ссылки
  разрешаются лениво, только когда бэкенд `gateway` читает фазу юнита. Замечание вне BRD: в реестре
  потребителя пароли БД сейчас записаны умолчаниями `${VAR:пароль}` и лежат в git. Их стоит
  ротировать и перевести на `*-ref`.
- **SEC-05.** Предпроверка фазы юнита только читает: `CALL` одной программы чтения статуса. Никаких
  CL-команд, меняющих состояние, и никакой подстановки пользовательских строк в CL. У библиотеки
  логин вставляется в текст команды, Г-9.
- **SEC-06.** Guardrails кита применяются к `EqSeed` так же, как к остальным шагам: нет адресов,
  секретов и фиксированных идентификаторов в тесте.

## 17. Критерии приёмки

- **AC-1.** Тест без `.environment()` проходит на ift при незаданной `APP_STEND` и на test при
  `APP_STEND=test`. Код одинаковый.
- **AC-2.** Тест с `.openedAt(прошлое)` без opt-in отвергается на test на фазе `prepare`, **до**
  первого сетевого вызова; с opt-in проходит, а отчёт показывает приближение.
- **AC-3.** Сбой `OKC` после успешного `ONU` даёт ошибку с PIN созданного клиента. Таймаут ответа на
  `ONU` даёт ошибку «состояние неизвестно» с маркером `testRunId`, повтора `ONU` нет.
- **AC-4.** Юнит не в рабочей фазе: каждый сценарий с `eq.seed` падает на `prepare` одной и той же
  инфраструктурной ошибкой; обращение к AS/400 — одно в пределах TTL кеша; вызовов шлюза — ни одного.
- **AC-5.** В контексте потребителя нет бинов модуля вне автоконфигурации; нет Jackson 2 и
  Spring Boot 3 в `runtimeClasspath`; jt400 нет в `runtimeClasspath` потребителя, который не
  объявил `unit-phase`.
- **AC-6.** Все пункты Приложения Г закрыты тестами модуля.
- **AC-7.** Сценарий с прямым `RestStep.post("showcases")` на test отвергается валидатором до IO
  (`NON_WHITELISTED_SERVICE`).
- **AC-8.** При десяти параллельных сценариях с `eq.seed` на бэкенде `gateway` в любой момент
  выполняется не больше одной цепочки на пару `(base-url, unit)` в одной JVM; ожидания видимости
  идут параллельно; истечение `acquire-timeout` даёт инфраструктурную ошибку с длиной очереди.
  Конфигурация пилота подтверждает `maxParallelForks = 1` и отсутствие одновременных CI jobs на
  ту же пару; при ином запуске требуется внешний координатор (BR-26).
- **AC-9.** В `application.yml` с окружением `test`, записанным по BR-46, прогон на ift проходит
  без единой переменной стенда test.
- **AC-10.** После перевода на `stand-test-http` тесты `stand-test-rest` проходят без изменений, а
  публичный API `RestStep` не меняется.
- **AC-11.** В `stand-test-core` нет типов и полей, специфичных для EQ: раздел `eq-backends` виден
  core только как расширяемая секция с алиасами; из EQ-имён в core есть лишь wire-константы
  маршрутизации в `StepParameterKeys` (префикс `eq.`, ключ `backend`, имя секции `eq-backends`).
