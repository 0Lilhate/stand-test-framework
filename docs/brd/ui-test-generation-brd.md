## 1. Резюме

`stand-test-sdk` сегодня закрывает интеграционные и e2e-проверки на уровне протоколов (REST, Kafka,
JDBC, gRPC) против реальных DEV/IFT-стендов и уже поставляет **AI-authoring-кит** (`docs/ai-agent/`),
которым агент в хосте (Claude Code / opencode) превращает текстовый кейс в готовый Java-автотест под
guardrails.

Предлагается закрыть последний непокрытый слой — **пользовательский интерфейс**, и закрыть его тем же
способом: не «ещё одна UI-библиотека», а **UI как ещё один тип шага в существующей модели сценария**
плюс расширение кита, чтобы агент писал UI-тест сам, а недостающие детали добирал, **открывая живой UI
на стенде и проходя по нему**.

Заявляемое отличие от отдельных UI-фреймворков — **один сценарий проверяет и экран, и его
backend-последствия**: клик в интерфейсе, затем проверка сообщения в Kafka и записи в БД в том же
тесте, связанные захваченными с экрана данными (а где backend протягивает корреляцию — общим
`correlationId`), с единым отчётом. Это **гипотеза ценности, а не установленный факт**;
условия её подтверждения и опровержения заданы в §12 (KPI-5) и §19. Контраргумент — смешение слоёв
удлиняет тест и размывает диагностику — разобран в §7, D-7.

Горизонт — 2–3 квартала, поставка волнами (§18). Стоимость и модель окупаемости — §13; условия, без
которых проект не стартует, — §14; условия, при которых он закрывается, — §19.

## 2. Контекст и постановка проблемы

### 2.1 Что есть сейчас

- SDK покрывает REST / Kafka / DB / gRPC; UI-слой не покрыт вообще.
- UI-регресс в командах выполняется преимущественно вручную либо разрозненными Selenium-проектами без
  общих guardrails, единого механизма ожиданий, единой отчётности и `testRunId`/`correlationId`.
- Написание одного UI-автотеста занимает у автоматизатора часы: нужно вручную обойти экран, подобрать
  локаторы, разложить ожидания, вычистить flaky.
- Ручной тестировщик, знающий бизнес-кейс лучше всех, не может довести его до автотеста
  самостоятельно — нет входа без навыка кода.

> **Все четыре утверждения — экспертная оценка, а не замер.** Числовые базы (часы на тест, доля
> покрытого регресса, текущий flaky rate, число дефектов рассинхрона UI↔backend) подлежат измерению
> **до старта разработки** — см. предусловие G-2 в §14. Без этого ни ROI (§13), ни метрики (§12) не
> доказуемы.

### 2.2 Боль

| Симптом | Следствие для бизнеса |
|---|---|
| Ручной UI-регресс | Долгий цикл релиза, регресс — узкое горло перед выкладкой |
| Дорогое написание автотеста | Автоматизируются только самые критичные пути, длинный хвост кейсов не покрыт |
| Flaky UI-тесты | Падениям не верят, красный CI перестаёт быть сигналом |
| Разрыв UI и backend | Дефект «на экране ок, а в топик не ушло» ловится только в проде |
| Знание кейса и навык кода — у разных людей | Потери на передаче контекста между ручным QA и автоматизатором |

### 2.3 Почему это делаем внутри `stand-test-sdk`, а не отдельным продуктом

1. Комбинированные проверки UI + Kafka/DB/REST в одном сценарии возможны только при общей модели
   сценария и общем `VariableStore`: значение, захваченное с экрана, переиспользуется в проверке
   Kafka/БД. Там, где backend протягивает корреляцию, к этому добавляется общий `correlationId`
   (AS-07).
2. Guardrails (`ForbiddenOperation`, реестр сред, запрет прода, запрет секретов в коде) уже написаны и
   протестированы — UI попадает под них без дублирования.
3. AI-кит с пайплайном стадий и гейтами уже существует; UI добавляется как новая ветка авторинга, а не
   как новый продукт со своим жизненным циклом.

Вопрос «а стоит ли делать вообще» рассмотрен отдельно — §3.

## 3. Альтернативы

| # | Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|---|
| A-0 | **Не делать ничего.** UI-регресс остаётся ручным | Нулевые затраты | Боль из §2.2 сохраняется; регресс остаётся блокером релиза; длинный хвост кейсов не покрыт никогда | Отвергнут при условии, что замер G-2 подтвердит масштаб боли. **Если замер покажет, что ручной регресс не является узким местом — этот вариант выигрывает**, см. §19 |
| A-1 | **Купить коммерческую AI/low-code платформу** (Testim, Mabl, Katalon и аналоги) | Быстрый старт, готовый self-healing, поддержка вендора | Внешний SaaS с доступом к тестовым контурам и данным — отдельное согласование ИБ; сквозные проверки UI+Kafka+БД невозможны или требуют самописных плагинов; лицензии на команду; вендор-лок; тесты живут вне git | Отвергнут: главная заявленная ценность (§1) недостижима, а ИБ-контур делает срок внедрения сопоставимым с разработкой |
| A-2 | **Отдельный Playwright-проект без SDK и без агента** | Минимальная связность, свобода команд | Не решает главную боль (стоимость написания теста); нет общих guardrails, отчётности, `correlationId`; каждая команда строит своё | Отвергнут: экономит разработку модуля, но не даёт ни одной из бизнес-целей §4.1 |
| A-3 | **Только кит: агент пишет тесты поверх чужого UI-фреймворка команды** | Дёшево, SDK не трогаем | Нет единых guardrails и await-механизма; агент генерирует под N разных фреймворков — качество и безопасность не гарантируются; сквозные проверки невозможны | Отвергнут (был явной развилкой на этапе постановки) |
| A-4 | **Модуль SDK + расширение кита** (предлагаемый) | Сквозные сценарии; переиспользование guardrails, реестра сред, отчётности, пайплайна кита; тесты в git потребителя | Требует разработки модуля; ответственность за поддержку остаётся внутри | **Принят** |

Экономическое сравнение A-0/A-1/A-4 — §13.4.

## 4. Цели и результаты

### 4.1 Бизнес-цели

- **BG-1.** Сократить стоимость создания UI-автотеста до <1 человеко-часа включая ревью (базовое
  значение — по замеру G-2).
- **BG-2.** Поднять долю автоматизированного критичного UI-регресса до уровня, при котором ручной
  регресс перестаёт быть блокером релиза. Измеримое выражение цели — **длительность ручного регресса
  перед выкладкой**; KPI-2 (доля покрытия ≥60%) — рабочая прокси-метрика, и связь «60% ⇒ не блокер»
  подтверждается замером G-2, а не постулируется.
- **BG-3.** Сделать UI-автотесты доверенным сигналом качества — управляемый flaky rate,
  воспроизводимость, внятная диагностика падения.
- **BG-4.** **Снизить порог входа для ручных тестировщиков:** тестировщик формулирует кейс в
  структурированном виде и получает готовый тест, не написав кода. Ревью и сопровождение остаются на
  автоматизаторе — самостоятельного владения Java-тестом от ручного QA **не ожидается** (см. D-4 и
  ограничение в §8, UC-01).
- **BG-5.** Ловить рассинхрон «UI ↔ backend» на стенде, а не в проде **(гипотеза, подлежащая проверке
  — KPI-5)**.

### 4.2 Что считается результатом (Definition of Success)

Команда даёт агенту структурированный кейс и алиас приложения на IFT → получает Java-тест на JUnit 5 с
Page Object'ами, прошедший автоматические гейты безопасности и качества → тест ревьюит автоматизатор →
тест стабильно прогоняется в CI и падает преимущественно на реальных дефектах. Количественные пороги —
§12, условия признания успеха и неудачи — §19.

### 4.3 Вне целей (Non-goals)

- Не строим собственный агентный рантайм в этом репозитории — агентом остаётся хост
  (Claude Code / opencode). Решение зафиксировано ранее и не пересматривается.
- Не заменяем ручное исследовательское тестирование.
- Не автоматизируем нагрузочное и security-тестирование UI.
- Не тестируем мобильные нативные и desktop-приложения (только web, включая мобильные вьюпорты).
- Не даём агенту доступ к промышленному контуру ни при генерации, ни при прогоне.
- Не делаем ручного тестировщика самостоятельным владельцем сгенерированного кода (см. BG-4).

## 5. Стейкхолдеры и владение

| Роль | Интерес | Влияние на требования |
|---|---|---|
| **QA-инженеры автоматизаторы** | Основные потребители: ревьюят, дорабатывают и **владеют** сгенерированным | Читаемость Java-теста, Page Objects, отсутствие «магии», отладка локально в headed-режиме |
| **Ручные тестировщики без навыков кода** | Превращают свой кейс в автотест без написания кода | Простой вход (структурированный кейс / ссылка на Jira), понятный отчёт о генерации; ревью — не их зона |
| **Разработчики продуктовых команд** | Пишут тесты к своему фиче-бранчу | Быстрая генерация, локальный прогон, интеграция с их сборкой |
| **QA-лиды / руководство качества** | Метрики покрытия, стабильность, скорость | Отчётность, измеримые KPI (§12) |
| **Команда `stand-test-framework`** | Владелец SDK и кита | Сохранение архитектурных инвариантов (core — сток графа зависимостей, без IO) |
| **Информационная безопасность** | Секреты, доступы, границы контуров, ПД | §11 |
| **Владельцы инфраструктуры CI** | Браузеры в CI, grid/Selenoid, ресурсы, бюджет | §13.2, §15 |

## 6. Область (Scope)

### 6.1 В области

1. Новый рантайм-модуль SDK (рабочее имя `stand-test-ui`): UI-шаги, локаторы, ожидания,
   скриншоты/трейсы, интеграция с существующим отчётом и `correlationId`.
2. Расширение AI-кита (`docs/ai-agent/`): скиллы и команды для разведки UI, проектирования UI-сценария,
   авторинга Java-теста с Page Objects, а также UI-специфичные проверки в safety- и quality-ревью.
3. Комбинированные сценарии «UI + REST/Kafka/DB/gRPC» в одном тесте.
4. Расширение реестра сред (`stand-test-environments.yml` / `stand.test.environments.*`) логическими
   алиасами UI-приложений и стратегией аутентификации.
5. Расширение базы знаний (KB) сущностями UI: экраны, элементы, пользовательские флоу — с сохранением
   обратной совместимости схем (BR-36).
6. Виды генерируемых проверок: позитивный путь и валидации форм; негативные и краевые кейсы;
   визуальные регрессы; доступность, кросс-браузерность, адаптивность.
7. Контролируемая подмена сетевых ответов для проверки поведения UI при отказе backend (BR-33).
8. Прогон в CI (headless в контейнере), на централизованном grid/Selenoid и локально в headed-режиме.

### 6.2 Вне области

- Нативные мобильные приложения, desktop-приложения.
- Тестирование через изображение экрана без DOM (CV-подход).
- Автоматическая правка теста в рантайме прогона (self-healing) — см. D-3.
- Собственная ферма браузеров — используется инфраструктура организации.
- Автоматический коммит и merge сгенерированного теста без человеческого ревью.
- **Автоматическое распознавание и маскирование персональных данных на растровом изображении**
  (OCR-подход) — маскирование выполняется до снятия снимка, по разметке (BR-35, SEC-05).
- **Генерация нагрузочных, security- и мутационных проверок UI.**
- **Миграция существующих Selenium-наборов команд** — новые тесты пишутся заново, старые доживают свой
  срок; конвертер не разрабатывается.
- **Тестирование сторонних (вендорских) веб-интерфейсов**, на которые нет влияния по вёрстке и
  доступам.

## 7. Зафиксированные решения

| # | Решение | Обоснование |
|---|---|---|
| **D-1** | Поставка = **модуль SDK + расширение кита** | Единственный вариант, дающий сквозные UI+backend проверки при общих guardrails (§3, A-4) |
| **D-2** | Драйвер — **Playwright for Java** | Автоожидания вместо `Thread.sleep`, trace/video/screenshot из коробки, устойчивые локаторы, перехват сети (BR-33), headless в CI. *Формально это техническое решение: при переработке фиксируется отдельным ADR, BRD на него ссылается* |
| **D-3** | Агент использует браузер **только на этапе генерации** | Прогон в CI детерминирован и не требует доступа к модели; совпадает с решением «агент — это хост, рантайма в репозитории нет» |
| **D-4** | Артефакт генерации — **Java-тест JUnit 5 + Page Objects** | Ревьюится и сопровождается автоматизатором, живёт в git потребителя. **Следствие, принимаемое сознательно:** ручной тестировщик не может самостоятельно отревьюить и починить результат — BG-4 ограничена соответствующим образом. Декларативный YAML — второй трек (BR-32), решение по нему по итогам Фазы 1 (OQ-09) |
| **D-5** | `data-testid` — **рекомендация, не требование** | Нельзя блокировать поставку на изменениях в продуктовых командах. **Компенсация:** отчёт агента перечисляет хрупкие локаторы, и при превышении порога (§12, KPI-9) вопрос эскалируется на архитектурный комитет как отдельная инициатива |
| **D-6** | **Поставка волнами внутри горизонта 2–3 кварталов** | «Широкий запуск» реализуется как управляемое расширение: волна 1 — 2–3 приложения, волна 2 — расширение после гейта §19.1, волна 3 — масштабирование. Это снимает противоречие с митигациями RISK-08/RISK-10, которые требуют контролируемого первого шага |
| **D-7** | Сквозные UI+backend сценарии **допустимы, но не обязательны**; диагностика падения обязана указывать слой | Контраргумент «смешение слоёв размывает диагностику» принимается: отчёт указывает, на каком шаге и в каком слое произошёл отказ (BR-22), а сценарий можно разделить тегами на UI-часть и backend-часть без переписывания |
| **D-8** | Связывание UI-действия с backend-эффектом — **по захваченным данным**; `correlationId` предпочтителен, но не является обязательным условием | Сегодня SDK владеет `correlationId` и инжектит его исходящим. В UI-цепочке заголовок уходит из браузера, и чтобы дойти до Kafka, его обязан протянуть **backend продукта**, а топик — объявить HEADER-носитель (единственный реализованный). Это требование к чужим системам, поэтому оно вынесено в допущение AS-07 и в гейт G-6, а BR-13 сформулировано так, чтобы отсутствие протягивания понижало качество связывания, но не делало Must-требование невыполнимым |
| **D-9** | Откат данных, созданных через UI, **требует доработки `stand-test-core`**: компенсации не-DB шагов | Существующий механизм — undo-log с компенсаторами, и единственный, кто их регистрирует, — DB-адаптер; сценарных компенсирующих шагов поверх REST/UI нет, а дефолтная `CleanupPolicy` — `ON_FAILURE` (на зелёном прогоне данные остаются намеренно). BR-24 для UI требует и нового механизма, и политики `ALWAYS`. Работа учтена отдельной строкой в §13.1 и фиксируется отдельным ADR |
| **D-10** | Совместимость реестра сред при добавлении UI-алиасов решается **версионированием файла** | Загрузчик реестра fail-closed: неизвестный ключ среды отвергается как ошибка конфигурации. Значит общий `stand-test-environments.yml` с секцией UI-приложений перестал бы читаться проектами на старой версии SDK. Файл получает явную версию формата, старые версии SDK распознают её и дают внятный отказ вместо «unknown key» (BR-37) |

## 8. Пользовательские сценарии

**UC-01. Ручной тестировщик доводит свой кейс до автотеста.**
Даёт агенту структурированный кейс и алиас приложения на IFT → агент открывает UI, проходит флоу,
задаёт уточняющие вопросы только по действительно неоднозначным местам → выдаёт тест и отчёт о том, что
покрыто и под какими допущениями → **тест уходит на ревью автоматизатору, который становится его
владельцем**. Ручной тестировщик не правит код и не отвечает за его сопровождение (BG-4, D-4).

**UC-02. Автоматизатор покрывает новую фичу до её релиза.**
Даёт ссылку на задачу в Jira и макет Figma → агент сверяет ожидаемый UI с реализацией на стенде, пишет
позитивный сценарий и негативные кейсы → автоматизатор правит 1–2 места и коммитит.

**UC-03. Сквозная проверка «клик → backend».**
Кейс: «оформление заявки в портале». Агент генерирует тест: заполнение формы в UI → ожидание успешного
состояния на экране → проверка события в Kafka → проверка записи в БД → откат тестовых данных.
Развёрнутая иллюстрация — **Приложение А**.

**UC-04. Разработчик проверяет свой бранч.**
Локальный headed-прогон существующего теста, отладка по трейсу.

**UC-05. Дрейф UI сломал тесты.**
Тест падает в CI → отчёт о падении (скриншот, трейс, `scenarioId`/`testRunId`/`correlationId`) → агент
по команде отладки классифицирует: дефект продукта, дрейф UI или инфраструктура → предлагает патч.

**UC-06. Ночной регресс.**
Набор UI-тестов прогоняется в CI headless, результат — единый отчёт с метриками стабильности.

### 9.2 Полнота покрытия («узкие места»)

| ID | Требование | Критерий приёмки | Приоритет |
|---|---|---|---|
| BR-10 | Позитивный сценарий: основной путь от входа до подтверждения результата | Покрыт для каждого кейса эталонного набора | M |
| BR-11 | Валидации форм: обязательные поля, граничные значения, формат ввода, тексты ошибок | Для формы с N валидациями сгенерировано не менее N проверок либо перечислены пропуски с причиной | M |
| BR-12 | Негативные и краевые кейсы: пустые состояния, отсутствие прав, повторный/двойной клик, потеря сессии | Каждый применимый к экрану случай покрыт либо явно отброшен с причиной | M |
| BR-13 | Комбинированные проверки: UI-действие и его backend-последствия в одном сценарии. Связывание — **по захваченным с экрана данным либо по `correlationId`**; `correlationId` предпочтителен, но доступен только там, где backend продукта протягивает его от фронтенда до Kafka/БД (D-8, AS-07, DEP-08) | Сценарий связывает UI-захват и backend-проверку по данным или по `correlationId`, а не по совпадению; выбранный способ связывания назван в отчёте генерации (BR-07) | M |
| BR-14 | Визуальные регрессы: сравнение с эталоном, управляемые пороги, маскирование динамических зон | Ложные срабатывания на стабильном экране за 20 прогонов — 0 | S |
| BR-15 | Кросс-браузерность: минимум Chromium и Firefox для критичного набора | Критичный набор зелёный в обоих браузерах | S |
| BR-16 | Адаптивность: прогон отмеченных сценариев на мобильном вьюпорте | Вьюпорт задаётся конфигурацией, тест не дублируется | S |
| BR-17 | Доступность (a11y): автоматические проверки на ключевых экранах | Отчёт содержит перечень нарушений с уровнем | C |
| BR-33 | **Контролируемая деградация backend:** перехват и подмена сетевых ответов (5xx, таймаут, пустой ответ) для проверки поведения UI. Перехват разрешён **только по паттернам внутри origin алиаса приложения**; подмена, переадресующая запрос на посторонний origin, блокируется гейтом наравне с литеральным URL (SEC-01) | Тест воспроизводит отказ детерминированно, без вмешательства в стенд; факт подмены виден в отчёте; гейт блокирует перехват с внешним origin | S |

> **Трейд-офф по BR-33.** Подмена ответов означает, что часть проверок перестаёт быть полностью
> сквозной: браузер получает искусственный ответ вместо стендового. Это сознательное отступление от
> принципа «только реальные стенды» — иначе поведение UI при отказе backend непроверяемо в принципе.
> Такие шаги обязаны быть помечены в отчёте, чтобы их не путали со сквозными.
>
> **Вторая сторона трейд-офа — guardrails.** Перехват сети — это и способ подменить *любой* запрос
> браузера, то есть потенциальный обход вайтлиста хостов изнутри теста. Поэтому область перехвата
> ограничена origin'ом алиаса приложения, а выход за него приравнивается к литеральному URL
> (SEC-01) и блокируется гейтом, а не остаётся на усмотрение автора теста.

## 10. Нефункциональные требования

| ID | Требование | Целевое значение и метод проверки |
|---|---|---|
| NFR-01 | **Определение и цель flaky rate** | *Определение:* доля прогонов теста, завершившихся падением, которое не подтвердилось дефектом продукта при разборе, на скользящем окне 20 прогонов. | NFR-05 | Изоляция архитектуры | `stand-test-core` не получает зависимостей от Playwright и любого IO; **модель сценария не получает UI-специфичных полей** (вьюпорт, браузер, локаторы — вне `Scenario`, см. BR-31); проверяется тестом графа зависимостей в сборке |
| NFR-06 | Совместимость с существующими тестами | Подключение UI-модуля не ломает написанные REST/Kafka/DB/gRPC-тесты; проверяется прогоном существующего набора |

## 11. Безопасность, границы и комплаенс

| ID | Требование | Приоритет |
|---|---|---|
| SEC-01 | **Промышленный контур запрещён жёстко.** Агент и тесты работают только с DEV/IFT; хосты проверяются по вайтлисту реестра, произвольные URL блокируются | M |
| SEC-02 | **Запрет разрушающих действий при разведке.** Агент не выполняет необратимых операций («Удалить», «Подтвердить платёж», массовые операции) без явного подтверждения человека. Это поведенческое правило, а не машинно-проверяемый guardrail — оно опирается на SEC-10 | M |

### 13.3 Модель окупаемости

```
Экономия в год = N_тестов_в_год × (T_ручное_написание − T_с_агентом) × C_час
               + N_регресс_прогонов × T_ручной_регресс × C_час
               − T_сопровождение_набора × C_час

Окупаемость (мес) = (Разработка + Инфраструктура_год) / (Экономия_в_год / 12)
```

Где `T_ручное_написание`, `T_ручной_регресс` и `N_*` берутся из замера G-2, а `T_с_агентом` — целевое
значение KPI-1.

**Оговорка о двойном счёте.** В командах уже есть разрозненные Selenium-наборы (§2.1), а их миграция
вне области (§6.2). Значит часть регресса автоматизирована и не даёт экономии от замены ручного
прогона. G-2 обязан разделить: объём **ручного** регресса, объём, покрытый существующими наборами, и
ту его часть, которая будет переписана заново. В формулу входит только первое слагаемое и
переписываемая часть — иначе экономия завышается.

**Порог принятия решения:** проект признаётся экономически оправданным, если расчётная окупаемость
≤ `‹18 месяцев›` при консервативном сценарии (экономия × 0,5). Иначе — вариант A-0 или A-1 из §3.

**Чувствительность.** Модель наиболее чувствительна к `T_сопровождение_набора`: при дрейфе UI выше
ожидаемого (RISK-04) сопровождение съедает экономию от генерации. Поэтому KPI-7 (MTTR) — не
второстепенная метрика, а вход в бизнес-кейс.

### 13.4 Сравнение вариантов (заполняется на G-2)

| Вариант | Разработка | Год эксплуатации | Сквозные проверки | Согласование ИБ |
|---|---|---|---|---|
| A-0 «не делать» | 0 | стоимость ручного регресса `‹сумма›` | нет | не требуется |
| A-1 коммерческая платформа | внедрение `‹сумма›` | лицензии `‹сумма›` | нет / только через доработку | внешний SaaS с доступом к контурам — длительное |
| A-4 предлагаемый | `‹сумма›` | `‹сумма›` | да | внутреннее (G-4) |

## 15. Допущения и зависимости

### Допущения

- **AS-01.** UI-приложения имеют развёрнутые работоспособные стенды DEV/IFT с доступом из сети CI.
- **AS-02.** Продуктовые команды не обязаны добавлять `data-testid` (D-5), поэтому часть локаторов
  строится по ролям и тексту — с более высоким риском дрейфа. Локатор по роли и доступному имени
  завязан на **текст интерфейса**: правка формулировки, а не только перевёрстка, ломает такой тест;
  для мультиязычных приложений локаль прогона фиксируется конфигурацией (BR-31).
- **AS-03.** Сгенерированный тест всегда проходит человеческое ревью перед merge.
- **AS-04.** Хост-агент (Claude Code / opencode) доступен инженерам; отдельный API-ключ и собственный
  рантайм не требуются. Стоимость подписок учтена в §13.2.
- **AS-05.** Тестовые данные, созданные через UI, поддаются удалению доступными средствами (UI, API или
  БД); для каждого приложения волны способ подтверждён до начала работ.
- **AS-06.** Стенды DEV/IFT достаточно стабильны, чтобы их недоступность не превышала `‹порог›` прогонов;
  превышение делает NFR-01 недостижимым по причинам вне проекта.
- **AS-07.** Сквозная передача `correlationId` **не предполагается по умолчанию**. Заголовок, который
  SDK инжектит в запросы браузера, доходит до Kafka/БД только если backend продукта его протягивает, а
  топик объявляет HEADER-носитель (единственный реализованный в SDK). Где этого нет, связывание
  выполняется по захваченным с экрана данным (D-8, BR-13); наличие протягивания фиксируется по
  приложениям на гейте G-6.
- **AS-08.** Приложения волны позволяют выделить учётную запись для разведки, лишённую прав на
  необратимые операции (SEC-10). Без этого SEC-02 не имеет технической опоры.

> Вопрос MFA/OTP/КАПЧИ перенесён из допущений в предусловие G-1: он определяет исполнимость, а не
> вероятностный риск.

### Зависимости

- **DEP-01.** Инфраструктура CI: образ с браузерами либо доступ к grid/Selenoid, квоты, бюджет.
- **DEP-02.** Реестр сред с алиасами UI-приложений и secret-ref для учётных записей.
- **DEP-03.** Пул технических учётных записей с нужными ролями, включая учётку разведки без
  необратимых прав (BR-34, SEC-10, G-5).
- **DEP-04.** Доступ агента к Jira/Confluence (BR-02) и Figma (BR-04).
- **DEP-05.** Хранилище эталонных снимков для визуальных регрессов (BR-14).
- **DEP-06.** Согласование ИБ по §11 (G-4).
- **DEP-07.** Назначенные владельцы наборов в командах-потребителях (§17, G-6).
- **DEP-08.** Для сценариев, связываемых по `correlationId`: протягивание корреляционного заголовка
  командой-владельцем backend от фронтенда до Kafka/БД и объявленный HEADER-носитель у топика
  (AS-07). Отсутствие зависимости не блокирует BR-13 — понижает способ связывания до данных.

## 17. Операционная модель

### 17.1 Владение

- Владелец **сгенерированного теста** — автоматизатор команды-потребителя, принявший его на ревью
  (RACI, §5). Автор кейса владельцем не становится.
- Владелец **набора команды** — QA-лид команды: приоритеты, карантин, удаление мёртвых тестов.
- Владелец **модуля SDK и кита** — команда `stand-test-framework`: дефекты платформы, версии, миграции.

### 17.2 Сопровождение

- Красный ночной регресс разбирается владельцем набора в течение рабочего дня (KPI-7).
- Классификация падения — через команду отладки (BR-26): дефект продукта → дефект в бэклог команды;
  дрейф UI → перегенерация или правка Page Object; инфраструктура → эскалация владельцам стендов.
- Тест, не починенный за 2 недели, уходит в карантин; в карантине >2 недель — удаляется из набора
  (RISK-13). Молчаливое отключение проверок запрещено: удаление фиксируется в отчёте команды.
- Дефекты платформы (не теста) — в бэклог команды SDK с SLA `‹согласовать›`.

### 17.3 Внедрение и обучение

- Волна 1: команда SDK сопровождает 2–3 команды вручную, собирает обратную связь и метрики.
- Материалы: обновление `docs/ai-agent/usage-guide.md` UI-разделом, шаблон структурированного кейса для
  ручных тестировщиков, разбор одного реального кейса на команду.
- Волна 2 и далее: самообслуживание по документации, поддержка командой SDK по запросу.

## 19. Критерии приёмки и остановки

### 19.1 Гейт после волны 1 (продолжаем / корректируем / останавливаем)

> **Оговорка о профиле замера.** Волна 1 покрывает позитивный путь и валидации форм (BR-10, BR-11);
> негативные и краевые кейсы (BR-12) — волна 2. Самая трудная для агента часть в замер не попадает,
> поэтому KPI-4 и KPI-1 волны 1 — оптимистичная оценка, и решение «продолжаем» принимается с этим
> знанием. Пороги ниже подобраны с запасом именно по этой причине.

**Продолжаем**, если одновременно:
- KPI-4 (принято без правок) ≥40% — генерация даёт экономию, а не перекладывает работу на ревью;
- KPI-3 (flaky) ≤5% на наборе волны 1;
- KPI-1 (часы на тест) ≤50% базы, замеренной на G-2, — половина пути к цели пройдена;
- расчётная окупаемость по §13.3 при консервативном сценарии ≤ `‹18 мес›`.

**Корректируем скоуп**, если один показатель не достигнут: сокращаем волну 2 до минимума, устраняем
причину, повторяем гейт через `‹6 недель›`.

**Останавливаем**, если два и более показателя не достигнуты либо KPI-1 не опустился ниже базы G-2
более чем на четверть: генерация не даёт выигрыша против ручного написания, и дальнейшие вложения не
оправданы. Пороги выражены **относительно базы**, а не абсолютным числом часов: при базе 10 ч
абсолютный порог «4 ч» закрыл бы проект, дающий ускорение в два с лишним раза.

### 19.2 Гейт после волны 2

- **KPI-5 <2** — гипотеза сквозной ценности не подтверждена: BR-13 понижается до Should, ценность
  решения пересматривается против A-1 (§3), сквозные сценарии остаются как возможность, но перестают
  быть аргументом бизнес-кейса.
- **KPI-6 <2 команд** — адоптации нет: до расширения выясняется причина; масштабирование волны 3
  замораживается.
- **KPI-7 >2 рабочих дней** — сопровождение дороже генерации: пересматривается §17 или сокращается
  набор.

### 19.3 Условия признания успеха по горизонту

Все целевые значения §12 достигнуты, гейты 19.1 и 19.2 пройдены, окупаемость подтверждена фактическими
затратами, ≥3 команд эксплуатируют решение самостоятельно.

### А.1. Вход: структурированный кейс от ручного тестировщика

```text
Кейс CP-204. Оформление заявки на кредитный продукт в клиентском портале.

Предусловия: пользователь с ролью «клиент», продукт «Экспресс-кредит» доступен на стенде.
Шаги:
  1. Войти в портал.
  2. Открыть «Заявки» → «Новая заявка».
  3. Выбрать продукт «Экспресс-кредит», указать сумму 100 000, срок 12 месяцев.
  4. Подтвердить заявку.
Ожидаемо: на экране появляется номер заявки и статус «Принята»;
заявка уходит в обработку (событие в очереди) и появляется в витрине заявок.
Проверить также: сумма меньше минимальной (1 000) — форма не отправляется, показывается ошибка.
```

Всё, что не сказано в кейсе — конкретные локаторы, тексты подсказок, поведение кнопки во время
отправки, имя топика и таблицы — агент добирает: интерфейс он **открывает на стенде и проходит сам**,
контракты backend берёт из базы знаний (BR-03, BR-05).

### А.2. Конфигурация: алиас приложения и вход по secret-ref

Агент не пишет URL и учётные данные в тест — он дописывает алиас в реестр сред (BR-27, BR-28, SEC-01,
SEC-04):

```yaml
# stand-test-environments.yml
version: 2                                      # версия формата файла, BR-37: старый SDK отказывается
                                                # внятно, а не как на «неизвестном ключе»
environments:
  ift:
    ui-applications:
      client-portal:
        base-url-ref: CLIENT_PORTAL_IFT_URL     # имя переменной окружения, не значение
        viewport: desktop                       # профиль прогона — конфигурацией, не кодом (BR-31)
        auth:
          scheme: FORM                          # FORM | SSO | STORAGE_STATE — ключ `scheme`,
                                                # как у сервисов, а не `type` (BR-37)
          credentials-pool-ref: CLIENT_PORTAL_TEST_USERS   # пул учёток по ролям, BR-34
          roles: [client, operator, no-rights]  # роли, которые сценарий может запросить
          discovery-account-ref: CLIENT_PORTAL_DISCOVERY   # учётка разведки без необратимых прав,
                                                           # SEC-10
```

### А.3. Page Object: единственное место, где живут локаторы

```java
package example.qa.portal.pages;

import ru.alfa.stand.test.ui.UiLocator;
import ru.alfa.stand.test.ui.UiStep;

/**
 * Экран «Новая заявка» клиентского портала.
 *
 * <p>Локаторы собраны здесь, чтобы дрейф вёрстки чинился в одном файле (RISK-02).
 * Приоритет локаторов: data-testid → роль + доступное имя → текст. Поля «сумма» и «срок»
 * data-testid не имеют — использована роль; см. отчёт о генерации, п. «хрупкие локаторы».
 */
public final class NewApplicationPage {

    private static final String APP = "client-portal";

    private static final UiLocator PRODUCT = UiLocator.testId("application-product");
    private static final UiLocator AMOUNT = UiLocator.role("textbox", "Сумма");
    private static final UiLocator TERM = UiLocator.role("textbox", "Срок, месяцев");
    private static final UiLocator SUBMIT = UiLocator.role("button", "Подтвердить заявку");
    private static final UiLocator STATUS = UiLocator.testId("application-status");
    private static final UiLocator NUMBER = UiLocator.testId("application-number");
    private static final UiLocator AMOUNT_ERROR = UiLocator.testId("application-amount-error");

    private NewApplicationPage() {
    }

    public static UiStep open() {
        return UiStep.open(APP, "/applications/new")
                .id("open-new-application")
                .injectCorrelationId()
                .expectVisible(SUBMIT)
                .build();
    }

    public static UiStep fill(String product, String amount, String term) {
        return UiStep.form(APP)
                .id("fill-application-form")
                .select(PRODUCT, product)
                .type(AMOUNT, amount)
                .type(TERM, term)
                .build();
    }

    public static UiStep submit() {
        return UiStep.click(APP, SUBMIT)
                .id("submit-application")
                .build();
    }

    public static UiStep awaitAccepted() {
        return UiStep.expectEventually(APP, STATUS)
                .id("await-accepted-status")
                .assertText("Принята")
                .withinSeconds(20)
                .capture("applicationNumber", NUMBER)
                .screenshot("application-accepted")
                .build();
    }

    public static UiStep expectAmountError(String message) {
        return UiStep.expectEventually(APP, AMOUNT_ERROR)
                .id("await-amount-error")
                .assertTextContains(message)
                .withinSeconds(10)
                .build();
    }

    public static UiLocator submitButton() {
        return SUBMIT;
    }
}
```

```java
 * (открывается в новой вкладке PDF — вне текущей области UI-модуля).
 */
@SpringBootTest
@EnabledIfEnvironmentVariable(named = "CLIENT_PORTAL_IFT_URL", matches = ".+")
class NewApplicationTest {

    @Autowired
    private StandClient stand;

    @Test
    @DisplayName("Заявка оформляется в портале, публикуется в очередь и попадает в витрину")
    void applicationIsCreatedAndProjected() {
        Scenario scenario = Scenario.builder("cp-204-new-application")
                .environment("ift")
                .tag("ui")
                .tag("e2e")
                .tag("client-portal")
                // Политика ALWAYS: заявка отзывается и на зелёном прогоне тоже (BR-24);
                // дефолт ON_FAILURE оставил бы данные после успешного теста.
                .cleanupPolicy(CleanupPolicy.ALWAYS)
                // Учётка запрашивается по роли из кейса, а не «любая из пула» (BR-34).
                .step(UiStep.login("client-portal")
                        .id("login")
                        .role("client")
                        .build())
                .step(NewApplicationPage.open())
                .step(NewApplicationPage.fill("Экспресс-кредит", "100000", "12"))
                .step(NewApplicationPage.submit())
                .step(NewApplicationPage.awaitAccepted())
                // Связывание по correlationId доступно, потому что для client-portal подтверждено
                // протягивание заголовка от фронтенда до топика (G-6, AS-07). Где не подтверждено —
                // строка correlationIdFromContext() опускается, и связывание держится на
                // ${applicationNumber} ниже (BR-13, D-8).
                .step(KafkaStep.expect("application-events")
                        .id("await-application-event")
                        .correlationIdFromContext()
                        .withinSeconds(30)
                        .assertPath("$.type", "APPLICATION_CREATED")
                        .assertPath("$.applicationNumber", "${applicationNumber}")
                        .build())
                .step(DbStep.expectEventually("applications-db")
                        .id("verify-showcase")
                        .sql("SELECT status FROM showcase.applications WHERE application_number = :number")
                        .param("number", "${applicationNumber}")
                        .expectValue("IN_PROGRESS")
                        .withinSeconds(30)
                        .build())
                // Откат данных, созданных через UI: заявка отзывается сервисным вызовом (BR-24).
                // Способ очистки подтверждён для этого приложения (AS-05, OQ-06).
                // ВНИМАНИЕ: сценарных компенсирующих шагов в SDK сегодня нет — сейчас компенсации
                // регистрирует только DB-адаптер. Требует доработки core (D-9, §13.1).
                .cleanup(RestStep.post("application-service", "/api/applications/${applicationNumber}/withdraw")
                        .id("withdraw-application")
                        .expectStatus(200)
                        .build())
                .build();

        ScenarioResult result = stand.run(scenario);

        assertThat(result.isSuccessful()).isTrue();
    }

    @Test
    @DisplayName("Сумма ниже минимальной: форма не отправляется, показана ошибка")
    void amountBelowMinimumIsRejected() {
        Scenario scenario = Scenario.builder("cp-204-amount-below-minimum")
                .environment("ift")
                .tag("ui")
                .tag("negative")
                .tag("client-portal")
                .step(UiStep.login("client-portal")
                        .id("login")
                        .role("client")
                        .build())
                .step(NewApplicationPage.open())
                .step(NewApplicationPage.fill("Экспресс-кредит", "999", "12"))
                .step(NewApplicationPage.submit())
                .step(NewApplicationPage.expectAmountError("Минимальная сумма — 1 000"))
                .step(UiStep.expect("client-portal", NewApplicationPage.submitButton())
                        .id("submit-still-on-form")
                        .assertEnabled(true)
                        .build())
                .build();

        ScenarioResult result = stand.run(scenario);

        assertThat(result.isSuccessful()).isTrue();
    }
}
```

Что здесь принципиально:

- **Ни одного `Thread.sleep` и ни одного фиксированного ожидания** — только `expectEventually` с
  ограниченным таймаутом через единый await-механизм (BR-23).
- **Ни одного URL и ни одного пароля** — алиас `client-portal` и `login(...)` берут и то и другое из
  реестра, учётка выдаётся из пула (BR-27, BR-34, SEC-04).
- **`${applicationNumber}`** захвачен с экрана и переиспользован в проверках Kafka и БД: UI-действие и
  его backend-след связаны данными, а не догадкой. Это **основной** механизм связывания;
  `correlationId` добавляет второй контур там, где backend его протягивает, и опускается там, где нет
  (BR-13, D-8, AS-07).
- **Cleanup** выполняется и на упавшем, и на успешном сценарии — за счёт явной политики
  `CleanupPolicy.ALWAYS`; дефолт `ON_FAILURE` оставил бы заявку после зелёного прогона (BR-24).
- **Негативный кейс** проверяет не только текст ошибки, но и то, что форма осталась на месте — иначе
  проверка «зелёная» и на сломанном экране (BR-12).

## 22. Приложение Б. Пример сгенерированного YAML-сценария

> ### 📌 Пометка команды SDK, 2026-08-04 (`UITG-F002`, конфликт `CONF-03`)
>
> **Текст приложения не изменялся.** Как и §21, это иллюстрация намерения, а не описание формата:
> норма — ADR-UI-003 и код. Одно утверждение ниже подтвердилось и стоит выделить, потому что оно
> определяет объём: **JSON Schema для UI-шагов действительно не существует и сегодня** — `ui.*`
> остаётся Java-треком, декларативный трек отложен (`UITG-S046`) и BRD §18 сам ставит его
> существование в зависимость от ответа на OQ-09.

> **Статус приложения.** Решение D-4 фиксирует основным артефактом Java-тест с Page Objects. YAML —
> **второй трек** (BR-32, приоритет Should), и приложение показывает, как выглядел бы тот же кейс
> CP-204 в декларативном виде, чтобы решение о втором треке (OQ-09) принималось по факту, а не по
> описанию. Формат повторяет существующий AI-формат SDK
> (`docs/ai-agent/.claude/skills/stand-test-yaml-authoring/example-generated.yaml`), расширенный
> UI-шагами; JSON Schema для них ещё не существует.
>
> **Объём расширения схемы шире, чем кажется** (BR-32). Помимо новых типов шагов требуется:
> 1. **Новая грамматика ассершенов.** Существующий `assertion` обязателен по `path` и допускает ровно
>    один матчер над JSONPath; UI-проверки (`text`, `visible`, `enabled`) устроены иначе и в этот
>    def не укладываются.
> 2. **Раздел `cleanup` верхнего уровня.** Сегодня его в формате нет вообще: корень схемы закрыт
>    `additionalProperties: false` и содержит только `id`, `title`, `description`, `environment`,
>    `tags`, `steps`. Блок `cleanup:` ниже — это предлагаемое расширение, а не существующая
>    конструкция, и он опирается на ту же доработку core, что и Java-трек (D-9).
>
> Оба пункта входят в оценку решения OQ-09 — иначе второй трек выглядит дешевле, чем он есть.

### Б.3. Чем этот трек отличается от Java (Приложение А)

| Свойство | YAML (AI-формат) | Java + Page Objects |
|---|---|---|
| Проверка до запуска | JSON Schema отсекает недопустимые конструкции ещё до компиляции — самый безопасный вход для генерации | Компилятор + гейты |
| Порог входа для чтения | Читается ручным тестировщиком без знания Java — единственный трек, реально закрывающий BG-4 целиком | Требует навыка чтения кода |
| Переиспользование локаторов | Дублируются между файлами: **Page Object'а нет** — при дрейфе вёрстки правится каждый сценарий | Один Page Object на экран |
| Сложная логика | Ограничена набором шагов схемы: условия, циклы, вычисления недоступны | Полный Java |
| Отладка | Только через отчёт прогона | Точки останова, headed-режим, трейс |

**Следствие для UI.** Ровно та причина, по которой YAML силён на протокольных тестах (жёсткая схема,
узкий набор конструкций), делает его слабее на UI: локаторы размазываются по файлам без единой точки
исправления, а дрейф вёрстки — самый частый источник правок (RISK-02). При этом именно YAML —
единственный трек, при котором ручной тестировщик может прочитать и проверить результат сам. Поэтому
решение по BR-32 вынесено на гейт после волны 1 (OQ-09), когда будут данные о KPI-4 и о доле простых
линейных сценариев.

## 23. Глоссарий

| Термин | Значение |
|---|---|
| **Стенд (DEV/IFT)** | Реальный тестовый контур, против которого работают тесты; Testcontainers сознательно не используется |
| **Агент** | LLM-агент в хосте (Claude Code / opencode), который читает кейс, ходит по UI и пишет тест. Собственного агентного рантайма репозиторий не содержит |
| **Кит (AI-authoring kit)** | Набор скиллов, команд, правил и гейтов под `docs/ai-agent/`, устанавливаемый в проект потребителя |
| **База знаний (KB)** | Курируемое описание контрактов (сервисы, эндпоинты, топики, таблицы, а также экраны и флоу), из которого агент берёт факты вместо догадок |
| **Реестр сред** | Конфигурация, отображающая логические алиасы на адреса стендов и ссылки на секреты; точка контроля вайтлиста |
| **Guardrails** | Машинно-проверяемые запреты (прод, произвольные URL, секреты в коде, разрушающие операции, `Thread.sleep`) |
| **Гейт** | Обязательная проверка: либо автоматическая между стадиями генерации (находка BLOCK останавливает выдачу), либо управленческая между волнами (§14, §19) |
| **Волна** | Этап поставки с фиксированным составом приложений и командами; переход к следующей — только через гейт §19 |
| **Page Object** | Класс, инкапсулирующий локаторы и действия одного экрана; точка локализации изменений UI |
| **`testRunId` / `correlationId`** | Идентификаторы прогона и сквозной цепочки. `correlationId` принадлежит SDK и инжектится исходящим, но в UI-цепочке доходит до Kafka/БД **только если backend продукта его протягивает** (AS-07); базовый способ связать UI-действие с backend-следом — захваченные с экрана данные |
| **Связывание по данным** | Значение, захваченное с экрана (номер заявки, идентификатор), переиспользуемое в backend-проверке того же сценария через `VariableStore`. Основной механизм BR-13, работающий независимо от корреляции |
| **Flaky-тест** | Тест, падение которого не подтверждается дефектом продукта при разборе (определение и метод замера — NFR-01) |
| **Хрупкий локатор** | Локатор, построенный не по `data-testid`, а по роли, доступному имени или тексту |
