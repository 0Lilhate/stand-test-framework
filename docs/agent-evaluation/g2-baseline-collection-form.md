# Форма сбора базы G-2 — KPI-1, KPI-2, KPI-3, KPI-5

Форма для гейта **G-2** (`UITG-X002`): значения **ДО** внедрения, с которыми сравниваются замеры
волны 1. Парная к [`kpi-collection-template.md`](kpi-collection-template.md), который меряет сторону
**ПОСЛЕ** — «по прогонам эталонного набора и по смерженным тестам волны 1».

Заполняется QA-лидами. Определения KPI — §12 BRD [`../brd/ui-test-generation-brd.md`](../brd/ui-test-generation-brd.md);
здесь только процедура, знаменатели и то, чем каждое число **не** является.

> **Почему это отдельный документ, а не раздел шаблона.** Шаблон объявляет себя формой замеров после
> внедрения и держит для базы **одну клетку** — «База G-2 (ручной путь), ч-ч» — не говоря, откуда её
> взять. Двух из четырёх нужных баз он не покрывает **по собственному признанию**: «`KPI-2`… `KPI-5` —
> не волна 1 либо не корпус». Смешать «до» и «после» в одном документе значит однажды сравнить число
> с самим собой.

> **Правило заполнения — то же, что в шаблоне, и это не совпадение, а требование.** Пустая клетка
> означает «не мерили», прочерк — «мерили, значения нет». Никогда не заполняйте клетку значением,
> полученным иначе, чем описано в её строке: два числа с одинаковым названием и разными источниками —
> худшее, что может случиться с гейтом «продолжаем или останавливаем».

## Шапка замера

| Поле | Значение |
|---|---|
| Дата замера | |
| Кто мерил | |
| Период наблюдения | напр. «последние 6 месяцев» — база это практика, а не один спринт |
| Приложения волны 1 | из G-6 (`UITG-X006`) |

| Замер повторяем? | **да / нет** — если нет, назвать, что мешает |

## §13.3 — разделение объёма регресса. **Заполняется первым**

Оговорка BRD §13.3 о двойном счёте: в командах уже есть разрозненные Selenium-наборы, их миграция вне
области. Значит **часть регресса автоматизирована и не даёт экономии** от замены ручного прогона.
Модель окупаемости берёт только два слагаемых из трёх, и без этого разделения экономия завышается.

| Категория кейсов критичного регресса | Кол-во | Как считали |
|---|---|---|
| (A) Прогоняются **вручную** | | |
| (B) Покрыты **существующими** наборами и остаются как есть | | **не даёт экономии** |
| (C) Покрыты существующими наборами, но будут **переписаны** | | |
| **Итого перечень критичного регресса** | | A + B + C |

> **В формулу окупаемости входят A и C. B — не входит.** Это единственное место формы, ошибка в
> котором не видна в самом числе: она проявится только тем, что окупаемость окажется лучше, чем есть.

## KPI-1 (база) — стоимость **ручного** создания UI-автотеста

Человеко-часы от получения кейса до merge, включая ревью, **на сегодняшнем пути без агента**. Это то
самое число, для которого шаблон держит клетку «База G-2 (ручной путь), ч-ч».

| Кейс / тест | Ч-ч: разбор кейса | Ч-ч: написание | Ч-ч: отладка | Ч-ч: ревью и merge | **Итого ч-ч** | Комментарий |
|---|---|---|---|---|---|---|
| | | | | | | |

| Сводка | Значение |
|---|---|
| Тестов в выборке (знаменатель) | |
| **Медиана ч-ч на тест** | |
| Разброс (min–max) | |
| Откуда взято | тайм-трекинг / замер на выборке / оценка |

Чем это число **не** является: временем «написать тест», если под ним понимать только набор кода.
Ревью и отладка входят — иначе база окажется меньше настоящей, а `KPI-1` волны 1 будет сравниваться с
заниженным ориентиром и выглядеть хуже, чем есть.

**Порог §19.1 читает это число:** цель `KPI-1` — **≤50 % базы**. То есть завышенная база делает гейт
проходимым незаслуженно, заниженная — непроходимым.

## KPI-2 (база) — покрытие критичного UI-регресса автотестами

**Абсолютная величина, а не прирост** (§12 BRD). Знаменатель — перечень критичного регресса из
раздела §13.3 выше, то есть A + B + C.

| Сводка | Значение |
|---|---|
| Кейсов в перечне критичного регресса (знаменатель) | из §13.3, строка «Итого» |
| Покрыто автотестами сегодня (числитель) | = B + C |
| **KPI-2 база, %** | |
| Перечень критичного регресса существует? | **да / нет** |

> **Если перечня критичного регресса нет — это и есть результат замера,** а не повод его отложить.
> Запишите «нет», и `KPI-2` окажется неизмеримым до тех пор, пока перечень не заведут: цель «≥60 % к
> концу горизонта» без знаменателя не проверяется ничем.

## KPI-3 (база) — flaky rate существующих наборов

По определению `NFR-01`: доля прогонов, завершившихся падением, **не подтверждённым дефектом продукта
при разборе**, на скользящем окне **20 прогонов**. Падения по недоступности стенда исключаются и идут
отдельным счётчиком.

| Набор | Прогонов | Красных | Подтверждённые дефекты | Флейк | Недоступность стенда | **Flaky rate** |
|---|---|---|---|---|---|---|
| | | | | | | |

| Сводка | Значение |
|---|---|
| Прогонов всего (знаменатель) | |
| Флейк-прогонов | |
| **KPI-3 база, %** | |
| Недоступность стенда, % | порог **≤5 %** — решение `UITG-X009` |

Красный прогон, нашедший настоящий дефект, — **не** флейк. Смешивать их нельзя: иначе набор выглядит
тем стабильнее, чем меньше он находит.

**Если существующих наборов нет или они не прогоняются регулярно** — так и запишите. `KPI-3` базы в
этом случае не существует, и цель «≤5 % на волне 1» сравнивать не с чем; это факт о состоянии, а не
пробел в форме.

## KPI-5 (база) — валидация гипотезы UI↔backend

| Сводка | Значение |
|---|---|
| Дефектов рассинхрона, пойманных сквозными сценариями | **0** |
| Основание | сквозных UI+backend сценариев не существует: `BR-13` относит их к волне 2 |

**Это единственная база, которая известна заранее и не требует замера.** Она равна нулю **по
построению**, а не по результату наблюдения, и BRD ставит её базой явно. Строка присутствует в форме
затем, чтобы ноль был *записан*, а не *подразумевался*: пустая клетка здесь прочиталась бы как «не
мерили».

## Что эта форма не измеряет

- **`KPI-4`, `KPI-6`, `KPI-7`, `KPI-8`, `KPI-9`** — у них нет стороны «до»: они описывают работу
  агента и набора, которых до внедрения не существовало. `KPI-4` и `KPI-9` меряются
  [`kpi-collection-template.md`](kpi-collection-template.md).
- **Стоимость человеко-часа.** Это `OQ-10` (`UITG-X011`), владелец — Руководство качества; форма даёт
  часы, а не деньги.
- **Качество существующих наборов по существу.** Форма считает, сколько кейсов покрыто, и не
  утверждает, что покрыто правильно.

## Куда попадают эти числа

| Число | Куда |
|---|---|
| `KPI-1` база | клетка «База G-2 (ручной путь), ч-ч» в [`kpi-collection-template.md`](kpi-collection-template.md); `T_ручное_написание` в §13.3 BRD |
| §13.3 A и C | слагаемые формулы экономии; B **не входит** |
| `KPI-2` база | порог §19.1 «≥60 % к концу горизонта» |
| `KPI-3` база | порог §19.1 «≤5 % на волне 1» |
| `KPI-5` база | порог §19.2 «≥5 за волну 2; менее 2 — гипотеза не подтверждена» |

Формат таблиц и правило заполнения намеренно повторяют парный шаблон: первый критерий приёмки
`UITG-V006` требует, чтобы формат базы совпадал с форматом последующих замеров, — **иначе сравнивать
нечего с чем**.
