# Шаблон сбора KPI-1, KPI-3, KPI-4, KPI-9

Форма для замеров гейта §19.1 BRD на волне 1. Заполняется **человеком по прогонам эталонного
набора** ([`dataset/`](dataset/)) и по смерженным тестам волны 1. Определения KPI — §12 BRD
[`../brd/ui-test-generation-brd.md`](../brd/ui-test-generation-brd.md); здесь только процедура,
знаменатели и то, чем каждое число НЕ является.

Три числа из четырёх считаются командами ниже — вручную, но воспроизводимо; каждая команда приведена
целиком, чтобы замер повторил кто угодно, а не только тот, кто его придумал. **KPI-9 с задачи
`UITG-S024` считает инструмент** — подкоманда `kpi-locators` гарда (см. соответствующий раздел):
метрика запускает эскалацию, и ручной подсчёт по грепу здесь означал бы, что триггер зависит от
того, кто и как посчитал.

> **Правило заполнения.** Пустая клетка означает «не мерили», прочерк — «мерили, значения нет».
> Никогда не заполняйте клетку значением, полученным иначе, чем описано в её строке: два числа с
> одинаковым названием и разными источниками — это худшее, что может случиться с гейтом «продолжаем
> или останавливаем».

## KPI-1 — стоимость создания UI-автотеста (цель ≤1 ч, гейт: ≤50% базы G-2)

**Человеко-часы** от получения кейса до merge, включая ревью человеком. Машинное время генерации
(NFR-02) — отдельная строка: это вход в стоимость подписок, а не в трудозатраты.

| Кейс / тест | Ч-ч: интейк и вопросы | Ч-ч: ревью и правки | Ч-ч: merge | **Итого ч-ч** | Машинное время, мин | Комментарий |
|---|---|---|---|---|---|---|
| | | | | | | |

| Сводка | Значение |
|---|---|
| Тестов в замере (знаменатель) | |
| Медиана ч-ч на тест | |
| База G-2 (ручной путь), ч-ч | |
| Доля от базы | |

Чем это число **не** является: временем работы агента. Прогон, вернувшийся вопросом, стоит человеку
времени на ответ — и это время входит сюда, иначе KPI-1 будет измерять удобство агента, а не
экономию команды.

## KPI-3 — flaky rate (цель ≤5% на волне 1)

По определению NFR-01: доля прогонов теста, чей результат менялся без изменений в тесте и в системе.
Меряется **только повторными прогонами** — одиночный зелёный прогон о флейкости не говорит ничего.

| Тест | Прогонов | Красных | Из них подтверждённые дефекты | Из них флейк | **Flaky rate** | Причина флейка |
|---|---|---|---|---|---|---|
| | | | | | | |

| Сводка | Значение |
|---|---|
| Прогонов всего (знаменатель) | |
| Флейк-прогонов | |
| **KPI-3** | |

Красный прогон, нашедший настоящий дефект, — **не** флейк, и смешивать их нельзя: иначе набор
выглядит тем стабильнее, чем меньше он находит.

В корпусе `repeats: 3` стоит у двух кейсов (`flaky-every-third-fails`, `ui-pos-support-request-registered`);
у UI-кейса это задел — до подключения браузерного дубля или живого стенда его `execution.outcome`
равен `NOT_RUN`, и KPI-3 по корпусу не считается вовсе.

## KPI-4 — доля тестов, принятых без правок (цель ≥60%, гейт §19.1: ≥40%)

Диф между **исходной выдачей генерации** (снимок по BR-07, раздел 8 отчёта) и смерженным файлом.
Правка — изменение исполняемых строк теста или Page Object; форматирование и переименования не
считаются.

```bash
# по одному сгенерированному набору: снимок против смерженного
diff -ru ui-generation/<scenario-id>/original/ src/test/java/<пакет>/ui/
# быстрый ответ «правили или нет» — только по хешам
sha256sum -c ui-generation/<scenario-id>/original.sha256
```

| Тест | Снимок есть? | Файлов | Изменённых исполняемых строк | Правка по определению? | Что именно правили |
|---|---|---|---|---|---|
| | | | | | |

| Сводка | Значение |
|---|---|
| Тестов с сохранённым снимком (знаменатель) | |
| Принято без правок | |
| **KPI-4** | |
| Тестов без снимка — **вне знаменателя** | |

Тест без снимка исходной выдачи в знаменатель **не входит**: BRD говорит прямо, что без базы дифа
метрика ненаблюдаема. Считать такой тест «принятым без правок» — самый дешёвый способ получить
хороший KPI-4 и ничего им не сказать.

## KPI-9 — доля хрупких локаторов (триггер эскалации >50%)

Считается **статически по Page Object'ам смерженного набора** — не по отчётам генерации. Источник
намеренно другой: метрика запускает эскалацию политики `data-testid` на архитектурный комитет и не
должна зависеть от самооценки агента.

Хрупкий — всё, кроме `TEST_ID` (единственное определение — `UiLocator.fragile()`).

```bash
# Инструмент, а не греп: числитель, знаменатель, разбивка по стратегиям и ПЕРЕЧЕНЬ хрупких локаторов
node .claude/hooks/stand-guard.mjs kpi-locators src/test/java
# машинный вывод для протокола замера
node .claude/hooks/stand-guard.mjs kpi-locators src/test/java --json
```

Что даёт инструмент сверх грепа и почему именно это важно:

- **локатор, названный в комментарии, не считается** — строка правила «никогда не пишите здесь
  `UiLocator.css(...)`» грепом читается как использование стратегии, которую она запрещает;
- **пустой каталог даёт «знаменатель 0», а не 0%** — иначе лучший возможный KPI-9 получает тот, кто
  измерил пустоту;
- **прогон не блокируется никогда**: превышение порога помечается как триггер эскалации, код
  возврата остаётся 0. Метрика, роняющая сборку, — метрика, которую перестают считать;
- вывод содержит `файл:строка` каждого хрупкого локатора: заявка продуктовой команде на
  `data-testid` состоит из этого перечня, а не из процента.

| Приложение / набор | Локаторов всего | `testId` | role+name | label | text | css | **Хрупких, %** |
|---|---|---|---|---|---|---|---|
| | | | | | | | |

| Сводка | Значение |
|---|---|
| Локаторов всего (знаменатель) | |
| Хрупких | |
| **KPI-9** | |
| Из них **ломких** CSS (цепочка ≥3 шагов, `nth-child`, сгенерированный класс, тег-шаг, комбинатор, индекс) | |
| Превышен ли порог 50% | |

Ломкость и хрупкость — разные вопросы, и таблица отвечает на оба: короткий атрибутный селектор
хрупок, но не ломок, и заявка продуктовой команде выглядит иначе в этих двух случаях.

**Замер на сегодняшних артефактах репозитория** (см. отчёт о готовности): единственный существующий
эталонный Page Object даёт 5 локаторов, из них 3 хрупких — **60%**, выше порога эскалации. Это число
инструмент воспроизводит на каждом прогоне сборки (`KpiLocatorCountTest` в `stand-test-ai-schema`),
поэтому оно не разойдётся с примером молча. Это не
KPI-9 волны 1: знаменатель — один файл примера, а не смерженный набор. Строка нужна затем, чтобы
показать, что порог достижим не в теории и что разговор с продуктовыми командами про `data-testid`
начинается не после замера, а до него.

## Замеры прогона набора (не KPI, но именно их спрашивают первыми)

Считаются по каталогу `batch/` после прогона и по артефактам, которые сессии записали.

| Показатель | Как считается | Знаменатель | Значение |
|---|---|---|---|
| Compile success | `./gradlew compileTestJava checkstyleTest` в проекте-потребителе после прогона; PASS/FAIL на тест | тесты, которые кейс ТРЕБОВАЛ произвести (`expected.artifacts.required` содержит `ui-test`) | |
| Доля необоснованно выдуманных деталей | каждый локатор и каждый асcертируемый текст артефакта ищется в `seeded/UiDiscoveryReport.md` своего кейса; не найденный = выдуманный | все локаторы и тексты произведённых артефактов | |
| Хрупкие локаторы присутствуют | по формуле KPI-9 над произведёнными Page Object'ами | локаторы произведённых Page Object'ов | |
| Литеральных URL нет | `node <bundle>/hooks/stand-guard.mjs scan <произведённые файлы>` — находка `HARDCODED_STAND_URL` | произведённые артефакты | |
| `Thread.sleep` нет | тот же скан — находка `THREAD_SLEEP` | произведённые артефакты | |
| Артефакт, который кейс запрещал | `batch-report.md`, колонка «Ожидание» | кейсы с `expected.artifacts.forbidden` | |

Про «долю выдуманных деталей» отдельно: она **потому и измерима**, что шесть UI-кейсов отдают отчёт
разведки готовым. Против живого приложения знаменателя нет — сравнивать пришлось бы с DOM в момент
прогона, а он к моменту разбора уже другой. Это единственное место, где подсаженный отчёт даёт
корпусу то, чего живой прогон не даёт.

## Что этот шаблон не измеряет

- **KPI-2 (покрытие критичного регресса), KPI-5 (гипотеза UI↔backend), KPI-6, KPI-7, KPI-8** — не
  волна 1 либо не корпус. KPI-5 требует волны 2 по построению.
- **Качество разведки.** Корпус подсаживает её результат; что агент действительно откроет живое
  приложение и посмотрит, не измеряется ничем.
- **Правильность теста по существу.** Ни один гейт корпуса не утверждает, что тест проверяет
  правильную вещь: это остаётся за человеком, и `stand-batch.mjs` пишет это в каждом своём отчёте.
