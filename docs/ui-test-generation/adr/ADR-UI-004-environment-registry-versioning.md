# ADR-UI-004: Версионирование реестра сред и алиасы UI-приложений

**Статус:** Proposed · **Дата:** 2026-08-01 · **Волна:** 1

## Контекст

BR-37 и D-10 требуют версионировать файл реестра сред, потому что загрузчик fail-closed и добавление
секции UI-приложений сделает общий файл нечитаемым для проектов на старой версии SDK.

Сверка с кодом ([`00-current-state.md`](../00-current-state.md) §7.2) подтверждает диагноз и
уточняет его.

```java
// stand-test-config/.../EnvironmentConfig.java
private static final Set<String> ROOT_KEYS = Set.of("environments");
private static final Set<String> ENV_KEYS  = Set.of("services", "topics", "datasources",
        "grpc-targets", "grpcTargets", "kafka-cluster", "kafkaCluster",
        "kafka-clusters", "kafkaClusters");
// …
throw new StandTestException("Unknown field '" + key + "' at " + location + " (allowed: " + known + ")");
```

Файл из Приложения А.2 BRD отвергается **дважды**:
`Unknown field 'version' at <document> (allowed: environments)` и
`Unknown field 'ui-applications' at environments.ift (allowed: …)`. Сообщение называет поле, но не
говорит «файл новее вашего SDK — обновитесь».

**Следствие, которого нет в формулировке D-10** (Q-06): **введение версии само по себе является
ломающим изменением для уже выпущенных версий SDK.** Обещание «старая версия отказывается внятно»
достижимо только для тех версий, которые ключ `version` уже знают. Задним числом поведение
выпущенного артефакта не меняется.

Два обстоятельства делают вопрос решаемым дёшево — **сейчас**:

1. **SDK ещё не публиковался.** Публикация параметризована (`standTestPublish*`), но эндпоинт не
   назначен и первого реального выпуска не было (`docs/publishing.md`). Окно совместимости сегодня
   **пусто**.
2. Поверхностей две: файл (`EnvironmentConfig`) и Spring (`StandTestProperties` +
   `EnvironmentRegistryFactory`) — у них **разные мапперы**, и дрейф между ними уже зафиксирован как
   известный риск проекта.

## Рассматриваемые варианты

**А. Ввести `version` в `ROOT_KEYS` немедленно, отдельным изменением, до UI-секции.**
В первом релизе ключ принимается и проверяется на «не больше поддерживаемой»; UI-секция приходит
следующим релизом.

**Б. Ввести `version` вместе с UI-секцией, одним изменением.**

**В. Не версионировать; сделать `ui-applications` игнорируемым неизвестным ключом.**
Ослабить fail-closed до warn для неизвестных ключей верхнего уровня среды.

**Г. Отдельный файл `stand-test-ui-applications.yml`.**
Общий файл не трогается вовсе.

## Решение

Принимается **вариант А** — с явным разделением на два независимых изменения и жёстким порядком.

### Шаг 1 (не зависит от UI-работ, делается первым)

- `version` добавляется в `ROOT_KEYS`. Тип — целое, необязательное; **отсутствие означает `1`**.
- Поддерживаемая версия хранится константой в `stand-test-core` (`EnvironmentConfigFormat.SUPPORTED`),
  чтобы обе поверхности — файл и стартер — читали **одно** число.
- Поведение:

| Версия в файле | Поведение SDK |
|---|---|
| отсутствует | читается как `1`; полная обратная совместимость |
| `== SUPPORTED` | читается |
| `< SUPPORTED` | читается (старые файлы валидны) |
| `> SUPPORTED` | **отказ с сообщением о версии**: «файл реестра сред имеет версию N, эта версия SDK поддерживает до M — обновите `stand-test-*` до версии, поддерживающей формат N» |
| не целое / ≤ 0 | отказ как ошибка конфигурации |

- То же самое зеркалируется в стартере, из той же константы.

### Шаг 2 (UI-работы)

- Секция `ui-applications` внутри среды; `version: 2` объявляет её наличие.
- Модель: `UiApplicationDefinition` в `core/environment/` рядом с
  `ServiceEndpointDefinition`; `EnvironmentDefinition` получает **опциональное** поле
  `uiApplications` (пустая мапа по умолчанию — существующие конструкторы сохраняются, как это уже
  сделано для `kafkaClusters`).

```yaml
version: 2
environments:
  ift:
    ui-applications:
      client-portal:
        base-url-ref: CLIENT_PORTAL_IFT_URL    # голое имя переменной окружения
        default-viewport: desktop
        viewport-profiles:
          desktop: { width: 1440, height: 900 }
        trace: off                              # ADR-UI-005 §маскирование
        auth:                                   # Slice 3
          scheme: FORM                          # ключ `scheme`, как у сервисов (BR-37)
          credentials-pool-ref: CLIENT_PORTAL_TEST_USERS
          roles: [client, operator, no-rights]
          discovery-account-ref: CLIENT_PORTAL_DISCOVERY
```

### Соглашения об именовании (BR-37 требует следовать существующему стилю)

- схема аутентификации — `scheme`, **не** `type`;
- ссылки на секреты — суффикс `-ref`, значение — **голое имя** переменной; проходит
  `SecretReferences.requireReferenceShape(...)`, отвергающий `literal://`, резолвнутый адрес и
  инлайн-креденшел;
- kebab-case с приёмом camelCase-варианта, как у `grpc-targets`/`grpcTargets`;
- никаких абсолютных URL в файле — только `*-ref`.

## Последствия

**Положительные.**
Окно совместимости открывается **до** первой публикации, то есть бесплатно: ни у одного потребителя
нет версии SDK, которая отвергнет `version`. Одна константа поддерживаемой версии на две поверхности
сокращает известный риск дрейфа мапперов. Существующие файлы без `version` продолжают читаться без
изменений — NFR-06 в части конфигурации не затрагивается.

**Отрицательные.**
Шаг 1 — изменение `stand-test-config` и стартера, не связанное с UI, но обязательное к выпуску
раньше. Это добавляет релиз в цепочку.

Ослабляется одна грань fail-closed: неизвестный ключ **верхнего уровня** теперь может быть
легитимным (`version`). Компенсация — список остаётся явным, добавлена только одна запись.

**Нейтральные.**
Разделение на два шага делает шаг 1 полезным независимо от судьбы UI-проекта: версионирование
конфигурации нужно любому SDK, который планирует расширять формат.

## Риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Шаг 1 не успеет в релиз до UI-секции — окно закроется | **Средняя** | **Высокое** | Шаг 1 вынесен отдельной задачей S-0.2 и не зависит ни от чего в UI-работах; может быть выпущен параллельно |
| Дрейф мапперов: файл понимает версию, стартер — нет | Средняя | Высокое | Общая константа в `core`; **contract-тест, прогоняющий одну и ту же конфигурацию через обе поверхности** и сверяющий результат |
| `${VAR}` внутри UI-`*-ref` на поверхности стартера (ловушка двойного разрешения) | Средняя | Высокое | Существующее правило переносится на UI-поля: на стартере ref — **голое имя**; проверка `requireReferenceShape` + детектор гейта |
| Потребитель воспримет `version` как версию SDK | Низкая | Низкое | Формулировка сообщения называет и версию формата, и что делать |
| Секция UI попадёт в файл раньше, чем модуль научится её читать | Низкая | Низкое | Незнакомая среде секция без модуля просто не используется; вайтлист алиасов сработает только на `ui.*`-шагах |

## Отклонённые альтернативы

**Б — версия вместе с UI-секцией.** Отклонено. Ровно тот случай, от которого предостерегает Q-06:
версионирование и ломающее расширение приезжают одним релизом, и «старая версия отказывается внятно»
оказывается недостижимой — первое же столкновение даст `Unknown field 'version'`, то есть то самое
сообщение, ради ухода от которого всё затевалось. Требование было бы формально выполнено и фактически
бесполезно.

**В — ослабить fail-closed до warn.** Отклонено. Fail-closed — не побочный эффект, а свойство,
которым SDK ловит опечатки в именах алиасов и сред: `servcies:` вместо `services:` сегодня падает,
а стал бы молча пустой мапой, и тест пошёл бы на «несуществующий» стенд с внятной, но поздней
ошибкой. Обмен диагностики на удобство расширения здесь невыгоден.

**Г — отдельный файл для UI.** Отклонено. Расщепляет вайтлист на два источника, требует второго
загрузчика и второй SPI-точки, а на Spring-поверхности вообще неприменимо (там конфигурация — это
`application.yml`). Кроме того, не решает исходную проблему: сквозной сценарий «UI + Kafka + БД»
резолвит алиасы обоих типов из **одной** среды.

## Требования BRD, которые закрывает ADR

`BR-37` (версионирование файла реестра), `D-10`, `BR-27` (UI-приложение адресуется логическим
алиасом), `BR-31` (профили вьюпорта — конфигурацией), `BR-28`/`SEC-04` (secret-ref для учётных
данных), `SEC-01` (реестр как точка вайтлиста), `OQ-13`.
