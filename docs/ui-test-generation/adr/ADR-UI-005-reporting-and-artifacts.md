# ADR-UI-005: Отчётность, артефакты падения и маскирование

**Статус:** Accepted · **Дата:** 2026-08-01 · **Принят:** 2026-08-04 · **Волна:** 1

> **Принят как написан — вариант А** (`record Attachment` получает компонент `Path file` с
> инвариантом «ровно одно из `content`/`file` не null`»). Отклонённые альтернативы Б–Д остаются в
> §«Отклонённые альтернативы» как запись рассмотрения. Реализация — `UITG-S012` и задачи
> `UITG-T001`…`T003`; это правка **стока графа зависимостей**, поэтому обязателен полный регресс
> (RISK-15) и `ModuleDependencyArchTest` в том же изменении.

## Контекст

BR-21 требует прикладывать к упавшему шагу **четыре** артефакта: скриншот, трейс/видео, консоль
браузера, сетевые запросы. BR-22 требует, чтобы отчёт нёс `scenarioId`/`testRunId`/`correlationId`,
шаги и **слой отказа**. BR-35/SEC-05 требуют маскировать чувствительные зоны **по разметке, до
снятия артефакта**.

Сверка с кодом ([`00-current-state.md`](../00-current-state.md) §8, §11.4) даёт разделение:

**Достаётся бесплатно.** `StepEvent`/`ScenarioEvent` уже несут все три идентификатора; «слой» уже
переносится полем `stepType` (`ui.click` против `kafka.expect`); публикация — best-effort
side-channel (бросивший приёмник проглатывается на WARN, `Throwable`, не только `RuntimeException`);
MDC на прогон и на шаг; метка `Step [i/n] 'id' (type)` в логе и в исключении; маскирование текста на
приёмнике (`SecretMasker`).

**Не достаётся.** `Attachment` — это `record Attachment(String name, String mediaType, String
content)`, а `DefaultAllureLifecycleFacade:67` делает `content.getBytes(StandardCharsets.UTF_8)`.
Тракт вложений **текстовый целиком**. Консоль и сеть пройдут. **Скриншот (PNG), видео (WebM) и
Playwright-трейс (ZIP) — не пройдут.**

Base64 в текстовое поле не решает: `AttachmentType.extensionForMediaType()` выдаст `.bin`, и в Allure
вместо картинки окажется base64-простыня.

Это **изменение `stand-test-core`, не учтённое в §13.1 BRD** — там как правка core названа только
«компенсации не-DB шагов» (D-9).

## Рассматриваемые варианты

**А. Добавить в `Attachment` компонент `Path file`** с инвариантом «ровно одно из `content`/`file`
не null», сохранив трёхаргументный конструктор и `of(...)`.

**Б. Компонент `byte[] binaryContent`.**

**В. Отдельный record `BinaryAttachment` + второй список в `StepResult`/`StepEvent`.**

**Г. Не трогать core: класть путь к файлу в `content` как текст** с условленным media type; приёмник
читает файл.

**Д. Артефакты вообще не проходят через отчёт**: складываются в каталог прогона, в диагностику
кладутся пути.

## Решение

### 1. Модель вложения — вариант А

```java
public record Attachment(String name, String mediaType, String content, Path file) {
    // канонический конструктор: ровно одно из content/file не null
    public Attachment(String name, String mediaType, String content) { this(name, mediaType, content, null); }
    public static Attachment of(String name, String mediaType, String content);      // без изменений
    public static Attachment ofFile(String name, String mediaType, Path file);       // новое
    public boolean isBinary();
}
```

Существующие вызовы `new Attachment(a, b, c)` и `Attachment.of(...)` компилируются без правок.
`Path` (в отличие от `byte[]`) корректно ведёт себя в `equals`/`hashCode` record'а — это требование
правил репозитория об иммутабельных value-типах.

`AllureAttachmentPublisher` получает ветку: текст — существующий путь с `SecretMasker.maskText`;
файл — чтение и передача байтов в `AllureLifecycleFacade` (метод `addAttachment(name, type, ext,
Path)` добавляется рядом с существующим строковым, не заменяя его).

### 2. Четыре артефакта волны 1

| Артефакт | Представление | Media type | Когда снимается |
|---|---|---|---|
| Скриншот | `Path` (PNG) | `image/png` | только на отказе шага |
| Трейс | `Path` (ZIP) | `application/zip` | на отказе, **если разрешён** (см. п. 4) |
| Консоль браузера | `String` | `text/plain` | на отказе |
| Сетевые запросы | `String` | `text/plain` | на отказе |

**Видео в волну 1 не входит.** BR-21 формулирует требование как «трейс/видео» — дизъюнкция; трейс
информативнее для отладки (DOM-снимки, действия, сеть в одном файле), а видео удваивает объём
хранения (SEC-09, NFR-09) и несёт тот же риск ПД без возможности постобработки.

**На зелёном прогоне артефакты не снимаются.** Скриншот успешного шага не имеет сценария
использования в волне 1 (визуальные регрессы — волна 3), но стоит места (SEC-09) и времени (NFR-03).

### 3. Слой отказа

Отдельного поля не заводится — **оно уже есть**: `stepType`. Дополнительно executor кладёт в
`StepResult.diagnostics`:

| Ключ | Назначение |
|---|---|
| `ui.application` | алиас приложения |
| `ui.url` | текущий URL (внутри origin алиаса) |
| `ui.locator` / `ui.locator.strategy` | описание локатора; стратегия — вход в KPI-9 |
| `ui.element.present` / `.visible` / `.enabled` | снимок на момент отказа: отвечает «кнопки не было» против «кнопка была, но неактивна» |

Это ровно то, что делает `RestStepExecutor`, кладя в диагностику метод, URL и статус.

### 4. Маскирование — и честное ограничение волны 1

Маскирование выполняется **в DOM, до снятия любого артефакта**. Иначе нельзя: `SecretMasker`
работает по тексту и растр замаскировать не может, а OCR вынесен из области (§6.2 BRD).

Источник разметки — флаг `sensitive` на `UiLocator` в Page Object (волна 1); позже — запись экрана в
KB (BR-08).

Порядок на отказе: заменить значения помеченных элементов в DOM → снять скриншот **дополнительно с
`mask`-опцией Playwright** (защита в глубину) → снять текстовые логи → пропустить их через
существующий `SecretMasker`.

> **Ограничение по трейсу.** Playwright-трейс содержит DOM-снимки за весь прогон, **включая моменты
> до маскирования**. Постобработки трейса в волне 1 нет. Поэтому: **трейс снимается только если у
> приложения не объявлено ни одной чувствительной зоны.** Если зоны объявлены — трейс отключается,
> и падение сопровождается замаскированным скриншотом, консолью и сетью. Управляется полем
> приложения в реестре; **умолчание — безопасное (`trace: off`)**.

Это сознательное ограничение, а не недосмотр. Альтернативы: утечка ПД в трейс (RISK-05: «любой
подтверждённый случай → остановка прогонов до исправления») либо задержка волны 1 на разработку
постобработки. Компенсирующий контроль — SEC-09. Снятие ограничения — волна 2.

## Последствия

**Положительные.**
BR-21 закрывается целиком для трёх артефактов из четырёх и для четвёртого — под явным условием.
Изменение `Attachment` аддитивно и полезно за пределами UI: любой будущий адаптер с бинарными
данными получает канал. Слой отказа не требует ни строки нового кода.

**Отрицательные.**
Правка `stand-test-core` в общей модели событий — **самое рискованное изменение волны 1** после
`Attachment` ничего сопоставимого не остаётся. Требует полного регресса `stand-test-allure`
(57 тестов) и всего набора (1203).

Файловое вложение вводит зависимость от файловой системы в контракт отчётности: файл обязан
существовать в момент публикации. Публикация синхронна внутри `run()`, поэтому в волне 1 это
безопасно, но становится ограничением для будущих асинхронных приёмников — фиксируется в Javadoc.

Условный трейс означает, что для приложений с ПД отладка беднее. Это осознанный обмен в пользу
SEC-05.

**Нейтральные.**
`SecretMasker` остаётся в `stand-test-allure`. UI-модулю он недоступен без дублирования или
переноса — в волне 1 UI-модуль маскирует **в DOM**, а текстовые логи маскирует приёмник, как и
сегодня. Перенос `SecretMasker` в core не требуется.

## Риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Изменение record `Attachment` сломает потребителя, использующего деконструкцию в pattern matching | Низкая | Среднее | `--release 17` запрещает record-patterns в исходниках SDK; у внешних потребителей проверяется полным регрессом и отмечается в release notes |
| ПД утечёт через трейс | Средняя | **Высокое** (RISK-05) | Умолчание `trace: off`; трейс запрещён при объявленных `sensitive`-зонах; SEC-09 |
| ПД утечёт через скриншот из-за незамеченной зоны | Средняя | Высокое | Двойное маскирование (DOM + `mask`); детектор гейта «поле пароля без `sensitive()`»; component-тест на отсутствие значения на PNG |
| Артефакты переполнят хранилище CI | Средняя | Среднее | Снятие только на отказе; видео исключено; SEC-09; KPI-8 |
| Файл артефакта удалён к моменту публикации | Низкая | Низкое | Каталог прогона живёт до конца JVM; публикация синхронна; приёмник при отсутствии файла логирует WARN и не падает (best-effort уже так устроен) |

## Отклонённые альтернативы

**Б — `byte[] binaryContent`.** Отклонено. Массив в record ломает `equals`/`hashCode` (сравнение по
ссылке) — прямое нарушение правил репозитория об иммутабельных value-типах с корректной семантикой
равенства. Кроме того, держит скриншот и трейс в куче: трейс — это мегабайты, и при параллельном
прогоне они складываются.

**В — отдельный `BinaryAttachment` и второй список.** Отклонено. Удваивает поверхность
`StepResult`/`StepEvent`, требует правки каждого приёмника и каждого места, где события
конструируются, и заставляет потребителя обрабатывать два списка вместо одного. Больше изменений в
core, чем вариант А, ради меньшей выразительности.

**Г — путь в поле `content` как текст.** Отклонено. Скрытый контракт: поле называется «содержимое»,
а содержит путь; отличить настоящий текст от пути можно только по media type. Существующий
`SecretMasker.maskText` при этом применится к **пути**, а не к содержимому — маскирование станет
бессмысленным и незаметно бессмысленным. Экономия одной правки core не стоит контракта, о котором
надо помнить.

**Д — артефакты только в диагностике, вне отчёта.** Отклонено как постоянное решение, **принято как
временное для Slice 1**: пока правка `Attachment` не выпущена, spike кладёт пути в
`StepResult.diagnostics`. Это позволяет вести Slice 1 параллельно с работой над core, но не
удовлетворяет BR-21 («все четыре приложены к упавшему шагу»).

## Требования BRD, которые закрывает ADR

`BR-21` (артефакты падения), `BR-22`/`D-7` (идентификаторы и слой отказа), `BR-35` (разметка
чувствительных зон), `SEC-05` (маскирование по разметке до снятия), `SEC-09` (срок жизни артефактов
— как компенсирующий контроль), `NFR-08` (наблюдаемость), `NFR-09` (ресурсоёмкость — артефакты
только на отказе).
