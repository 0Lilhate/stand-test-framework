# ADR-UI-007: Компенсации не-DB шагов и откат данных, созданных через UI

**Статус:** Proposed · **Дата:** 2026-08-01 · **Волна:** 1 (частично), волна 2 (остаток)

## Контекст

D-9 в BRD утверждает: «Откат данных, созданных через UI, **требует доработки `stand-test-core`**:
компенсации не-DB шагов». §13.1 выделяет на это отдельную строку сметы, RISK-15 объявляет риск
дестабилизации существующих тестов, BR-24 требует политику `ALWAYS` и очистку на зелёном прогоне
тоже.

Сверка с кодом ([`01-brd-traceability.md`](../01-brd-traceability.md), D-9) показала, что
**утверждение верно только для одной из двух трактовок**, и BRD их смешивает.

**(а) Компенсатор, регистрируемый адаптером.**

```java
// stand-test-core/.../compensation/Compensator.java — целиком
public interface Compensator {
    String actionId();
    String target();
    CompensationOutcome compensate();
}
```

Ничего DB-специфичного. `UndoLog` — тоже: `register`, `isEmpty`, `size`, `inReverseOrder`.
`StepExecutionContext.undoLog()` доступен **любому** executor'у. `CleanupPolicy.ALWAYS` реализована
и работает (`shouldCompensate(runFailed)`). `drainCompensations()` в `finally` раннера обходит
`UndoLog` в обратном порядке, best-effort по каждому действию, с защитным `catch (Throwable)`.

То, что регистрирует компенсаторы ровно одно место — `DbStepExecutor:191` (проверено поиском по всем
`src/main`), — **факт употребления, а не ограничение модели**. **Правки core для (а) не требуется
вовсе.**

**(б) Сценарный компенсирующий шаг** — `Scenario.builder(...).cleanup(RestStep.post(...))` из
Приложения А. **Действительно отсутствует**: в `Scenario` нет поля, в билдере нет метода,
`drainCompensations()` обходит только `UndoLog`. Само Приложение А помечает это как «не существует».

**Третий факт, который связывает всё вместе.** ADR-UI-001 запрещает `stand-test-ui` зависеть на
другие адаптеры (ArchUnit-правило `adaptersDoNotDependOnEachOther`). Значит компенсация вида
«отозвать заявку REST-вызовом» **внутри UI-модуля невыразима** — не из-за отсутствия механизма, а
из-за границы модулей.

Внешний вход: **Q-12 / OQ-06 / AS-05** — способ удаления данных, созданных через UI, свой у каждого
приложения и подтверждается владельцами.

## Рассматриваемые варианты

**А. Волна 1 = только (а).** UI-адаптер регистрирует `UiCompensator`, компенсирующий **средствами
UI** (отзыв заявки через сам интерфейс). Core не трогается. (б) — волна 2.

**Б. Волна 1 = (а) + (б).** Сразу вводятся сценарные cleanup-шаги.

**В. Только (б).** Компенсация всегда объявляется шагом; адаптеры компенсаторов не регистрируют.

**Г. UI-модуль получает узкий HTTP-клиент для компенсаций** (без зависимости на `stand-test-rest`).

**Д. Компенсация не автоматизируется в волне 1** — данные вычищаются внешним заданием по
`testRunId`.

## Решение

Принимается **вариант А**.

### Волна 1

1. `UiStepExecutor` регистрирует `UiCompensator` в `context.undoLog()` в момент создания сущности.
   Что считать «созданием» — определяет автор шага: вводится необязательный маркер на шаге,
   объявляющий компенсирующее действие в терминах UI.
2. Компенсация исполняется **средствами того же UI**: открыть страницу сущности по захваченному
   идентификатору, нажать «Отозвать», дождаться подтверждения. Тем же `UiDriver`, в **той же**
   сессии — она ещё жива, потому что `drainCompensations()` выполняется **до** `closeQuietly`
   (порядок в `finally` прокомментирован в раннере как нагруженный смыслом, и это ровно тот случай,
   ради которого он такой).
3. Политика — существующая. Сценарий объявляет `.cleanupPolicy(CleanupPolicy.ALWAYS)`; ничего нового
   не требуется.
4. Идентификация созданного — по **захваченному с экрана значению** (`${applicationNumber}`), а где
   у формы есть поле для метки — дополнительно по `testRunId`, как это уже делает db-адаптер
   (`taggedByTestRunId`/`whereTestRunId`).
5. `CompensationOutcome` возвращается по существующему контракту: `APPLIED` / `SKIPPED` (нечего
   компенсировать) / `CONFLICT` (сущность изменена кем-то ещё) / `FAILED`. `target()` — алиас
   приложения. Отчёт получает событие с типом шага компенсации.
6. **Изменений в `stand-test-core` — ноль.**

### Волна 2

Сценарные cleanup-шаги (б) — отдельным ADR и отдельной задачей, вместе с решением по компенсации
чужим протоколом. Тогда же снимается ограничение «UI компенсирует только средствами UI».

### Явное следствие, которое нельзя замалчивать

Вариант А работает **только для приложений, где созданную сущность можно отозвать через интерфейс**.
Если у приложения волны такой возможности нет (Q-12), BR-24 для него в волне 1 **не закрывается**, и
это должно быть записано в отчёт о готовности приложения, а не обойдено расширением скоупа задним
числом.

## Последствия

**Положительные.**
`stand-test-core` в волне 1 не меняется по этой линии вовсе — **RISK-15 из плана волны 1 уходит**, а
строка «Доработка `stand-test-core`: компенсации не-DB шагов» из §13.1 BRD переносится в волну 2.
Оценка §13.1 подлежит корректировке (см. оговорку ниже). Компенсация средствами UI попутно
**проверяет сам интерфейс отзыва** — то есть покрывает сценарий, который иначе остался бы
непротестированным.

Дренаж уже best-effort по каждому действию: новый источник компенсаторов не меняет поведения
существующих DB-компенсаций, и они дренируются вместе, в общем обратном порядке.

**Отрицательные.**
Компенсация через UI **медленная** (страница, клик, ожидание) и **хрупкая** — она наследует все
риски UI-теста, включая дрейф локаторов (RISK-02). Упавшая компенсация на зелёном прогоне валит тест
(так устроен раннер: `primary == null` → `throw cleanupFailure`), то есть хрупкость компенсации
превращается во flaky самого теста. Это реальная цена, и она должна попасть в замер NFR-01.

Ограничение «только средствами UI» сузит применимость: часть приложений закроется только в волне 2.

**Оговорка о смете.** Уход этой строки из волны 1 **не означает, что правок core стало меньше**.
[`10-target-architecture.md`](../10-target-architecture.md) §15 перечисляет пять других:
ветка `ui.` в валидаторе, константы `StepParameterKeys`, `UiApplicationDefinition` в
`EnvironmentDefinition`, ключ `version` в загрузчике и — самая существенная — `Attachment`
(ADR-UI-005). Суммарный объём вмешательства в core сопоставим с исходной оценкой; изменились статьи,
а не порядок величины.

**Нейтральные.**
Интерфейс `Compensator` остаётся неизменным. Второй адаптер, которому понадобится компенсация,
воспользуется тем же механизмом.

## Риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| У приложений волны нет UI-способа отозвать созданное (Q-12) | **Средняя** | **Высокое** | Ответ на Q-12 нужен до Slice 5; при отрицательном — BR-24 для приложения переносится в волну 2 и это фиксируется, а не обходится |
| Хрупкая компенсация валит зелёные прогоны | Средняя | Среднее | Отказ компенсации отделён в отчёте (`CompensationOutcome`, отдельный тип события); NFR-01 учитывает его отдельным счётчиком; при систематических отказах — `CONFLICT`/`SKIPPED` вместо `FAILED` |
| Компенсация выполняется после того, как сессия испортилась падением | Средняя | Среднее | Компенсатор проверяет живость сессии; при непригодности — `FAILED` с внятной причиной, а не исключение (контракт: компенсатор не бросает) |
| Медленная компенсация выводит сценарий за NFR-03 | Средняя | Низкое | Бюджет компенсации измеряется отдельно от бюджета сценария; NFR-03 нормирует прогон, а не уборку |
| Соблазн «временно» сделать HTTP-вызов из UI-модуля | Средняя | Высокое | ArchUnit-правило `uiDoesNotDependOnOtherAdapters` + отсутствие HTTP-клиента в зависимостях модуля |
| Правка core «просочится» позже под видом мелочи | Низкая | Среднее | Состав полей `Scenario` зафиксирован тестом `scenarioHasNoUiFields` (ADR-UI-001) — добавление `cleanup` сломает его осознанно |

## Отклонённые альтернативы

**Б — (а) + (б) в волне 1.** Отклонено. Вносит в самую нагруженную волну изменение `Scenario`,
билдера и раннера, то есть RISK-15 («любая регрессия существующих тестов — блокирующий дефект,
работа откатывается») — там, где без него можно обойтись. Ценность (б) реальна, но она про
**кросс-протокольную** компенсацию, а не про UI как таковой, и потому естественно живёт в волне 2
вместе со сквозными сценариями.

**В — только (б).** Отклонено. Требует правки core прямо сейчас и вдобавок отменяет работающий
механизм db-компенсаций, которым уже покрыты тесты (`DbWriteUndoTest`). Хуже по обоим измерениям.

**Г — узкий HTTP-клиент внутри UI-модуля.** Отклонено, и это стоит назвать прямо: технически это
обошло бы ArchUnit-правило (правило запрещает зависеть на **модуль** `stand-test-rest`, а не на
`java.net.http`), но нарушило бы его смысл. Появился бы второй, неподконтрольный путь исходящих
HTTP-вызовов, мимо `EnvironmentRegistry`, мимо вайтлиста алиасов, мимо инъекции `correlationId` и
мимо auth-резолвера — то есть мимо всех guardrails, ради которых REST-адаптер и существует. Это
прямой путь к нарушению SEC-01. Правильный ответ на ту же потребность — (б) в волне 2.

**Д — внешняя уборка по `testRunId`.** Отклонено как замена, **принято как страховка**. BR-24
требует, чтобы «повторный прогон не накапливал данные», и внешнее задание этого формально достигает,
но: способ очистки не указан в отчёте (критерий приёмки BR-24), очистка не привязана к прогону, а
данные живут между уборками. Как второй контур для случаев `FAILED`-компенсаций — полезно, и это
стоит предусмотреть эксплуатационно.

## Требования BRD, которые закрывает ADR

`BR-24` (идентификация и вычистка данных UI, политика `ALWAYS`) — **частично**: для приложений с
UI-способом отзыва. `D-9` — с уточнением трактовки. `SEC-03` (только тестовые данные, созданное
вычищается). `NFR-06` (существующие тесты не меняют поведения — здесь достигается тем, что core не
трогается). `RISK-15` — снимается с волны 1. `AS-05`, `OQ-06` — внешний вход.

**Не закрывает:** кросс-протокольную компенсацию (волна 2) и приложения без UI-способа удаления.

## Тесты архитектурного решения

| Тест | Уровень | Что доказывает |
|---|---|---|
| `uiCompensatorIsRegisteredOnEntityCreation` | unit (фейковый драйвер) | После шага создания `UndoLog.size() == 1` |
| `uiAndDbCompensatorsDrainInReverseOrderTogether` | unit | Общий обратный порядок; смешанный сценарий |
| `compensationRunsOnGreenRunWithAlwaysPolicy` | unit | `CleanupPolicy.ALWAYS` — существующий механизм работает для UI |
| `compensationSkippedOnGreenRunWithDefaultPolicy` | unit | Дефолт `ON_FAILURE` не изменён |
| `oneFailingCompensatorDoesNotAbortTheRest` | unit | Best-effort по каждому действию сохранён |
| `compensatorNeverThrows` | unit | Контракт: ошибка сворачивается в `FAILED`-исход |
| `compensationRunsBeforeSessionIsClosed` | unit | Порядок `drain → closeQuietly` — сессия жива на момент компенсации |
| `compensationFailureOnGreenRunFailsTheTest` | unit | Существующая семантика раннера не изменена |
| `compensationOutcomeAppearsInReport` | integration | Способ очистки виден в отчёте (критерий BR-24) |
| **`uiModuleHasNoHttpClientDependency`** | arch | Ни `stand-test-rest`, ни `java.net.http`, ни иной HTTP-клиент в `stand-test-ui` |
| `scenarioHasNoCleanupField` | arch | Пока (б) не принята — `Scenario` не обзавёлся полем cleanup |
| `existingDbCompensationTestsUnchanged` | `stand-test-db` | `DbWriteUndoTest` и прочие зелёные |
