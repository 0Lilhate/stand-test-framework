# ADR-UI-001: Границы модуля `stand-test-ui` и защита `stand-test-core` от Playwright

**Статус:** Accepted · **Дата:** 2026-08-01 · **Реализован:** 2026-08-02 (минимальный вертикальный срез) · **Волна:** 1

## Контекст

BRD требует UI как **тип шага в существующей модели сценария**, а не как отдельный UI-фреймворк
(§1, D-1). Ограничение зафиксировано в NFR-05: «`stand-test-core` не получает зависимостей от
Playwright и любого IO; модель сценария не получает UI-специфичных полей; **проверяется тестом графа
зависимостей в сборке**». RISK-09 объявляет любое нарушение блокирующим дефектом сборки.

Сверка с кодом ([`00-current-state.md`](../00-current-state.md) §2, §6.3) дала два факта, которые
меняют постановку задачи:

1. **Механизм расширения полностью готов.** `StepExecutor` диспетчеризуется по строке
   `ScenarioStep.type()`; `GenericStep` несёт произвольную `Map<String,Object>`; регистрация — через
   `ServiceLoader`. Core не получает ни compile-ребра, ни знания о браузере. Так живут четыре
   существующих адаптера.
2. **Обещание NFR-05 сегодня не подкреплено.** `ModuleDependencyArchTest` проверяет **только рёбра
   между модулями SDK**: core как сток, адаптеры не зависят друг на друга, спутники core-only,
   starter — лист. Правила «core зависит только на JDK + `slf4j-api`» **не существует**; правила «в
   `Scenario` нет UI-полей» — тоже. Строка `implementation(libs.playwright)` в
   `stand-test-core/build.gradle.kts` прошла бы сборку и все 1203 существующих теста.

То есть главный риск этого ADR — не «как встроить UI», а «как не дать инварианту протечь молча».

## Рассматриваемые варианты

**А. Новый модуль-адаптер `stand-test-ui` → `core` + `await`; правила графа заводятся заранее.**
Полная симметрия с rest/kafka/db/grpc. Playwright — `implementation` только в новом модуле.

**Б. Тот же модуль, но правила графа заводятся вместе с модулем или после.**
Экономит одну задачу в начале. Ценой того, что первое нарушение будет поймано ревью, а не сборкой.

**В. UI внутри `stand-test-core` за интерфейсом с рефлексивной загрузкой.**
Формально «core не зависит на Playwright» — зависимость только рантайм-рефлексивная.

**Г. Отдельный репозиторий / отдельный артефакт вне графа SDK.**
Максимальная изоляция core.

**Д. Расширение `stand-test-rest` (там уже есть HTTP-семантика и резолв алиасов).**
Переиспользование `BaseUrlResolver` и auth-резолвера.

## Решение

Принимается **вариант А**.

1. Новый модуль `stand-test-ui`, пакет `ru.alfa.stand.test.ui`, координаты
   `ru.alfa.stand.test:stand-test-ui`. Зависимости: `api(core)`, `implementation(await)`,
   `implementation(playwright)`, `implementation(slf4j-api)` — форма один в один как у
   `stand-test-rest`.
2. Playwright физически заперт в подпакете `ru.alfa.stand.test.ui.playwright`; ни один тип вне его
   не импортирует `com.microsoft.playwright.**`.
3. **Три ArchUnit-правила заводятся ДО первой строки модуля** (это отдельная задача бэклога,
   S-0.1, и она первая):
   - `coreHasNoUiOrIoDependencies` — `stand-test-core` не зависит ни на что, кроме JDK и `slf4j-api`;
   - `scenarioHasNoUiFields` — состав полей `Scenario` зафиксирован явным списком;
   - `playwrightIsConfinedToDriverPackage`.
   Плюс расширение существующих `adaptersDoNotDependOnEachOther` и `nothingDependsOnTheStarter` на
   новый модуль.
4. Правки `stand-test-core`, которые этот ADR **разрешает** (они не являются зависимостью и не
   являются IO): ветка `ui.` в `DefaultScenarioValidator.checkAliasWhitelist()`, константы
   `UI_PREFIX`/`APPLICATION` в `StepParameterKeys`, опциональное поле `uiApplications` в
   `EnvironmentDefinition`, константы `ForbiddenOperation`. Правка `Attachment` рассматривается
   отдельно (ADR-UI-005).
5. Правки `stand-test-core`, которые этот ADR **запрещает**: любая новая внешняя зависимость;
   поля `viewport`/`browser`/`baseUrl`/`headless`/`locale` в `Scenario`; типы `UiStep`/`UiLocator` в
   core; компонент `BrowserContext` в `StepExecutionContext`; методы вида `locator()` в
   `ScenarioStep`.

## Последствия

**Положительные.**
Модуль встаёт пятым адаптером без единого изменения в раннере, JUnit-расширении и SPI. Потребитель,
не подключивший `stand-test-ui`, не получает Playwright даже транзитивно. Автор теста видит UI-шаг
как обычный шаг SDK. Три новых правила графа полезны сами по себе, независимо от исхода проекта: они
закрывают дыру, существующую сегодня.

**Отрицательные.**
Пять правок `stand-test-core` вместо одной, названной в §13.1 BRD (там как единственная указана
«компенсации не-DB шагов» — а её волна 1, по ADR-UI-007, не делает). Оценка §13.1 подлежит
пересмотру: статьи другие, суммарный объём вмешательства в core сопоставим.

Запрет «UI-модуль не зависит на другие адаптеры» означает, что компенсация UI-данных чужим
протоколом (REST-вызов отзыва) внутри модуля невыразима — это прямо ведёт к ADR-UI-007.

**Нейтральные.**
`stand-test-junit` не получает ребра на `stand-test-ui`: SPI-регистрации достаточно. Starter
подключает модуль как `compileOnly optional` — шестым в существующем списке.

## Риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Правило `coreHasNoUiOrIoDependencies` окажется слишком строгим и начнёт падать на легитимном изменении | Низкая | Низкое | Правило перечисляет разрешённое явным списком; расширение списка — осознанное действие с ревью |

## Отклонённые альтернативы

**Б — правила графа после модуля.** Отклонено. RISK-09 обещает блокирующий дефект сборки; правило,
заведённое после нарушения, ловит его на ревью. Стоимость правил — часы, стоимость протёкшей
зависимости — релиз SDK с Playwright у всех потребителей протокольных тестов.

**В — UI в core за рефлексией.** Отклонено. Формально проходит проверку графа и полностью
нарушает её смысл: core перестаёт быть JDK-only по существу, а рефлексивная загрузка ломает
диагностику и превращает ошибку компиляции в `ClassNotFoundException` в рантайме. Это тот же приём,
которым обходят архитектурные правила, а не соблюдают их.

**Г — отдельный репозиторий.** Отклонено. Убивает главную заявленную ценность (§1 BRD): сквозной
сценарий «UI + Kafka + БД» требует общей модели сценария и общего `VariableStore`. Отдельный артефакт
вне графа не может быть шагом того же `Scenario`. Плюс дублирование релизного цикла, BOM и кита.

**Д — расширение `stand-test-rest`.** Отклонено дважды. Во-первых, `stand-test-rest` попал бы под
Playwright, и каждый REST-тест потянул бы браузер. Во-вторых, переиспользование там мнимое: `HttpCaller`
исполняет запрос без DOM, `BaseUrlResolver` — тривиальная лямбда `String → String`, а auth-резолвер
возвращает HTTP-заголовок, тогда как UI-вход — это форма или IdP-редирект (ADR-UI-006). Общего кода
меньше, чем цены связывания.

## Требования BRD, которые закрывает ADR

`D-1` (модуль SDK + расширение кита), `D-2` (место для Playwright), `NFR-05` (изоляция архитектуры,
проверяемая тестом графа), `NFR-06` (подключение не ломает существующие тесты), `BR-31` (браузер и
вьюпорт вне `Scenario`), `RISK-09`.

## Статус реализации (сверка с кодом, 2026-08-02)

Контекст ADR писался до коммитов `94666b6`/`46d3cfb` и в двух местах разошёлся с кодом. Сверка:

| Пункт решения | Состояние | Комментарий |
|---|---|---|
| Модуль `stand-test-ui`, форма зависимостей как у `rest` | **сделано** | `api(core)` + `implementation(await, playwright, slf4j-api)` |
| Playwright заперт в `…ui.playwright` | **сделано** | Правило ArchUnit + отдельная проверка непустоты (§ниже) |
| Три правила графа **до** модуля (S-0.1) | **сделано, но после модуля** | Правила заведены в том же изменении, что и модуль, а не раньше. Каждое проверено падающим на искусственном нарушении (поле в `Scenario`, импорт Playwright в `…ui.UiSession`, сужение allow-list ядра) — то есть обещание RISK-09 подкреплено; изменился порядок, не результат |
| Ветка `ui.` в `checkAliasWhitelist`, `UI_PREFIX`/`APPLICATION`, `uiApplications` в `EnvironmentDefinition` | **уже было** | Приехало раньше UI-модуля (`46d3cfb`); ADR описывал это как предстоящее |
| Starter подключает модуль `compileOnly optional` | **не сделано** | Вне минимального среза: SPI-пути `ServiceLoader` достаточно для plain-JUnit. Проводка стартера — отдельная задача |
| Constraint в `stand-test-bom` | **сделано** | |

**Расширение списка разрешённых правок ядра.** §4 называл две константы (`UI_PREFIX`, `APPLICATION`).
Реализация добавила в `StepParameterKeys` ещё семь: `LOCATOR`, `STRATEGY`, `ACCESSIBLE_NAME`, `VALUE`,
`PROPERTY`, `ATTRIBUTE`, `SOURCE`. Причина — действующее соглашение репозитория, проверяемое тестом
`stepParameterKeysAreMirrored`: **каждый** wire-ключ адаптера ссылается на константу ядра
(так устроены `RestStepParameters`, `DbStepParameters`, `GrpcStepParameters` — включая вложенные ключи
вроде `COLUMN` и `JSON_PATH`). Ключи, объявленные локально в адаптере, выпадают из проверок валидатора,
которые работают по имени ключа, — ровно тот дефект, ради предотвращения которого зеркалирование и
введено. Это по-прежнему константы: ни зависимости, ни IO, ни UI-семантики в ядро не добавлено.
