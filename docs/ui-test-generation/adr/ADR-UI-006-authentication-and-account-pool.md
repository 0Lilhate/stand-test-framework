# ADR-UI-006: Аутентификация, сессии и пул технических учёток

**Статус:** Accepted, реализовано · **Дата:** 2026-08-01 · **Реализовано:** 2026-08-02 · **Волна:** 1 (Slice 3–4)

> **Что фактически в коде.** `ui.login` (`UiStep.login(...).role(...)`), `AccountPool` /
> `LeasedAccount` / `InProcessAccountPool`, реестр учёток `AccountRoster`, `StorageStateStore`,
> `UiLoginService`, точка расширения `UiLoginChallengeHandler`; в реестре — `UiLoginFormConfig` и
> `UiLoginChallenge`; в валидаторе — `UI_LOGIN_ROLE_REQUIRED` / `UI_LOGIN_ROLE_UNKNOWN`. Контракт и
> отличия от этого документа — в разделе [«Реализация»](#реализация) ниже и в
> [`stand-test-ui/README.md`](../../../stand-test-ui/README.md).

## Контекст

§13.1 BRD называет аутентификацию **самой рискованной частью волны 1**. Требования:

- **BR-28** — вход логин/паролем техучётки через secret-ref, учётных данных нет в git;
- **BR-29** — вход через корпоративный IdP с переиспользованием сессии; **`storageState` привязан к
  учётной записи, а не к набору** — иначе переиспользование противоречит изоляции параллельных
  прогонов;
- **BR-30** — документированная стратегия MFA/OTP/КАПЧА; при отсутствии байпаса сценарий помечается
  неавтоматизируемым;
- **BR-34** — пул техучёток с выдачей **по ролям**, размер ≥ целевой параллельности; при исчерпании
  пула — ожидание **в пределах ограниченного таймаута** и падение как инфраструктурный отказ;
  бесконечное ожидание запрещено наравне с прочими (BR-23);
- **SEC-10** — разведка под учёткой без прав на необратимые операции.

Сверка с кодом ([`01-brd-traceability.md`](../01-brd-traceability.md), BR-28/29/34):

- `AuthScheme` содержит **ровно два значения** — `BASIC`, `BEARER`. Ни `FORM`, ни `SSO`, ни
  `STORAGE_STATE`;
- `AuthConfig(scheme, usernameRef, passwordRef, tokenRef)` — **одна** учётка на сервис, без ролей и
  без пула;
- понятия сессии в SDK нет;
- `SecretReferences.requireReferenceShape(...)` рассчитан на **одиночное** значение;
- рабочий прецедент «учётка из реестра → инъекция на исполнении» есть: `AuthConfig` +
  `EnvironmentAuthHeaderResolver` в `stand-test-rest`;
- механизм ресурса на прогон с гарантированным освобождением есть: `ResourceScope`
  (`register`/`closeAll` в `finally`).

Внешние блокеры: **G-1** (байпас MFA — OQ-01) и **G-5** (выделение пула и учётки разведки — OQ-12).
Ни один не закрывается кодом.

## Рассматриваемые варианты

**По схемам входа**

**А1. Только `FORM` в волне 1; `SSO` и `STORAGE_STATE` — следующим шагом.**
**А2. Все три схемы сразу.**
**А3. Только `STORAGE_STATE`:** сессию готовит внешний процесс, SDK её лишь загружает.

**По пулу учёток**

**Б1. Пул внутри `stand-test-ui`, in-process, на JVM.**
**Б2. Пул в `stand-test-core` как общий механизм для любых адаптеров.**
**Б3. Внешний брокер учёток (сервис), SDK — клиент.**
**Б4. Без пула: одна учётка на приложение, параллельность отключена.**

## Решение

### 1. Схемы входа — А1, с местом под остальные

`AuthScheme` **не расширяется** (он про HTTP-заголовок сервиса и используется REST-адаптером).
Вводится отдельный `UiAuthScheme` в `core/environment/` рядом с `UiApplicationDefinition`:

| Схема | Волна | Что делает |
|---|---|---|
| `NONE` | 1 | Приложение без входа (используется в component-тестах и на витрине) |
| `FORM` | 1 (Slice 3) | Заполнение формы логина по локаторам, объявленным в реестре приложения |
| `STORAGE_STATE` | 1 (Slice 3) | Загрузка заранее подготовленного состояния сессии из файла по `*-ref` |
| `SSO` | **2** | IdP-редирект; форма фиксируется в модели, реализация — после G-1 |

`SSO` присутствует в enum, но отвергается executor'ом с внятным «не реализовано в этой версии» —
это лучше, чем отсутствие значения: реестр можно писать заранее, и отказ будет говорящим.

**`STORAGE_STATE` в волне 1 — ключевое решение.** Оно даёт обходной путь для приложений, где вход
недоступен автоматизации (MFA, КАПЧА): сессия готовится человеком или внешним процессом один раз,
SDK её только использует. Это техническая опора для BR-30 «при отсутствии байпаса… альтернатива
(заранее выданная сессия)» и **снимает G-1 с критического пути разработки**, оставляя его на
критическом пути эксплуатации.

### 2. `ui.login` — отдельный тип шага

Вход — **шаг**, а не неявное действие сессии. Причины: он попадает в отчёт со своим номером и своим
слоем (`Step [1/6] 'login' (ui.login)`); его отказ классифицируется отдельно; его длительность
измеряется отдельно (NFR-02/NFR-03).

```java
UiStep.login("client-portal").id("login").role("client").build();   // → ui.login
```

`role(...)` обязателен, когда у приложения объявлен пул: **«любая учётка» невыразима**. Это прямое
требование BR-34 — иначе предусловия кейсов и негативные проверки прав (BR-12) не выражаются.

### 3. Пул учёток — Б1 за интерфейсом

```java
public interface AccountPool {
    /** Ожидание строго ограничено; исчерпание → StandTestException (BROKEN). */
    LeasedAccount lease(String application, String role, Duration timeout);
}

public interface LeasedAccount extends AutoCloseable {
    String usernameRef();
    String passwordRef();
    String role();
    /** Путь к storageState этой учётки; общий для всех тестов, получивших её. */
    Optional<Path> storageState();
    @Override void close();     // возврат в пул
}
```

- Реализация волны 1 — in-process, поверх `Semaphore`/`BlockingQueue` **на роль**.
- `LeasedAccount` регистрируется в **`ResourceScope`** — возврат в пул происходит в `finally`
  раннера, то есть и на упавшем прогоне. Это тот же механизм, что закрывает `BrowserContext`.
- **Таймаут ожидания обязателен и ограничен.** Умолчание — 60 с, верхняя граница — общая
  `MAX_TIMEOUT_MILLIS` (1 ч). Исчерпание → `StandTestException` (`BROKEN`) с сообщением, называющим
  приложение, роль, размер пула и таймаут. Бесконечное ожидание запрещено наравне с прочими (BR-23).
- Интерфейс публичный: он же — шов для unit-тестов (фейковый пул из двух учёток) и точка подключения
  внешнего брокера (Б3) в будущем.

### 4. Привязка `storageState` к учётке, а не к набору (BR-29)

Состояние сессии хранится **по ключу учётки**, а не глобально:

```
<artifacts.dir>/storage-state/<application>/<accountId>.json
```

`LeasedAccount.storageState()` отдаёт путь для **выданной** учётки. `BrowserContext` создаётся с
этим состоянием. Тест, получивший другую учётку, получает другой файл. Два параллельных прогона с
разными учётками сессий друг друга не видят — это проверяется тестом.

Файл `storageState` содержит куки — то есть **фактически секрет**. Он никогда не прикладывается к
отчёту, не логируется и живёт в каталоге артефактов под контролем SEC-09.

### 5. Секреты — существующая модель без исключений

Все ссылки в секции `auth` — `*-ref`, голое имя переменной, проходит
`SecretReferences.requireReferenceShape(...)`. Пул — новая форма (список), поэтому ссылка
`credentials-pool-ref` указывает на переменную, содержащую **имена** учёток или префикс, из которого
складываются имена; сами логины и пароли остаются в переменных окружения и никогда не появляются в
файле реестра. Точная форма — деталь реализации Slice 4; инвариант — **в конфигурации нет значений
секретов**.

> **Ревизия 2026-08-10: инвариант ослаблен решением владельца линии — версия формата 4.**
>
> Добавлена пара `auth.credentials-username` / `auth.credentials-password`: приложение с **одной**
> технической учёткой называет её прямо, вместо реестра из нескольких. Пара взаимоисключающа с
> `credentials-pool-ref` и покрывает все объявленные `roles`.
>
> **Что осталось верным.** Оба поля — по-прежнему ссылки: голое слово это имя переменной окружения,
> и `requireReferenceShape` применяется к ним так же, как ко всем остальным. Конфигурация,
> написанная голыми именами, секрета не содержит.
>
> **Что перестало быть верным, и это надо назвать прямо.** Спеллинг `${VAR:значение}` даёт **дефолт
> как значение**, а не как имя запасной переменной, — то есть учётные данные впервые стали выразимы
> в файле реестра. Формулировка «в конфигурации нет значений секретов» больше не является свойством
> конструкции; она остаётся **правилом**, которое держится документацией, ровно как у
> `password-ref` датасорса («never give a default to a password ref»).
>
> Цена принята сознательно: ради простоты записи для приложения с одной учёткой. Механизм ничего не
> обязывает — секрет попадает в файл только если его туда написать; но раньше написать было **негде**,
> а теперь есть куда, и это разные уровни защиты. Читателю ADR важно не спутать одно с другим.

### 6. Учётка разведки (SEC-10)

`discovery-account-ref` — отдельное поле приложения, **не входящее в пул**. Со стороны SDK
обеспечивается один инвариант: **разведка не может взять учётку из рабочего пула**, а прогон не
может взять учётку разведки. Права самой учётки — вне SDK (G-5, AS-08).

## Последствия

**Положительные.**
`STORAGE_STATE` снимает G-1 с критического пути разработки: Slice 3 можно вести и демонстрировать до
согласования байпаса MFA. Возврат учётки через `ResourceScope` гарантирован тем же кодом, что
закрывает браузер, — отдельного механизма и отдельного риска утечки не появляется. Пул за
интерфейсом позволяет заменить in-process реализацию внешним брокером без изменения тестов.

**Отрицательные.**
`UiAuthScheme` — второй enum схем аутентификации рядом с `AuthScheme`. Это выглядит дублированием,
но им не является: `AuthScheme` описывает HTTP-заголовок, `UiAuthScheme` — способ входа в
интерфейс; объединение заставило бы REST-адаптер знать про `FORM`. Расхождение фиксируется в Javadoc
обоих типов.

Потолок параллельности становится равен размеру пула — параметру, который SDK не контролирует.

**Нейтральные.**
`SSO` в enum без реализации даёт говорящий отказ вместо ошибки конфигурации. Реализация — волна 2,
после G-1.

## Риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| G-1 не закрыт для приложений волны | **Высокая** | **Высокое** | `STORAGE_STATE` как обходной путь; BR-30 допускает пометку «неавтоматизируемо» |
| G-5 не закрыт — пула нет | **Высокая** | Высокое | До Slice 4 модуль работает последовательно на одной учётке; параллельность — отдельная задача, не блокирующая Slice 1–3 |
| Учётка не возвращена в пул при аварийном завершении JVM | Средняя | Среднее | In-process пул умирает вместе с JVM — проблема самоустраняется; для внешнего брокера (будущее) потребуется TTL аренды |
| `storageState` протухает (сессия истекла) | **Высокая** | Среднее | Проверка валидности при загрузке; при провале — повторный вход по `FORM`, если он доступен, иначе `BROKEN` с внятным сообщением |
| Файл `storageState` утечёт в артефакты | Низкая | **Высокое** | Явный запрет прикладывать; тест «`storageState` отсутствует среди вложений»; каталог под SEC-09 |
| Гонка за `storageState` одной учётки между двумя тестами | Средняя | Среднее | Учётка выдаётся эксклюзивно; два теста не могут держать одну учётку одновременно — это и есть инвариант пула |
| Пул станет узким местом и обесценит BR-25 | Средняя | Среднее | Диагностика «ожидание учётки заняло N с» в `StepResult`; замер на волне 1 |

## Отклонённые альтернативы

**А2 — все три схемы сразу.** Отклонено. `SSO` требует закрытого G-1 и знания конкретной
IdP-конфигурации каждого приложения; включение его в волну 1 ставит самую рискованную часть в
зависимость от внешнего согласования, которое BRD помечает как условие исполнимости, а не как
задачу.

**А3 — только `STORAGE_STATE`.** Отклонено. Перекладывает подготовку сессии на человека при **каждом**
прогоне для приложений, где обычная форма логина работает, и делает ночной регресс (UC-06)
неавтономным.

**Б2 — пул в `stand-test-core`.** Отклонено. Пул техучёток — UI-специфичная надобность (протокольные
адаптеры используют одну учётку сервиса из `AuthConfig`), а core обязан оставаться свободным от
надобностей одного адаптера. Если пул понадобится второму адаптеру — тогда и переносится, по факту,
а не авансом.

**Б3 — внешний брокер.** Отклонено для волны 1: требует отдельного сервиса, его эксплуатации и
согласования — новый внешний блокер там, где их и так пять. **Архитектурно не отвергается**:
`AccountPool` — интерфейс ровно ради этого.

**Б4 — без пула.** Отклонено как целевое: делает BR-25/BR-34 невыполнимыми. **Принято как режим по
умолчанию до Slice 4**: приложение без объявленного пула работает на одной учётке, параллельность
на уровне классов отключается пометкой `@StandSerial`.

## Реализация

Решения 1–6 реализованы. Четыре места, где код отличается от текста выше, и почему.

**1. У `LeasedAccount` нет `storageState()`.** Пул живёт на JVM и переживает любой прогон, а каталог
артефактов — это конфигурация прогона; путь, вычисленный пулом, заморозил бы настройки того прогона,
который случайно создал пул первым. Требование ADR — «состояние принадлежит учётке, а не набору» —
обеспечивается `accountId()` на аренде плюс `StorageStateStore`, который выводит путь из id учётки и
настроек текущего прогона. Инвариант тот же, источник истины один.

**2. Форма реестра учёток — `<id>:<роль>[:<переменная-логина>:<переменная-пароля>]`.** §5 оставлял
форму деталью реализации; вот она. Двухполевая запись выводит имена переменных из id, чтобы реестр из
десяти учёток был писуем. Плейсхолдеры `${VAR}` внутри записи запрещены: поля разделяет `:`, и
значение по умолчанию сделало бы запись неоднозначной.

**3. `challenge` объявляется в реестре, а обходится — только внешним обработчиком.** BR-30 требовал
«документированную стратегию»; вместо документа введены `UiLoginChallenge {NONE, MFA, OTP, CAPTCHA}` в
реестре и SPI `UiLoginChallengeHandler`. SDK не поставляет ни одной реализации: объявленный challenge
без обработчика на classpath — отказ конфигурации, называющий гейт G-1 и `STORAGE_STATE` как
альтернативу, **до** резолва учётных данных. Это переводит G-1 из «где-то в документации» в
«проверяемое поведение».

**4. Обязательность роли проверяет валидатор, а не сборка шага.** «Отказ сборки сценария» невозможен:
ленивый билдер не видит реестра. Правило вынесено в `DefaultScenarioValidator` (pre-flight, до аренды
и до браузера) под собственными кодами `UI_LOGIN_ROLE_REQUIRED` / `UI_LOGIN_ROLE_UNKNOWN` — **не**
константами `ForbiddenOperation`: это несоответствие сценария и реестра, а не запрещённая операция, и
раздувать словарь guardrails ради него было бы неверно.

**5. Путь состояния включает среду:** `<artifacts>/storage-state/<environment>/<application>/<accountId>.json`,
а не то, что написано в §4. Пул ключуется парой (среда, приложение), то есть один и тот же `accountId`
в `ift` и в `dev` — две независимо арендуемые учётки; общий файл означал бы, что прогон на DEV
восстанавливает куку IFT. Инвариант §4 («состояние принадлежит учётке») от этого только строже.

**6. Последнее слово о годности файла — за браузером.** `StorageStateStore.usable(...)` проверяет форму
файла, а не его содержимое: JSON-парсера у модуля нет, а единственная библиотека, которая умеет, заперта
в пакете драйвера. Недописанная сессия проходит эту проверку и отвергается уже при создании контекста —
и раньше на этом пути её никто не удалял, так что одна такая учётка ломалась бы одинаково в каждом
последующем прогоне, пока файл не удалят руками. Теперь отвергнутое состояние удаляется и сессия
открывается заново без него: контракт «испорченный кэш стоит одного входа, а не прогона», который store
и так декларирует для всех прочих негодных файлов, распространён на ветку, где он не соблюдался.

Дополнительно: `FORM` заполняет форму **каждый раз** и ничего не хранит на диске, а сессию
переиспользует только `STORAGE_STATE` — ровно так, как схемы описаны в §1. Приложение с
`STORAGE_STATE`, объявившее и локаторы формы, само себя загружает: первый прогон входит формой и
сохраняет сессию, последующие её переиспользуют.

## Требования BRD, которые закрывает ADR

`BR-28` (secret-ref для входа), `BR-29` (IdP и `storageState` на учётку), `BR-30` (стратегия
MFA/OTP — через `STORAGE_STATE` и пометку «неавтоматизируемо»), `BR-34` (пул по ролям с ограниченным
таймаутом), `BR-25` (изоляция параллельных прогонов), `BR-23` (ограниченность любого ожидания),
`SEC-04` (секреты только через ref), `SEC-10` (учётка разведки), `G-1`, `G-5`.
