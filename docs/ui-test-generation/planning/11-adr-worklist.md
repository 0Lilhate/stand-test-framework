## D-01 · ADR-UI-005 — форма бинарных вложений

| | |
|---|---|
| **ID** | D-01 · документ [`adr/ADR-UI-005-reporting-and-artifacts.md`](../adr/ADR-UI-005-reporting-and-artifacts.md) |
| **Название** | Отчётность, артефакты падения и маскирование |
| **Статус** | `PROPOSED` — черновик написан, решение не принято |
| **Причина** | `core/event/Attachment.java` — `record Attachment(String name, String mediaType, String content)`; `DefaultAllureLifecycleFacade:67` делает `content.getBytes(UTF_8)`. Тракт вложений текстовый целиком: PNG, WebM и ZIP не проходят. Base64 в текстовое поле не решает — `AttachmentType.extensionForMediaType()` выдаст `.bin`. **Это изменение `core`, не учтённое в §13.1 BRD**: там как правка core названы только компенсации (D-9) |
| **Варианты** | **А.** компонент `Path file` в `Attachment`, инвариант «ровно одно из `content`/`file` не null» · **Б.** компонент `byte[] binaryContent` · **В.** отдельный record `BinaryAttachment` + второй список в `StepResult`/`StepEvent` · **Г.** путь к файлу текстом в `content` с условленным media type · **Д.** артефакты не проходят через отчёт вовсе — каталог прогона + пути в диагностике |
| **Рекомендация** | **А** (позиция черновика ADR): аддитивно — `new Attachment(a,b,c)` и `of(...)` компилируются без правок; `Path`, в отличие от `byte[]`, корректен в `equals`/`hashCode` record'а, чего требуют правила репозитория об иммутабельных value-типах |
| **Последствия** | **А:** правка стока графа, от которого зависят все 14 модулей → RISK-15, обязательный прогон 1484 тестов · **Б:** ломает `equals`/`hashCode` record'а и правило иммутабельности · **В:** дублирует список вложений в двух контрактах, дрейф гарантирован · **Г:** тип-небезопасно, приёмник обязан догадываться · **Д:** BR-21 формально закрывается, но отчёт остаётся без картинки — падение диагностируется вне Allure |
| **Зависимые задачи** | S-2.1 (`BLOCKED`), S-2.2, S-2.3, N-07 — то есть **весь срез артефактов**; косвенно KPI-7 |
| **Требования** | BR-21, BR-22, BR-35, SEC-05, SEC-09, D-2 |
| **Владелец решения** | команда SDK |
| **Срок** | **до начала волны 1** — это узел критического пути разработки |

## D-02 · ADR-UI-007 — компенсации не-DB шагов

| | |
|---|---|
| **ID** | D-02 · документ [`adr/ADR-UI-007-non-db-compensations.md`](../adr/ADR-UI-007-non-db-compensations.md) |
| **Название** | Компенсации не-DB шагов и откат данных, созданных через UI |
| **Статус** | `PROPOSED` |
| **Причина** | D-9 BRD утверждает, что откат UI-данных требует доработки `core`. Сверка с кодом показала, что утверждение верно **только для одной из двух трактовок**: (а) компенсатор, регистрируемый адаптером, — `Compensator`, `UndoLog`, `CleanupPolicy.ALWAYS`, `drainCompensations()` реализованы и ничего DB-специфичного не содержат; то, что регистрирует только `DbStepExecutor:191`, — факт употребления, не ограничение модели. (б) сценарный cleanup-шаг — **действительно отсутствует**. Третий связывающий факт: `adaptersDoNotDependOnEachOther` делает компенсацию «отозвать заявку REST-вызовом» внутри UI-модуля невыразимой |
| **Варианты** | **А.** волна 1 = только (а): `UiStepExecutor` регистрирует `UiCompensator`, компенсирующий средствами самого UI; core не трогается · **Б.** волна 1 = (а) + (б) сразу · **В.** только (б) · **Г.** узкий HTTP-клиент в UI-модуле для компенсаций · **Д.** не автоматизировать в волне 1, чистить внешним заданием по `testRunId` |
| **Рекомендация** | **А** (позиция черновика ADR) |
| **Последствия** | **А:** BR-24 закрывается только там, где UI умеет отзывать сам; правки `core` не требуется — RISK-15 по этой линии снимается · **Б:** расширяет `Scenario` полем `cleanup` — граница «конфигурация/сценарий» и объём правки core растут · **В:** обесценивает работающий `UndoLog` · **Г:** дублирует `stand-test-rest` внутри UI-модуля · **Д:** BR-24 (Must) остаётся невыполненным, остаточные данные объявляются в отчёте |
| **Зависимые задачи** | N-02 (`BLOCKED`); сценарные cleanup-шаги волны 2 |
| **Требования** | BR-24, SEC-03, D-9, RISK-15 |
| **Владелец решения** | команда SDK; **вход извне** — OQ-06/AS-05: способ удаления данных подтверждается владельцами каждого приложения волны |
| **Срок** | до начала работ по BR-24; не блокирует критический путь разработки |

## D-04 · ADR-UI-008 — `nothingDependsOnUi` против автоконфигурации Spring

| | |
|---|---|
| **ID** | D-04 |
| **Название** | Подъём `UiStepExecutor` на Spring-пути |
| **Статус** | `REQUIRED` — ADR не написан |
| **Причина** | CONF-04 / GAP-10. `ModuleDependencyArchTest:121–126` запрещает любому модулю ссылаться на `ui` («the ui adapter must be a leaf: it is discovered by ServiceLoader, never depended on»). `StandTestAutoConfiguration:135–146` объявляет исполнителей поимённо и собирает раннер из `List<StepExecutor>` **бинов** — бина UI там нет. На plain-JUnit проблемы нет: `StandTestExtension:170` берёт исполнителей через `ServiceLoader` |
| **Варианты** | **А.** исключение из arch-правила для стартера (ребро `starter → ui` как `compileOnly` optional, по образцу прочих адаптеров) · **Б.** стартер добирает исполнителей `ServiceLoader`'ом **в дополнение** к бинам · **В.** оставить ручное объявление `@Bean UiStepExecutor` и задокументировать |
| **Рекомендация** | **Б**: не трогает arch-правило (компиляционного ребра не возникает), убирает ручной шаг у потребителя и заодно подхватит любой будущий сторонний адаптер. Требует дедупликации «бин + SPI одного типа» |
| **Последствия** | **А:** ослабляет правило, которое защищает протокольные тесты от браузера в classpath · **Б:** порядок исполнителей становится менее явным; нужен тест на дедупликацию · **В:** нулевая стоимость сейчас, постоянный налог на каждого Spring-потребителя; обход уже документирован |
| **Зависимые задачи** | N-04 (`BLOCKED`) |
| **Требования** | адоптация Spring-потребителями; NFR-05 (не нарушить) |
| **Владелец решения** | команда SDK |
| **Срок** | до первого Spring-потребителя UI; **планирование не блокирует** |

## D-07 · ADR-UI-011 — стратегия измерения набора: браузерный дубль или живой стенд

| | |
|---|---|
| **ID** | D-07 |
| **Название** | Как эталонный набор становится прогоняемым |
| **Статус** | `REQUIRED` · **SP-01 выполнен 2026-08-04** — решение больше ничего не ждёт |
| **Причина** | PQ-09 / GAP-06. У всех 12 UI-кейсов `execution.outcome: NOT_RUN`: браузерного дубля набор не поставляет. **Уточнение spike:** до браузера доходят **4 кейса из 12** — остальные восемь по замыслу заканчиваются на `AWAITING_APPROVAL` раньше, чем понадобится DOM, и их `NOT_RUN` верная запись, а не долг. Область сближения — **два экрана и одиннадцать элементов**. Кандидат существует — `stand-test-ui/src/test/java/.../playwright/LocalUiTestApplication.java` (тот же алиас `client-portal`, форма входа, сессионная кука, асинхронный статус), но **его DOM другой**. Шесть UI-кейсов получают отчёт разведки готовым, то есть набор измеряет авторинг, а не разведку |
| **Варианты** | **А.** привести `LocalUiTestApplication` к DOM кейсов · **Б.** привести кейсы к DOM существующего приложения · **В.** написать отдельный дубль под набор · **Г.** мерить только на живом стенде (тогда набор ждёт G-1/G-4/G-5) |
| **Рекомендация** | **А** — spike выполнен и ответил ([`31-ui-dom-convergence-spike.md`](31-ui-dom-convergence-spike.md) §6). Решает не объём правок (по строкам Б даже дешевле: ~170 против ~200 + ~200 тестов), а то, что **три кейса непереносимы** — `ui-fragile-locators-no-testid`, `ui-form-validation-…`, `ui-non-reversible-bulk-delete` написаны про свойство DOM, которого у дубля нет по построению, и ещё два обедняются. **Г** отдельно по-прежнему не годится: ставит измеримость кита в зависимость от внешних гейтов. Строка «выбирать до spike нельзя» снята — она относилась к состоянию до 2026-08-04 |
| **Последствия** | **А:** дубль растёт вместе с набором, и это не главная его цена — spike измерил скрытую: дубль, совпавший с шестью подсаженными отчётами разведки, обязан совпадать с ними и дальше, иначе корпус воспроизведёт дефект собственного кейса `ui-stale-discovery-testid-renamed`. Отсюда обязательный тест-парити · **Б:** кейсы теряют фактуру, ради которой писались · **В:** третий DOM в репозитории · **Г:** KPI-3/KPI-4 не наблюдаются до пилота. **Общее для А–В:** результат на дубле — **не** замер на живом приложении, и это обязано быть написано рядом с числом |
| **Зависимые задачи** | N-03 (`BLOCKED`), M-01 частично |
| **Требования** | KPI-3, KPI-4, измеримость BR-01/BR-05/BR-10/BR-11 |
| **Владелец решения** | команда SDK |
| **Срок** | до замеров §19.1 |

## D-08 · ADR-UI-012 — параллельность: классы или классы + методы

| | |
|---|---|
| **ID** | D-08 |
| **Название** | Модель параллельности UI-набора |
| **Статус** | `REQUIRED` — конфликт зафиксирован, решения нет |
| **Причина** | CONF-02. BR-25 требует «параллельность на уровне классов **и дополнительно на уровне методов внутри класса**». Реализовано: `mode.classes.default=concurrent`, `mode.default=same_thread`, `maxParallelForks = 1`. Обоснование записано в самом файле: инвариант SDK «один прогон сценария = один поток»; пул учёток внутрипроцессный, второй JVM выдал бы ту же учётку второму прогону |
| **Варианты** | **А.** понизить BR-25 до параллельности классов с объяснением в BRD · **Б.** признать методы отдельным требованием к изоляции состояния тестового класса и реализовать в волне 2 · **В.** оставить конфликт незакрытым |
| **Рекомендация** | **А или Б** — решение владельца BRD совместно с командой SDK; **В недопустимо**: BR-25 остаётся требованием, которое реализация не выполняет и никто об этом не объявил. Техническое замечание для решения: потолок параллельности UI-набора — размер пула учёток (OQ-12/G-5); выше него прогоны **очередятся, а не упадут** |
| **Последствия** | **А:** BR-25 закрывается сегодняшней реализацией · **Б:** работа волны 2 + пересмотр размера пула по OQ-12 · **В:** матрица прослеживаемости навсегда несёт `ARCHITECTURAL_CONFLICT` |
| **Зависимые задачи** | BR-25 в части методов — волна 2; размер пула учёток (OQ-12, G-5) |
| **Требования** | BR-25 (Should), BR-34, OQ-12 |
| **Владелец решения** | владелец BRD + команда SDK |
| **Срок** | до планирования волны 2; **волну 1 не блокирует** |
