## 0. Ответ в трёх строках

**Через сеть в раннер едут не «браузеры Playwright», а две разные посылки по двум разным каналам.**
Драйвер (Node.js плюс JS-пакет, `driver-bundle-1.61.0.jar` — **192 МБ**) приезжает по Maven через
внутренний Artifactory, то есть по уже согласованному и уже кэшируемому каналу. Из интернета идут
**только сборки браузера** — на Linux x64 это **293,5 МиБ** в трёх архивах.

**Способ доставки надо выбирать не между «зеркало» и «образ»: зеркало — это то, чем собирается
образ.** Предустановка в образ даёт ноль сетевого трафика в момент джобы и +539 МБ к образу;
зеркало нужно всё равно — в тот момент, когда образ пересобирают под новую версию Playwright.

**И главное, потому что оно опрокидывает написанное в README.** `browserTest` **не падает** на
машине без браузеров, как обещано в документе: Java-клиент молча скачивает их **прямо во время
теста** — измерено **1,1 ГБ**, включая Firefox и WebKit, которых этот модуль не водит. В закрытом
контуре это означает не «упадёт понятно», а «пойдёт в интернет там, где до него дотянется, и
свалится в середине прогона там, где нет». Выключается это одной переменной —
`PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1`, — и её отсутствие в CI-джобе делает бессмысленным любой из
двух способов доставки.

## 1. Что на самом деле пересекает сеть

| Посылка | Канал | Размер | Кто её уже возит |
|---|---|---|---|
| `com.microsoft.playwright:playwright:1.61.0` | Artifactory (Maven) | 632 КБ | Gradle, кэш `gradle-modules` |
| `com.microsoft.playwright:driver:1.61.0` (JS-пакет драйвера) | Artifactory (Maven) | 2,8 МБ | то же |
| `com.microsoft.playwright:driver-bundle:1.61.0` (бинарники Node для 5 платформ) | Artifactory (Maven) | **192 МБ** | то же |
| Сборки браузера | **cdn.playwright.dev** | **293,5 МиБ** (Linux x64) | никто |

Это разделение — самая полезная новость отчёта. `driver-bundle` содержит `node` для linux,
linux-arm64, mac, mac-arm64 и win32_x64 (~580 МБ в распакованном виде, 192 МБ в jar); он **не**
скачивается из интернета и не требует зеркала — он обычная Maven-зависимость и уже лежит в кэше
`.gradle-home/caches/modules-2/`, который `.gitlab-ci.yml` кэширует между прогонами. Согласовывать и
зеркалить надо только третью строку.

Побочное следствие для образа: 192 МБ — это то, что джоба тянет из Artifactory **при холодном
кэше**, и оно относится к `verify` тоже, а не только к будущей UI-джобе: `stand-test-ui` входит в
`./gradlew build`.

## 2. Что именно скачивается и откуда — точные адреса

`./gradlew :stand-test-ui:installPlaywrightBrowsers` запускает `com.microsoft.playwright.CLI install
chromium`. Прогон в чистый каталог показал, что «chromium» — это **три** артефакта, а не один:

| Артефакт | Ревизия / версия | Архив (Linux x64) | Байт | Распаковано |
|---|---|---|---|---|
| Chrome for Testing | 149.0.7827.55 (r1228) | `chrome-linux64.zip` | 185 646 494 (177,0 МиБ) | 344 МБ |
| Chrome Headless Shell | 149.0.7827.55 (r1228) | `chrome-headless-shell-linux64.zip` | 119 778 157 (114,2 МиБ) | 192 МБ |
| FFmpeg | r1011 | `ffmpeg-linux.zip` | 2 376 500 (2,3 МиБ) | 2,5 МБ |
| **Итого** | | | **307 801 151 (293,5 МиБ)** | **539 МБ** |

Распакованные размеры измерены на mac-arm64 (`du -sh` по каталогу `PLAYWRIGHT_BROWSERS_PATH` после
чистой установки); порядок величины для Linux тот же, точное число — за прогоном на образе.

**Адресов два, и это не формальность.** Разбор `DOWNLOAD_PATHS` в `coreBundle.js` драйвера и
проверка запросами дали:

| Класс артефакта | Базовый URL | Что отвечает |
|---|---|---|
| Chromium и headless shell | `https://cdn.playwright.dev/builds/cft/<browserVersion>/<platform>/<archive>.zip` | **HTTP 307** → `https://storage.googleapis.com/chrome-for-testing-public/…` |
| FFmpeg, Firefox, WebKit | `https://cdn.playwright.dev/dbazure/download/playwright/builds/<name>/<revision>/<archive>.zip` | HTTP 200, отдаёт сам |

То есть **разрешить в firewall один `cdn.playwright.dev` недостаточно**: байты Chromium физически
лежат в бакете Google, а `cdn.playwright.dev` для них — только редирект. Обратное тоже верно и
тоже проверено: путь `builds/cft/…` на зеркале `playwright.download.prss.microsoft.com`, которое
драйвер использует для остальных браузеров, отвечает **HTTP 400** — этот класс артефактов там
просто не лежит.

## 3. `PLAYWRIGHT_DOWNLOAD_HOST` — что он делает на самом деле

Проверено прогоном с заведомо несуществующим хостом, а не чтением документации:

```
PLAYWRIGHT_DOWNLOAD_HOST=https://mirror.invalid.example/playwright \
  ./gradlew :stand-test-ui:installPlaywrightBrowsers
→ Downloading Chrome for Testing 149.0.7827.55 (playwright chromium v1228)
  from https://mirror.invalid.example/playwright/builds/cft/149.0.7827.55/mac-arm64/chrome-mac-arm64.zip
→ Error: getaddrinfo ENOTFOUND mirror.invalid.example  (дважды, затем задача падает)
```

Из этого следуют три факта, каждый из которых нужен тому, кто будет заводить зеркало:

1. **Переменная заменяет только хост-префикс.** Путь `builds/cft/<version>/<platform>/<archive>.zip`
   дописывается дословно. Зеркало обязано отдавать **обе** формы пути — `builds/cft/…` и
   `builds/ffmpeg/…`, — иначе установка встанет на втором артефакте из трёх.
2. **Публичного отката нет.** Заданный хост *вытесняет* список публичных зеркал целиком
   (`mirrors = [customHostOverride]`), а не добавляется к нему. Это ровно то поведение, которого
   требует `security_requirements` карточки: при недоступном зеркале джоба падает, а не уходит в
   интернет.
3. **Ловушки с демоном Gradle нет.** Проверено отдельно: два запуска подряд с разными значениями
   переменной при живом демоне дали разные URL — `JavaExec` получает окружение текущего вызова, а не
   то, с которым стартовал демон. Инструкция «выставьте переменную окружения» работает как написана.

Есть и вторые переменные — `PLAYWRIGHT_CHROMIUM_DOWNLOAD_HOST`, `…_FIREFOX_…`, `…_WEBKIT_…`, — они
перекрывают общую для своего класса. Для нашего случая (только chromium) они не нужны.

## 4. Находка, из-за которой оба способа доставки без неё бессмысленны

`stand-test-ui/README.md` утверждает: «`browserTest` **всегда** нужен браузер и он падает громко без
него». **Это неверно.** Прогон против пустого `PLAYWRIGHT_BROWSERS_PATH`:

```
PLAYWRIGHT_BROWSERS_PATH=<пустой каталог> ./gradlew :stand-test-ui:browserTest --rerun-tasks
→ Downloading Chrome for Testing … / Chrome Headless Shell … / Firefox 151.0 … / WebKit 26.5 … / FFmpeg …
→ BUILD SUCCESSFUL in 1m
→ du -sh <каталог> = 1,1 ГБ
```

Java-клиент Playwright доустанавливает браузеры сам, при первом `Playwright.create()`, и берёт
**все пять наборов по умолчанию** — включая Firefox (274 МБ) и WebKit (291 МБ), которые этот модуль
не водит и никогда не запускал. То есть неуправляемый путь стоит **вдвое** дороже управляемого
(1,1 ГБ против 539 МБ) и идёт в интернет **из тестовой JVM**, а не из отдельной задачи установки.

Выключатель — `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` (читается классом `DriverJar` клиента). С ним тот
же прогон:

```
PLAYWRIGHT_BROWSERS_PATH=<пустой> PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 ./gradlew :stand-test-ui:browserTest --rerun-tasks
→ 24 из 24 браузерных тестов FAILED, скачано 0 байт
```

и отказ классифицирован верно — `StandTestException` (BROKEN), с именем приложения и полным путём к
отсутствующему исполняемому файлу:

> `Step [1/2] 'login' (ui.login) BROKEN: Could not start the 'chromium' browser for application
> 'client-portal-parallel': Executable doesn't exist at …/chromium_headless_shell-1228/…`

Одна оговорка к качеству этого отказа: подсказка внутри рамки от самого Playwright предлагает
**Maven**-команду (`mvn exec:java -D exec.mainClass=com.microsoft.playwright.CLI …`) — в
Gradle-репозитории она никуда не ведёт. Правильная команда — `./gradlew
:stand-test-ui:installPlaywrightBrowsers`, и это стоит написать рядом в README (сделано в этом же
изменении), потому что текст рамки приходит из чужого артефакта и нам не принадлежит.

**Вывод для CI:** `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` обязана стоять в UI-джобе `UITG-S026`
независимо от выбранного способа доставки. Без неё «браузеры в образе» и «браузеры с зеркала»
одинаково превращаются в «браузеры из интернета, если до него дотянемся» — то есть в зелёный прогон,
который ничего не доказывает про контур, и в красный там, где интернета нет, посреди теста, а не на
шаге установки.

Побочно измерено и тоже относится к CI: Gradle **не** считает расположение браузеров входом задачи.
Второй прогон `browserTest` с изменённым `PLAYWRIGHT_BROWSERS_PATH` вернул `UP-TO-DATE` за 587 мс,
не запустив ни одного браузера. Проверка «образ с браузерами работает» без `--rerun-tasks` ничего не
проверяет.

## 5. Два способа доставки, посчитанные

Общий знаменатель для обоих: версия браузера жёстко приколочена к версии Playwright (`browsers.json`
внутри `driver-1.61.0.jar` — chromium r1228 / 149.0.7827.55). Воспроизводимость обеспечивает
каталог версий `gradle/libs.versions.toml`, а не способ доставки: обновление `playwright = "1.61.0"`
меняет требуемую ревизию браузера и обязано менять обе стороны сразу.

| | **А. Внутреннее зеркало** (`PLAYWRIGHT_DOWNLOAD_HOST`) | **Б. Предустановка в образ** |
|---|---|---|
| Трафик на джобу | 293,5 МиБ при холодном кэше, 0 при тёплом | **0** |
| Время старта | скачивание + распаковка; локально на быстром канале — **16 с** на все три архива | 0 |
| Размер образа | без изменений | **+539 МБ** |
| Что надо завести | remote-repo/раздачу, отдающую две формы пути (§3.1); правило firewall на один внутренний хост | пересборку образа + место в реестре образов |
| Кто владелец | владелец Artifactory/зеркала | владелец CI-образа |
| Дрейф версий | невозможен: ревизию называет драйвер | **возможен**: образ отстаёт от каталога версий |
| Реакция на дрейф | — | молча скачает из интернета, **если** не стоит `SKIP_BROWSER_DOWNLOAD=1`; с ней — громкий отказ |
| Пригодность к оффлайну | нужен сетевой доступ к зеркалу | полный оффлайн |

**Промежуточный вариант, который стоит назвать отдельно, потому что он почти бесплатен.** GitLab
кэширует только пути под `$CI_PROJECT_DIR` — это уже записано в `.gitlab-ci.yml` про
`GRADLE_USER_HOME`. Значит достаточно направить `PLAYWRIGHT_BROWSERS_PATH` внутрь рабочего каталога
и добавить его в `cache.paths`:

```yaml
variables:
  PLAYWRIGHT_BROWSERS_PATH: "$CI_PROJECT_DIR/.playwright-browsers"
  PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD: "1"
cache:
  paths:
    - .playwright-browsers/
```

Это снимает 293,5 МиБ со всех прогонов, кроме первого после инвалидации кэша. Но кэш GitLab —
оптимизация, а не источник: он вытесняется, и вариант, который на него опирается, обязан иметь под
собой работающий А или Б. Как самостоятельный способ доставки он не годится.

## 6. Рекомендация

**Б как основной, А как то, чем Б собирается, и `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` в обоих.**

Причина предпочесть Б не в 293 мегабайтах и не в 16 секундах — эти числа малы и оба варианта их
переживают. Причина в том, что Б **не требует сетевого доступа в момент прогона теста**, а значит
не добавляет к прогону ещё одной причины «красный не из-за кода». Для набора, чей смысл — отвечать
на вопрос «сломало ли изменение существующее», лишний сетевой отказ дороже полугигабайта в образе.

Но называть А альтернативой неверно: чтобы **собрать** образ Б, браузеры всё равно надо откуда-то
взять, и в закрытом контуре это ровно зеркало из §3 (либо сборка образа в контуре, где интернет
есть, — организационное решение, не техническое). Поэтому А заводится один раз и живёт как вход
пересборки образа, а не как путь каждой джобы.

Конкретно, что должно оказаться в UI-джобе `UITG-S026`:

```yaml
variables:
  PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD: "1"     # без неё контур не закрыт
  PLAYWRIGHT_BROWSERS_PATH: "/opt/ms-playwright"   # путь в образе; либо кэш из §5
```

и никакого вызова `installPlaywrightBrowsers` в самой джобе — эта задача принадлежит сборке образа.
Системные библиотеки Chromium остаются заботой образа: `installPlaywrightBrowsers` намеренно идёт
без `--with-deps` (флаг требует root и упал бы ровно на тех агентах, где нужнее всего), так что
образ обязан нести их сам. Проверка «несёт ли» — не этот spike, а первый прогон `browserTest` на
образе; в него же попадёт и требование к `TMPDIR`: клиент распаковывает `node` своей платформы
(≈118 МиБ) плюс JS-пакет (12 МБ) во временный каталог на каждый прогон и убирает за собой (проверено
— каталогов `playwright-java-*` после прогонов не осталось).

## 7. AS-01 — не подтверждено и не опровергнуто

Второй критерий приёмки карточки — «стенды DEV/IFT достижимы из сети CI» — **этим spike закрыт быть
не может**, и это не оговорка, а честный результат: у сессии нет ни доступа к сети раннера, ни
адреса, который следовало бы проверить.

Второго нет буквально: в репозитории **не существует ни одного реального адреса стенда**. Реестр
сред хранит алиасы и `*-ref` (имена переменных окружения), а не значения, — это инвариант SDK, а не
пробел. Какое приложение будет первым и по какому адресу оно живёт, называет внешний гейт **G-6**
(`UITG-X006`), и до его ответа AS-01 нельзя даже сформулировать, не то что проверить.

Что закрывает AS-01, точно:

1. **G-6 называет приложение волны 1 и его `base-url` на DEV/IFT** (`UITG-X006`);
2. владелец CI запускает разовую джобу на **том самом раннере и с тем самым тегом**, который получит
   UI-набор, и она делает единственную вещь — `curl -sS -o /dev/null -w '%{http_code}'
   <base-url приложения>`. Не с ноутбука, не с bastion: сеть раннера — это отдельный факт;
3. результат вписывается в `UITG-X003` (G-3) — им же закрывается `definition_of_ready` карточки
   `UITG-S026`.

**Что делать, если AS-01 опровергнут** (`negative_scenarios` карточки): `S026` и `V001` неисполнимы
в этом виде, и эскалация идёт владельцам сети. Обхода в разработке нет и не будет: имитировать
достижимость стенда нечем, а браузерный набор против локального дубля отвечает на другой вопрос
(`UITG-S023`, ADR-UI-011). Вариант «раннер в другой сети» — организационное решение, и spike может
только назвать его как существующее.

**Что при этом всё равно сделано:** первый критерий приёмки закрыт целиком и `definition_of_done`
карточки — «`S026` может быть спланирована» — выполнен: способ доставки назван, посчитан, выбран, и
названы три переменные окружения, без которых он не работает. `S026` упирается теперь только в G-3,
то есть в наличие раннера с образом, а не в неизвестность про то, как туда попадут браузеры.

## 8. Что осталось неизвестным

- **Размеры и время на Linux.** Байты архивов сняты с CDN и точны; распакованные 539 МБ измерены на
  mac-arm64. Chromium под Linux распаковывается иначе (нет `.app`-обёртки), так что число сдвинется
  — в какую сторону, покажет первая сборка образа.
- **16 секунд — это про канал ноутбука, а не про раннер.** Переносить это число в оценку джобы
  нельзя; переносить можно 293,5 МиБ и делить на пропускную способность раннера.
- **Системные библиотеки Chromium в образе.** Мы намеренно не ставим `--with-deps`, значит
  ответственность на образе; какой именно базовый образ её несёт — вопрос владельца CI. Симптом
  отсутствия — падение запуска браузера, а не установки.
- **Стоит ли вообще ставить `chromium` (headed), а не только headless shell.** Установка тянет оба
  (177 + 114 МиБ); `browserTest` по умолчанию headless, но `-Dstand.test.ui.headless=false` —
  документированный режим отладки. Отказ от headed-сборки сэкономил бы ~177 МиБ образа ценой этого
  режима; решение не входит в границы spike и стоит рядом с `UITG-S026`.
- **`SELENIUM_REMOTE_URL`.** Клиент читает эту переменную — то есть путь «браузер вообще не в
  образе, а в grid» существует уже сегодня. Это `UITG-S035` (волна 2) и здесь только помечено как
  существующее, а не оценено.
