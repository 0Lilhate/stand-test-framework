## 1. Зачем это первым

`X006` — **корень всей заблокированной части бэклога**. В его тени 16 карточек из 25 заблокированных,
и четыре гейта объявляют его своим прямым предусловием формулировкой «состав приложений волны
определён»:

```
X006 (состав волны)
 ├─ X001  G-1  байпас MFA/OTP/КАПЧИ          → V001, V002, V003
 ├─ X005  G-5  пул техучёток и учётка разведки → V001, V002, V003
 ├─ X007  OQ-06 способ удаления данных        → ADR002 → E05, S019
 └─ X013  OQ-07 где живут сгенерированные тесты → ADR006 → V004
```

Ни один из четырёх нельзя даже поставить вопросом, пока не известно, **про какие приложения
спрашивают**. Поэтому порядок не «сначала ИБ, потом состав», а строго наоборот.

Гейт не требует ни строчки кода. Его выход — список.

## 2. Что решает гейт (BRD §14 G-6 дословно)

> Состав волны 1 определён: **2–3 приложения** с владельцами и назначенными
> **автоматизаторами-владельцами набора** (§17). Для каждого приложения зафиксировано, **протягивает ли
> backend корреляционный заголовок от фронтенда до Kafka/БД**; где не протягивает — записан fallback на
> связывание по захваченным данным (D-8, BR-13).

Критерий приёмки карточки — одна строка: **«список приложений с владельцами и отметкой про
корреляцию»**. Всё остальное ниже — подсказки, чтобы этот список сразу годился четырём следующим
гейтам и не пришлось собирать его дважды.

## 3. Бланк — по одному на приложение

Скопируйте блок 2–3 раза. Пустых полей быть не должно: «не знаю» и «нет» — **валидные ответы**,
незаполненное поле — нет, потому что молчание потом прочитают как «да».

```
### Приложение N

  1. Алиас (латиницей, kebab-case)     : ______________________   → станет ключом в реестре
  2. Человеческое название и контур     : ______________ DEV / IFT
  3. Владелец приложения (ФИО, команда) : ______________________
  4. Автоматизатор-владелец набора      : ______________________
  5. Второй фактор на входе             : нет / MFA / OTP / КАПЧА      (см. §4а)
 5а. Вход через корпоративный SSO       : да / нет
  6. Выдаётся ли сессия заранее         : да / нет
  7. Роли, которые нужны сценариям      : ______________________
  8. Корреляция (см. §4)                : ДА / НЕТ / НЕ ЗНАЮ
  9. Экранный идентификатор (см. §5)    : ______________________ / нет
 10. Способ удаления тестовых данных    : UI / API / БД / нет
```

Что каждое поле открывает дальше — и что сломается, если его не заполнить:

| № | Поле | Куда ложится | Что без него встанет |
|---|---|---|---|
| 1 | Алиас | ключ в `ui-applications` реестра сред | сценарий адресует приложение **только** алиасом; литеральный URL в шаге невыразим |
| 2 | Название и контур | `base-url-ref` (имя переменной окружения, не адрес) | нечего whitelist'ить |
| 3 | Владелец приложения | `X001`, `X005`, `X007` — все три идут к нему | некому задать три следующих вопроса |
| 4 | Автоматизатор-владелец набора | BRD §17, DEP-07 | **некому принимать результат** — прямая формулировка риска гейта |
| 5 | Второй фактор | `auth.challenge` в реестре; **вход `X001`** | SDK отказывается стартовать с внятным сообщением; байпаса нет и не будет |
| 5а | SSO | `auth.scheme: SSO` — **другое поле, не challenge** | схема в словаре есть, в этой версии SDK не реализована; приложение с SSO не идёт в волну 1 без отдельного решения |
| 6 | Сессия заранее | выбор `auth.scheme`: `FORM` или `STORAGE_STATE` | при MFA `STORAGE_STATE` — единственная альтернатива байпасу |
| 7 | Роли | `auth.roles` + размер пула в `X005` | `ui.login` обязан называть роль; незаявленная роль отвергается до старта браузера |
| 8 | Корреляция | **собственно отметка гейта**; BR-13, KPI-5 | способ связывания UI↔backend не определён |
| 9 | Экранный идентификатор | fallback-связывание по данным (D-8) | вместе с «нет» в п. 8 → см. §5 |
| 10 | Удаление данных | **вход `X007`** → `ADR002` | BR-24 остаётся декларацией |

**Секретов в бланке нет и быть не должно.** Логины, пароли и адреса стендов сюда не пишутся: SDK
принимает только **имена переменных окружения**, а сам ростер учёток живёт за `credentials-pool-ref`
и несёт идентификаторы, роли и **имена** переменных с учётными данными. Это предмет `X005`, не этого
бланка.

## 4а. Поле 5 — что считается «вторым фактором»

Всё, что приложение просит на входе **сверх логина и пароля**:

| Что видно на экране входа | Ответ | Значение `auth.challenge` |
|---|---|---|
| после логина и пароля сразу вошли | нет | `none` |
| подтверждение в приложении-аутентификаторе, push, аппаратный токен | MFA | `mfa` |
| одноразовый код по SMS или почте | OTP | `otp` |
| «докажите, что вы не робот» | КАПЧА | `captcha` |
| редирект на корпоративную страницу входа | **это поле 5а, а не 5** | `auth.scheme: SSO` |

**Как узнать за минуту:** открыть страницу входа приложения на DEV/IFT и ввести тестовый логин с
паролем. Что появилось следом — то и есть ответ.

**Почему SDK вообще про это спрашивает.** Браузер робота введёт логин и пароль, но код из SMS ему взять
неоткуда. **Байпаса второго фактора в SDK нет и не будет** — это решение записано в самом коде: обход,
встроенный в тестовый SDK, был бы постоянным приглашением ослабить настоящую защиту, поэтому вопрос
«можно ли ослабить второй фактор для тестовых учёток» решается организацией, а не библиотекой. Это и
есть гейт G-1 (`X001`).

Что SDK делает вместо: если приложение объявило challenge, UI-адаптер ищет `UiLoginChallengeHandler` в
`META-INF/services` и, не найдя, **отказывается до старта** сообщением, которое называет гейт G-1 и
санкционированную альтернативу — `STORAGE_STATE`.

**Объявлять challenge полезно даже без обработчика**, и это отдельная мысль: объявление превращает
«тест висит на экране одноразового пароля и падает по таймауту» в «это приложение не автоматизируется
через форму входа — используйте подготовленную сессию».

Что означает каждый ответ для следующего шага:

| Ответ | Что дальше |
|---|---|
| **нет** | `auth.scheme: FORM`, `challenge: none`. `X001` по этому приложению закрывается **тривиально** — согласовывать нечего |
| **MFA / OTP / КАПЧА** | Два пути: **(а)** ИБ разрешает отключить второй фактор *для тестовых учёток на стенде* — это и есть предмет согласования G-1; **(б)** `STORAGE_STATE`: сессию готовят один раз вне SDK, SDK её восстанавливает и проверяет по `signed-in-locator`, а при истечении переходит на форму. Тогда решающим становится поле 6 |
| **SSO (поле 5а)** | Схема есть в словаре конфигурации, но **в этой версии SDK не реализована** — отказ с внятным сообщением. Приложение с SSO не идёт в волну 1 без отдельного решения |

## 4. Поле 8 — единственное, где вопрос надо задать точно

Формулировка BRD «протягивает ли backend корреляционный заголовок **от фронтенда до Kafka/БД**» шире
того, что SDK умеет проверить. Разница не редакторская — от неё зависит, годится ли полученный ответ:

**Проверено по коду 2026-08-08:**

- **Браузер отправляет** `X-Correlation-Id` на каждом запросе. Имя фиксировано константой
  `UiStepExecutor.CORRELATION_HEADER`; в волне 1 у UI-приложения **нет** поля корреляции в реестре,
  в отличие от REST-сервиса, — то есть переименовать заголовок под приложение сегодня нельзя.
- **Kafka сверяет корреляцию только в заголовке сообщения.** `KafkaStepExecutor` реализует носитель
  `HEADER` и никакой другой: `KEY`, `PAYLOAD_FIELD` и `METADATA` в enum есть, но kafka-адаптер их не
  поддерживает. Значит «протянули, но положили в ключ сообщения или в тело» — это **НЕТ** для целей
  гейта.
- **У БД корреляции нет вовсе.** В `stand-test-db` слова `correlation` не встречается ни разу, и у
  `datasources` в реестре нет такой секции. **Связывание с БД всегда идёт по захваченным данным** —
  половина «до БД» из формулировки BRD технически не существует, и спрашивать про неё не нужно.

**Итого вопрос владельцу backend звучит так:**

> Если во входящем HTTP-запросе придёт заголовок `X-Correlation-Id`, доедет ли это значение до
> **заголовка** сообщения, которое сервис публикует в Kafka?

**Как проверить за 15 минут, не спрашивая никого:** отправить в API приложения запрос с заголовком
`X-Correlation-Id: <любой uuid>` и поискать этот uuid в заголовках сообщений топика. Нашёлся в
заголовке — **ДА**. Нашёлся в ключе или в теле — **НЕТ** (и это стоит назвать вслух: доработка на
стороне продукта тут маленькая, а выигрыш для KPI-5 большой). Не нашёлся — **НЕТ**.

**«НЕ ЗНАЮ» — тоже ответ и он не блокирует гейт.** BR-13 сформулировано так, что отсутствие
протягивания **понижает качество связывания, но не делает требование невыполнимым**: основной механизм —
связывание по данным, корреляция предпочтительна. Гейт закрывается отметкой, а не положительным
ответом.

## 5. Единственная комбинация, которая исключает приложение

Из `negative_scenarios` карточки и RISK-14:

> **нет корреляции (п. 8) И нет экранного идентификатора (п. 9)** → сквозной UI+backend сценарий для
> этого приложения **не строится**; кейс покрывается раздельно UI- и backend-тестами, а само приложение
> уезжает в волну 2.

Экранный идентификатор — это значение, которое видно на экране после действия и по которому потом
можно найти запись в backend: номер заявки, идентификатор договора, номер обращения. Захватывается со
страницы и переиспользуется в backend-проверке того же сценария.

Поэтому поле 9 заполняется даже при «ДА» в поле 8: два независимых способа связывания лучше одного,
и отчёт генерации обязан назвать, какой из них использован (BR-07).

## 6. Что считается закрытием гейта

Критерий приёмки — один, и он выполняется заполненным §3 по 2–3 приложениям. Дальше:

1. **Записать результат** в [`12-wave-plan.md`](12-wave-plan.md) §4 — строка `G-6` меняет «Ни один не
   закрыт» на дату и ссылку на ответ. Это `documentation_changes` карточки.
2. **Перевести `UITG-X006`** в `21-task-backlog.yaml` из `BLOCKED` в `DONE` с `status_reason`,
   называющим факт (кто ответил, когда, сколько приложений).
3. **Перевести из `BLOCKED` в `READY`** четыре карточки, чьё единственное предусловие — этот гейт:
   `X001`, `X007`, `X013` и — после `X010` — `X005`.

`definition_of_done` карточки сформулирован как проверка, а не как обещание: **«`X001` и `X005` могут
быть закрыты по каждому приложению»**. Если по какому-то приложению нельзя даже поставить вопрос ИБ
(поля 3 и 5 пусты) — гейт не закрыт, сколько бы строк ни было в списке.

## 8. Ответ владельца — 2026-08-09

Гейт закрыт. Ответ дал **Сотников Даниил** в сессии 2026-08-09, выступая владельцем приложения и
автоматизатором-владельцем набора одновременно. Записано дословно то, что отвечено; неотвеченное
названо неотвеченным.

### Приложение 1

```
  1. Алиас                              : taksa-portal
  2. Название и контур                  : Портал, контур DEV
  3. Владелец приложения                : Сотников Даниил
  4. Автоматизатор-владелец набора      : Сотников Даниил
  5. Второй фактор на входе             : нет
 5а. Вход через корпоративный SSO       : нет
  6. Выдаётся ли сессия заранее         : не требуется (вход формой)
  7. Роли, которые нужны сценариям      : client, operator, admin
  8. Корреляция                         : НЕ ЗНАЮ
  9. Экранный идентификатор             : НЕ ЗНАЮ — дополнено 2026-08-09
 10. Способ удаления тестовых данных    : НЕТ СПОСОБА — дополнено 2026-08-09
```

**Дополнение 2026-08-09.** Поля 9 и 10 доспрошены при закрытии `X007`. Поле 10 получило ответ
**«способа нет»** — валидное закрытие гейта (его критерий допускает «либо зафиксировано, что его
нет»), с последствием: остаточные данные объявляются в отчёте генерации, `BR-24` для приложения не
закрывается. Поле 9 осталось **«не знаю»**, и вместе с «не знаю» о корреляции это оставляет `RISK-14`
живым: при отсутствии И корреляции, И экранного идентификатора сквозной UI+backend сценарий для
приложения не строится вовсе. Отвечается взглядом на экран.

### Три оговорки, записанные явно

**Приложение одно, а BRD §14 просит 2–3.** Это осознанное отступление владельца, а не недосмотр:
волна 1 стартует одним приложением. Пересмотр — при добавлении второго.

**Поля 9 и 10 не отвечены, и это не мешает закрытию.** Оба кормят `X007` (способ удаления → `ADR002`),
а не `definition_of_done` этого гейта. **Но поле 9 становится обязательным именно из-за ответа на
поле 8:** при «НЕ ЗНАЮ» связывание UI↔backend идёт по захваченным с экрана данным, и если экранного
идентификатора тоже не окажется, сквозной сценарий для приложения не строится (§5, RISK-14). Этот
вопрос переходит в `X007` как первоочередной.

**Адрес стенда и учётные данные в репозиторий не записаны — намеренно.** Они прозвучали в сессии, но
конфигурация SDK принимает только имена переменных окружения, а литеральный адрес и пароль
отвергаются fail-closed. Конкретный стенд контура DEV задаётся **значением** `TAKSA_PORTAL_DEV_URL`,
которого в репозитории нет и не будет.

### Что из этого следует для реестра

Черновик записи (значения — на стенде, в файле только имена):

```yaml
ui-applications:
  taksa-portal:
    base-url-ref: TAKSA_PORTAL_DEV_URL
    auth:
      scheme: FORM
      credentials-pool-ref: TAKSA_PORTAL_TEST_USERS
      roles: [client, operator, admin]
      discovery-account-ref: TAKSA_PORTAL_DISCOVERY
      challenge: none
```

**`discovery-account-ref` обязан указывать на отдельную учётку без прав на необратимые операции** — не
на административную. Это `SEC-10` и предмет `X005`: на живом UI кнопку с необратимым действием нельзя
надёжно распознать до клика, поэтому ограничение прав учётки разведки — единственная машинно
гарантированная защита. Роль `admin` в пуле сценариев при этом допустима.
