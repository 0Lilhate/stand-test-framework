# 42. Пакет согласования ИБ: `X001`, `X004`, `S029` — одна встреча, три подписи

| | |
|---|---|
| **Документ** | Готовый к подписанию пакет по трём предметам ИБ волны 1 |
| **Кому** | Информационная безопасность |
| **Приложение волны** | `taksa-portal`, контур DEV (состав волны — [`40-g6-wave-composition-form.md`](40-g6-wave-composition-form.md) §8) |
| **Дата подготовки** | 2026-08-09 |
| **Статус** | **Гейты `X001`, `X004`, `S029` закрыты 2026-08-09** по заявлению владельца линии: ИБ пройдена, принята без вопросов. **Поля подписи ниже по-прежнему НЕ заполнены** — документ остаётся формой для оформления подписи к уже принятому решению, а не свидетельством о нём |

> **Зачем один документ на три гейта.** `X001` (G-1), `X004` (G-4) и `S029` (остаток `SEC-01`) идут к
> одной роли и содержательно связаны: у приложения нет второго фактора, поэтому разговор про доступ
> сводится к правам учёток, а он же — предмет `SEC-07`/`SEC-10` в §11. Три отдельных захода стоили бы
> трёх встреч и дали бы тот же результат.

> **Что этот документ НЕ делает.** Он не утверждает, что безопасность обеспечена. Он показывает, что
> закрывает машина, что остаётся людям, и где именно требуется решение ИБ. Из десяти требований §11
> полностью закрыто машиной **одно**; остальные — частично, и у каждого остаток назван.

## Предмет 1 — `X001` (G-1): второй фактор

**Что спрашивают.** Согласован ли обход MFA/OTP/КАПЧИ для тестовых учёток либо подтверждена
альтернатива — по каждому приложению волны.

**Факт, установленный владельцем приложения** ([`40-…`](40-g6-wave-composition-form.md) §8, поля 5 и
5а): у `taksa-portal` **второго фактора нет** — вход выполняется формой логин/пароль, корпоративный SSO
не используется.

**Что из этого следует.** Ослаблять нечего и согласовывать нечего. `definition_of_done` гейта
перечисляет три возможных статуса — «закрыт / обойдён `STORAGE_STATE` / приложение исключено», — и
применим первый.

**Почему всё же нужна подпись, а не устный ответ.** «Второго фактора нет» — утверждение о **чужой
системе**, которое может перестать быть верным без нашего ведома: включение MFA на стенде не обязано
нас уведомлять. Письменная фиксация даёт дату, от которой утверждение считается верным, и адресата,
которому обращаться, когда оно перестанет им быть.

**Что делает SDK, если второй фактор появится.** Ничего не обходит: приложение объявляет `challenge`,
UI-адаптер ищет `UiLoginChallengeHandler` и, не найдя, **отказывается до старта браузера** сообщением,
которое называет гейт G-1 и санкционированную альтернативу `STORAGE_STATE`. Байпаса второго фактора в
SDK нет и не планируется — обход, встроенный в тестовый SDK, был бы постоянным приглашением ослабить
настоящую защиту.

> **К подписанию.** Приложение `taksa-portal` (контур DEV) не использует второй фактор аутентификации:
> вход выполняется формой логин/пароль, корпоративный SSO не задействован. Обход второго фактора
> **не требуется и не запрашивается**.

## Предмет 2 — `X004` (G-4): согласование по §11

**Что спрашивают.** Протокол согласования по всем требованиям §11 BRD (`SEC-01`…`SEC-10`).

**Почему вопрос созрел именно сейчас.** Предусловие гейта — «механизм маскирования и срока жизни
артефактов предъявлен» — выполнено: маскирование (`S017`) и ретенция (`S018`) реализованы, и оба можно
посмотреть в работе.

### Состояние по §11 — не декларации, а состояния из матрицы прослеживаемости

| Требование | Состояние | Чем закрыто машиной | Что остаётся людям |
|---|---|---|---|
| `SEC-01` промышленный контур запрещён | частично | алиас обязан быть в whitelist реестра, отказ **до старта браузера**; литеральный URL в шаге невыразим; контур набора — enum `dev\|ift` | **предмет 3 этого документа** |
| `SEC-02` нет разрушающих действий при разведке | только документ | поведенческое правило кита | опирается на `SEC-10`: правами учётки, а не намерением |
| `SEC-03` только тестовые данные | частично | для БД write-guard и undo-log | у приложения волны **нет способа удаления** данных, созданных через UI (ответ на `X007`) — остаточные данные объявляются в отчёте генерации |
| `SEC-04` секреты только через `*-ref` | **реализовано полностью** | `literal://` отвергается fail-closed; `*-ref` обязан быть голым именем; детектор кита ловит пароль в фикстуре | — |
| `SEC-05` маскирование до снятия артефакта | частично | зоны закрашиваются **в DOM до** снятия скриншота; порядок закреплён тестом, падающим при перестановке | растровые ПД вне размеченных зон (OCR) — остаточный риск, принимается организационно |
| `SEC-06` гейт безопасности после генерации | частично | 26 детекторов, из них 6 UI-специфичных | девять гейтов остаются человеческими **по построению** |
| `SEC-07` техучётка с минимальными правами | внешнее | — | владельцы стендов; смыкается с `X005` |
| `SEC-08` синтетические ПД | частично | детектор ПД в фикстуре, работает и над прозой | **подтверждение ИБ — это и есть настоящий предмет G-4** |
| `SEC-09` срок жизни артефактов | частично | ретенция по настраиваемому сроку, 7 суток по умолчанию; `storage-state` не выметается — секрет живёт своим циклом | вычистка на стороне CI — `X003`/`S026` |
| `SEC-10` разведка без необратимых прав | частично | поле `discovery-account-ref` есть и обязательно | **выделение самой учётки — `X005`**; машинной проверки на стадии разведки нет и быть не может |

### Что можно показать вживую, если нужна не таблица, а доказательство

- [`34-allure-manual-run-report.md`](34-allure-manual-run-report.md) — ручной прогон: скриншот
  падения доходит до отчёта, чувствительная зона на нём **закрашена**;
- [`35-allure-trace-run-report.md`](35-allure-trace-run-report.md) — прогон с трейсом и разбор,
  **почему в ZIP нет DOM с введённым паролем**: запись трейса приостанавливается на время ввода
  учётных данных, потому что трейс сохраняет параметры действий, а параметр ввода — сам текст.

### Одно обстоятельство, которое стоит назвать первым, а не последним

Административная учётка, прозвучавшая при определении состава волны, **не может** быть учёткой
разведки. `SEC-10` требует у неё отсутствия прав на необратимые операции, потому что на живом UI
кнопку с необратимым действием **нельзя надёжно распознать до клика**. Это единственная машинно
гарантированная защита от `SEC-02`, и она обеспечивается правами, а не поведением агента.

> **К подписанию.** Состояние требований §11, изложенное выше, рассмотрено. Разведка живого UI и
> хранение артефактов прогона на условиях, описанных в `SEC-05`, `SEC-08`, `SEC-09`, —
> `согласовано / согласовано с замечаниями / не согласовано` (нужное подчеркнуть).

## Предмет 3 — `S029`: остаточный риск `SEC-01`

**Суть.** Адрес приложения приходит в SDK **именем переменной окружения**, а не значением. SDK
никогда не видит самого адреса и потому **не может машинно отличить DEV от промышленного контура**.

**Что при этом держится машиной, а не дисциплиной:**

- алиас, отсутствующий в `ui-applications`, отвергается **до старта браузера**
  (`NON_WHITELISTED_UI_APPLICATION`, пред-полётный валидатор);
- литеральный URL **невыразим** в шаге сценария — маршрутизировать себя куда-либо сценарий не может;
- контур в контракте эталонного набора — enum `dev | ift`, чья схема прямо говорит «Production is not
  expressible».

Достичь промышленного контура можно только направив туда переменную **уже разрешённого** алиаса —
намеренным действием того, кто настраивает стенд.

**Почему запретный список хостов рассмотрен и отвергнут.** Он ведётся руками, устаревает и потому даёт
**ложную уверенность** — состояние хуже честно названного предела. Вторая цена: он ломает работу на
стендах с нестандартными доменами, то есть требует собственного механизма исключений.

**Решение владельца линии 2026-08-09:** остаточный риск принят письменно; запись — в
[`stand-test-config/README.md`](../../../stand-test-config/README.md), раздел «The one thing this file
cannot check». `SEC-01` в матрице остаётся `PARTIALLY_IMPLEMENTED`: принятие риска не делает требование
реализованным.

> **К подписанию.** Остаточный риск `SEC-01` — невозможность машинно проверить, что резолвленный адрес
> приложения не принадлежит промышленному контуру, — **принят** при перечисленных выше компенсирующих
> контролях.
