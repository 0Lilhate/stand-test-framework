## Легенда статусов

| Статус | Значение |
|---|---|
| `SUPPORTED` | Работает как есть; для UI изменений в этом механизме не требуется |
| `PARTIALLY_SUPPORTED` | Механизм существует и переиспользуется, но требование покрывает не полностью |
| `NOT_SUPPORTED` | Механизма нет; строится с нуля |
| `ARCHITECTURAL_CONFLICT` | Требование сталкивается с существующим инвариантом или моделью; нужен выбор, а не дописывание |
| `EXTERNAL_DEPENDENCY` | Не закрывается кодом SDK ни при каком дизайне; требует решения или ресурса снаружи |

> Статус относится к **текущему состоянию репозитория**, а не к сложности реализации.
> `NOT_SUPPORTED` не значит «трудно» — значит «сейчас этого нет».

### BR-01 — кейс текстом/ТЗ/ФС → автотест без написания кода человеком

| | |
|---|---|
| **Статус** | `PARTIALLY_SUPPORTED` |
| **Существующие классы и файлы** | Пайплайн из 11 стадий: `docs/ai-agent/.claude/commands/stand-test-generate-java-test.md`; 17 скиллов в `docs/ai-agent/.claude/skills/`; вход ФС/PDF/DOCX — `stand-test-spec-ingestion` → `stand-test-kb-candidate-review` → `stand-test-kb-candidate-apply`. Эталонный набор: `docs/agent-evaluation/dataset/cases/` (**27 директорий**: 15 протокольных + 12 UI), контракт `docs/agent-evaluation/contracts/evaluation-case.schema.json` (`case.yml` + `input.md`), валидируется `EvaluationCaseSchemaValidationTest` |
| **Что уже верно** | Утверждение BRD «UI-кейсы добавляются как новые директории, отдельная инфраструктура не создаётся» **выполнено** (03.08.2026): двенадцать UI-кейсов — обычные директории того же набора, отдельной инфраструктуры не заведено. Оговорка к прежней формулировке: схема оказалась UI-агностичной не полностью — enum `category` закрыт, и восьми из двенадцати требуемых категорий в нём не было, поэтому контракт расширен **аддитивно** до версии 2 (пятнадцать прежних кейсов валидны без правок, что проверяет тест) |
| **Необходимое изменение** | (1) UI-ветка авторинга в пайплайне — **сделано**; (2) UI-кейсы в наборе — **сделано**; (3) `expected.retrieval` у UI-кейсов **не задаётся** (кроме `expectAbstention`/`expectConflict`): записей об экранах в KB нет (BR-08, бэклог S-5.3), и источником фактов о DOM служит подсаженный отчёт разведки внутри кейса. Осталось: браузерный дубль корпуса, иначе `execution.outcome` у всех двенадцати остаётся `NOT_RUN` |
| **Предполагаемый модуль** | `docs/ai-agent`, `docs/agent-evaluation/dataset` |
| **Риски** | RISK-03 (правдоподобный, но неверный тест). Скрытая связь: UI-кейс в наборе бессмыслен, пока нет KB-сущностей UI — BR-01 **блокируется BR-08** |
| **Требуемые тесты** | `EvaluationCaseSchemaValidationTest` должен принимать UI-кейсы **без правки схемы** — если правка потребуется, это регресс совместимости (BR-36); `EvaluationDatasetPatternsTest` расширить UI-инвариантами |

### BR-03 — подключение к живому UI по алиасу, наблюдаемое поведение как источник истины

| | |
|---|---|
| **Статус** | `NOT_SUPPORTED` + `EXTERNAL_DEPENDENCY` |

## 9.2 Полнота покрытия (часть, входящая в волну 1)

### BR-10 — позитивный сценарий: основной путь до подтверждения результата

| | |
|---|---|
| **Статус** | `NOT_SUPPORTED` |
| **Существующие классы и файлы** | Аналог для протокола реализован полностью: `RestStepExecutor`, `KafkaStepExecutor`, `DbStepExecutor`, `GrpcStepExecutor` + `stand-test-scenario-design`. Для UI — ни одного шага |
| **Необходимое изменение** | Минимальный набор шагов волны 1: открыть, кликнуть, заполнить форму, дождаться состояния, проверить, захватить значение. Каждый — `GenericStep` с `type="ui.*"` (§11.2 карты) |
| **Предполагаемый модуль** | `stand-test-ui` + `docs/ai-agent` |
| **Риски** | RISK-01 (хрупкие локаторы) — основной источник flaky на этом требовании |

### BR-11 — валидации форм: обязательные поля, границы, формат, тексты ошибок

### BR-21 — артефакты падения: скриншот, трейс/видео, консоль браузера, сетевые запросы

| | |
|---|---|
| **Статус** | `ARCHITECTURAL_CONFLICT` |
| **Существующие классы и файлы** | `core/event/Attachment.java` — `record Attachment(String name, String mediaType, String content)`; `StepResult`/`StepEvent` несут `List<Attachment>`; `AllureAttachmentPublisher` → `SecretMasker.maskText(...)` → `AllureLifecycleFacade.addAttachment(name, type, ext, String)`; `DefaultAllureLifecycleFacade:67`: `content.getBytes(StandardCharsets.UTF_8)`. `AttachmentType` знает `BINARY("application/octet-stream","bin")`, но контент всё равно строка |

| **Необходимое изменение** | Расширить модель вложений так, чтобы бинарь доходил до приёмника, **не ломая существующих потребителей** `Attachment`. Варианты (выбор — за техническим проектированием): (а) второе представление в `Attachment` (например, путь к файлу или `byte[]`) при сохранении текущего конструктора; (б) артефакт остаётся файлом на диске, вложение несёт ссылку, прикладывает приёмник |
| **Предполагаемый модуль** | `stand-test-core` (`core/event/Attachment.java`) + `stand-test-allure` + `stand-test-ui` |
| **Риски** | **Это изменение `stand-test-core`, не учтённое в §13.1 BRD** — там как правка core названа только «компенсации не-DB шагов» (D-9). Второй риск: маскирование. `SecretMasker` работает по тексту; бинарный скриншот он замаскировать не может — что и есть причина, по которой SEC-05 требует маскировать **до** снятия артефакта, в DOM |
| **Требуемые тесты** | Существующие текстовые вложения ведут себя без изменений (регресс `stand-test-allure`, 57 тестов); бинарное вложение доходит до Allure с корректным расширением; вложение с секретом в имени/пути не утекает |

### BR-23 — ожидания только через единый await; `Thread.sleep` отсекается гейтом

| **Требуемые тесты** | Два параллельных прогона не получают одну учётку; запрос роли возвращает учётку этой роли; исчерпание пула даёт `BROKEN` с внятным сообщением **в пределах таймаута**; учётка возвращается и на упавшем прогоне |

### BR-27 — логический алиас; произвольный URL запрещён

| | |
|---|---|
| **Статус** | `PARTIALLY_SUPPORTED` |
| **Существующие классы и файлы** | Механизм устроен **вычитанием, а не запретом**: у шагов нет параметра, куда положить URL — есть `service`/`topic`/`datasource`/`target` (алиасы) и относительный `path`. `ForbiddenOperation.HARDCODED_STAND_URL` в enum **есть, но рантайм-валидатор его никогда не испускает** (проверено grep по всем `src/main`). ## Сквозные наблюдения

Пять вещей, которые видны только на всей матрице целиком и ни в одном отдельном требовании.

1. **Правок `stand-test-core` в волне 1 больше, чем одна.** §13.1 BRD называет единственной правкой
   core «компенсации не-DB шагов» (D-9). Матрица даёт ещё три: ветка `ui.` в
   `DefaultScenarioValidator` (BR-27, SEC-01), константы в `ForbiddenOperation`/`StepParameterKeys`,
   и — самое существенное — расширение `Attachment` под бинарные артефакты (BR-21). При этом D-9 в
   своей формулировке (а) правки core **не требует**. Итоговый объём вмешательства в core примерно
   тот же, но статьи другие, и оценка §13.1 их не учитывает.

2. **Guardrail, который забыли включить, — самый дорогой класс дефекта в этом проекте.** Проверка
   алиасов в `DefaultScenarioValidator` диспетчеризуется по префиксу типа; ветки `ui.` нет, и без
   неё BR-27/SEC-01 будут «объявлены и не работать». Прецедент ровно такого дефекта закрыт
   последним коммитом ветки (`cf81358`, «guardrails that were declared and never ran»).
   Противоположный пример в том же коде — проверка таймаутов и заголовков: она работает по **имени
   ключа**, а не по префиксу типа, и потому распространится на UI бесплатно. Это готовый
   конструктивный урок: **guardrails, привязанные к ключу, переживают появление нового адаптера;
   привязанные к префиксу — нет.**

3. **NFR-05 сегодня не подкреплён проверкой в той части, которая для UI критична.** ArchUnit-тест
   стережёт рёбра между модулями SDK, но не внешние зависимости `core` и не состав полей
   `Scenario` — то есть ровно те два инварианта, которые называет NFR-05 и охраняет RISK-09
   («любое нарушение — блокирующий дефект сборки»). Оба правила стоит завести **до** начала работ
   над модулем, а не после: тогда первое же нарушение будет поймано сборкой, а не ревью.

4. **Порядок работ по версионированию важнее их объёма.** BR-36 (схемы KB) и BR-37/D-10 (реестр
   сред) страдают одной болезнью: версионирование вводится **одновременно** с ломающим
   расширением. В обоих случаях «старая версия отказывается внятно» недостижима задним числом. Если
   ключ версии не появится в релизе, предшествующем UI-расширению, требование будет формально
   выполнено и фактически бесполезно для уже выпущенных версий.

5. **Пять требований волны 1 не закрываются кодом ни при каком дизайне.** BR-29/BR-30 (IdP, MFA —
   G-1), BR-34/SEC-10 (пул учёток и учётка разведки — G-5), BR-18 (инфраструктура — G-3), BR-24 в
   части способа удаления (AS-05, OQ-06), BR-13 в части корреляции (G-6, DEP-08). Это не риски и не
   технический долг — это условия исполнимости, и BRD верно вынес их в гейты. Техническое
   проектирование можно начинать раньше их закрытия; **реализацию аутентификации — нет**.
