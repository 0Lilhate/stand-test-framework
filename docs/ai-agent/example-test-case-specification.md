## Кейс OP-310: Заявка с превышением лимита отклоняется и фиксируется в отчётной БД

**Стенд:** ift
**Системы:** клиентский сервис (alias: client-service), отчётная БД (alias: main-db, схема test_data)
**Пользователь:** тестовый (учётка из реестра стенда, отдельной роли не требуется)

### Предусловия

Нет — заявка создаётся самим тестом. Данные разных прогонов не должны конфликтовать
(уникальность обеспечить средствами теста).

### Основной сценарий (happy path)

1. Создать заявку: POST `/api/requests`, тело: `{ "amount": 100 }`.
   Ожидание: HTTP 200; в ответе поле `status` = `"ACCEPTED"` (точное значение);
   поле `requestId` присутствует и соответствует формату `r-<цифры>`.
2. Проверить фиксацию: в течение 30 секунд в таблице `test_data.orders` появляется строка,
   где `id` = `requestId` из шага 1, колонка `status` = `'NEW'` (точное значение).
3. Дождаться обработки: GET `/api/requests/{requestId}` — в течение 60 секунд (опрос не чаще
   чем раз в 500 мс) статус в ответе становится `"DONE"` (точное значение),
   поле `processedAt` заполнено (не null).

### Негативный сценарий

4. Создать заявку с превышением лимита: POST `/api/requests`, тело: `{ "amount": 1000000 }`.
   Ожидание: HTTP 200; `status` = `"REJECTED"` (точное значение);
   поле `rejectReason` = `"LIMIT_EXCEEDED"`.
   Проверка «строка в БД НЕ появилась» не требуется.

### Данные и очистка

Строки в `test_data.orders` создаёт приложение (ключ — `requestId`, сгенерированный сервером);
колонки `test_run_id` в таблице нет, очистка средствами теста невозможна — остаточные строки
допустимы (стенд чистится регламентно).

### Трассировка

Запрос и его следствия должны связываться сквозным correlation id (стандартный механизм SDK).
