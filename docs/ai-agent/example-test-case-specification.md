# Пример постановки тест-кейса для генерации автотеста AI-агентом

Эталонный входной документ для конвейера `/stand-test-design` → `/stand-test-java` →
`/stand-test-validate`: постановка написана так, что генерация проходит **без блокирующих
вопросов**. Все алиасы разрешаются в базе знаний этого репозитория
([`knowledge-base/services/showcase-mock.yml`](knowledge-base/services/showcase-mock.yml),
[`knowledge-base/endpoints/showcase-mock.yml`](knowledge-base/endpoints/showcase-mock.yml),
[`knowledge-base/environments/ift.yml`](knowledge-base/environments/ift.yml)), а ожидаемые
значения взяты с живого стенда, а не придуманы. Правила разбора входа — скилл
`stand-test-case-analysis`; требования к формулировкам (точные значения для Kafka/БД/gRPC,
SLA ожиданий, судьба данных) — там же.

> **Почему кейс именно такой.** Он намеренно ограничен тем, что KB реально покрывает: один
> сервис, REST, без корреляции и без БД. Постановка, требующая проверки в базе или события в
> Kafka, была бы для текущей KB *правильно* заблокирована — и как эталон «прохода без вопросов»
> не годилась бы. Хороший кейс не тот, который просит многого, а тот, чьи требования
> прослеживаются до контракта.

## Кейс SM-001: Неизвестный бизнес-код витрины отклоняется одинаково обоими способами запроса формата

**Стенд:** ift
**Система:** сервис витрин (alias: `showcase-mock`)
**Пользователь:** не требуется — сервис не объявляет аутентификации

### Предусловия

Нет. Кейс намеренно построен на **заведомо отсутствующем** бизнес-коде, поэтому не зависит ни от
каких данных стенда и не требует их подготовки. Код должен быть уникален для каждого прогона,
чтобы параллельные запуски не влияли друг на друга (средствами SDK).

### Основной сценарий

1. Запросить форматы списком: `POST /showcases/formats`, тело — массив из одного элемента
   `[{ "businessCode": "<уникальный код прогона>" }]`, поле `version` не передаётся.
   Ожидания: **HTTP 404**; в теле ответа
   - `status` = `404` (число, не строка),
   - `error` = `"NOT_FOUND"`,
   - `path` = `"/showcases/formats"` (точное значение — путь запроса, без кода),
   - `message` содержит `"Витрина не найдена"` и содержит запрошенный бизнес-код,
   - `details` = `null`.

### Второй сценарий (тот же контракт, другой способ вызова)

2. Запросить формат поштучно: `GET /showcases/formats/{code}` с тем же уникальным кодом,
   query-параметр `version` не передаётся.
   Ожидания: **HTTP 404**; тело той же формы, но
   - `path` = `"/showcases/formats/<запрошенный код>"` (путь включает код),
   - `message` содержит `"Витрина не найдена"`.

   Смысл проверки: оба входа обязаны давать одну и ту же структурированную ошибку. Расхождение
   между ними — регрессия контракта ошибок, а не деталь реализации.

### Что в кейс НЕ входит и почему

- **Позитивный путь** (запрос формата существующей витрины) — требует заранее заведённого на
  стенде бизнес-кода. Такой код не является ни константой, ни значением, которое тест может
  создать сам: в KB нет create-эндпоинта для витрин и нет датасорса с правом записи. Это честно
  блокирующая нехватка данных, поэтому она вынесена из эталона, а не замаскирована.
- **Проверка в БД и события Kafka** — у `showcase-mock` в KB нет ни датасорсов, ни топиков.

### Данные и очистка

Оба запроса read-only: ничего не создаётся и не изменяется. Очистка не требуется, остаточных
данных нет. Уникальность кода прогона нужна не для очистки, а для независимости параллельных
запусков.

### Тайминги

Асинхронных ожиданий нет — оба шага синхронные HTTP-вызовы, опрос и таймауты ожидания не нужны.
Отдельного SLA кейс не задаёт.

### Трассировка

Сквозной correlation id **не требуется и недоступен**: OpenAPI-контракт `showcase-mock` не
объявляет ни одного header-параметра, поэтому в KB у сервиса нет блока `correlation:`, а
`injectCorrelationId()` против него неприменим. Связь шагов обеспечивается тем, что оба
используют один и тот же код прогона.
