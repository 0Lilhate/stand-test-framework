# stand-test-ui

UI-адаптер SDK: браузерный шаг — это обычный шаг той же модели сценария. Пятый адаптер рядом с
`rest`/`kafka`/`db`/`grpc`, с той же грамматикой, тем же раннером, тем же механизмом ожидания и тем же
`VariableStore`.

**Playwright живёт только здесь** — в подпакете `ru.alfa.stand.test.ui.playwright`. Ни `stand-test-core`,
ни любой другой модуль его не видят: потребитель, подключивший только `stand-test-rest`, браузер не
получает даже транзитивно. Изоляция держится на структуре модулей: правила ArchUnit, которые её
проверяли (`coreHasNoUiOrIoDependencies`, `playwrightIsConfinedToDriverPackage`, `nothingDependsOnUi`),
жили в удалённом модуле `stand-test-example`, поэтому сейчас нарушение сборка не поймает.

Реализованный срез соответствует ADR-UI-001 (границы модуля), ADR-UI-002 (жизненный цикл, вариант А —
браузер на прогон) и ADR-UI-003 (публичный API).

## Что умеет (волна 1, минимальный вертикальный срез)

| Тип шага | Действие | Ожидание | Проверки | Захват |
|---|---|---|---|---|
| `ui.open` | навигация по **относительному** пути | таймаут навигации | нет | нет |
| `ui.click` | клик | actionability Playwright, ограниченная таймаутом действия | нет | нет |
| `ui.fill` | ввод (с резолвом `${var}`) | то же | нет | нет |
| `ui.expect` | нет | нет | обязательны | да |
| `ui.expectEventually` | нет | `Awaiter` SDK, обязательный ограниченный таймаут | обязательны | да |
| `ui.login` | вход техучёткой из пула по роли | два ограниченных ожидания: свободной учётки и самого входа | нет | нет |

```java
public final class NewApplicationPage {

    private static final String APP = "client-portal";

    private static final UiLocator AMOUNT = UiLocator.label("Сумма");
    private static final UiLocator SUBMIT = UiLocator.role("button", "Подтвердить");
    private static final UiLocator STATUS = UiLocator.testId("application-status");
    private static final UiLocator NUMBER = UiLocator.testId("application-number");

    public static ScenarioStep open() {
        return UiStep.open(APP, "/applications/new").id("open-form").injectCorrelationId().build();
    }

    public static ScenarioStep awaitAccepted() {
        return UiStep.expectEventually(APP, STATUS)
                .id("await-accepted")
                .assertVisible()
                .assertText("Принята")
                .capture("applicationNumber", NUMBER)
                .withinSeconds(20)
                .build();
    }
}
```

Захваченное значение доступно любому следующему шагу любого адаптера как `${applicationNumber}` —
это и есть связывание UI с бэкендом, и оно не потребовало ни строки нового кода в ядре.

## Публичный API

| Тип | Зачем публичен |
|---|---|
| `UiStep` | единственная точка входа автора теста; аналог `RestStep` |
| `UiLocator`, `LocatorStrategy` | живут константами в Page Object потребителя; без публичности локаторы утекут в тело теста |
| `UiLocator.asSensitive()` | разметка поля с секретом/ПД: его значение не попадает ни в сообщение об отказе, ни в диагностику ожидания |
| `UiProperty`, `UiCaptureSource` | появляются в сигнатурах `assertProperty(...)`/`capture(...)` |
| `UiAssertion`, `UiCapture`, `UiStepParameters` | контракт параметров шага для декларативного трека и для разбора чужого `GenericStep` |
| `UiDriver`, `UiDriverFactory`, `ElementSnapshot`, `UiElementNotActionableException` | шов подмены браузера: unit-тесты без Chromium — и нам, и потребителю (аналог публичного `HttpCaller`) |
| `UiApplicationResolver`, `ResolvedUiApplication`, `EnvironmentUiApplicationResolver` | шов к реестру окружений (аналог `BaseUrlResolver`) |
| `UiRunSettings` | headed/headless, браузер, таймауты — конфигурация прогона |

**Не публичны:** `UiSession`, `UiAssertionEvaluator`, весь пакет `…ui.playwright`. `UiStepExecutor`
объявлен `public` только по требованию `ServiceLoader` и в поддерживаемую поверхность не входит.

**Чувствительные поля.** `UiLocator.label("Пароль").asSensitive()` — и при провалившейся проверке в
отчёт уйдёт `LABEL(Пароль): expected VALUE EQUALS <masked> but got <masked>`: ни ожидаемого, ни
введённого значения. Всё остальное (какой элемент, какое свойство, какой матчер) остаётся, поэтому
сообщение по-прежнему пригодно для разбора. Метод назван `asSensitive()`, а не `sensitive()`, потому
что компонент записи уже даёт предикат `sensitive()` — симметрично `fragile()`.

**XPath отсутствует намеренно** — нет фабрики, нет константы стратегии. Тот же приём, которым в SDK
запрещён литеральный URL: некуда положить. `UiLocator.fragile()` — единое определение хрупкости
(`false` только для `TEST_ID`).

## Матчеры: объявленная асимметрия

| Свойство | Тип | Допустимые матчеры |
|---|---|---|
| `TEXT`, `VALUE`, `ATTRIBUTE` | строка | EQUALS, CONTAINS, MATCHES, EXISTS, NOT_NULL |
| `VISIBLE`, `ENABLED` | булево | **только EQUALS** |

Ограничение проверяется при сборке шага (`build()`), а не в рантайме. Сравнение целиком делегировано
в `AssertionMatchers` ядра — собственного эвалюатора у адаптера нет, поэтому пять адаптеров не могут
разъехаться в семантике равенства.

## Владение ресурсами

| Объект | Область жизни | Кто закрывает |
|---|---|---|
| `Playwright`, `Browser` | прогон (вариант А ADR-UI-002) | вместе с драйвером |
| `BrowserContext`, `Page` | прогон | `ResourceScope` раннера, ключ `ui.session:<alias>` |

Сессия открывается **лениво**, на первом реально исполняемом UI-шаге (`prepare` — no-op), и
переиспользуется остальными шагами прогона. Она не может лежать в поле `UiStepExecutor`: executor —
синглтон на JVM, разделяемый параллельными прогонами. Изоляцию даёт **контекст**: свои куки, storage,
кэш; браузерный тест `parallelRunsDoNotShareCookies` это проверяет. Закрытие идёт в `finally` раннера
на любом исходе, и отказ закрытия не превращает зелёный прогон в красный.

## Классификация отказа

| Что произошло | Что бросается | Как видно в отчёте |
|---|---|---|
| проверка не выполнилась (текст, видимость, доступность) | `StandTestAssertionError` | FAILED |
| элемент не стал actionable за таймаут действия | `UiElementNotActionableException` → `StandTestAssertionError` | FAILED |
| `expectEventually` не дождался | `StandTestAssertionError` с диагностикой ожидания | FAILED |
| захват из отсутствующего элемента | `StandTestAssertionError` | FAILED |
| локатор совпал с несколькими элементами | `StandTestException` с именем локатора и числом совпадений | BROKEN |
| браузер не стартовал, страница не загрузилась, алиас не в реестре, неизвестная ошибка драйвера | `StandTestException` | BROKEN |

Граница проведена в одном месте (`UiStepExecutor.driverCall`). Инфраструктурный отказ, записанный как
FAILED, отравляет измерение flaky rate — поэтому это контракт, а не деталь.

## Артефакты падения: скриншот на отказе

Упавший UI-шаг оставляет в каталоге артефактов прогона снятый в момент отказа PNG и прикладывает его к
отчёту **того же, упавшего шага**; зелёный шаг не снимает ничего (UITG-S013).

- **Только на ветке отказа и только если сессия открыта.** Шаг, упавший до появления браузера
  (неизвестный алиас, сломанный параметр, иностранный шаг) — скриншотить нечего: драйвера нет.
- **Доставка — общий канал, не самопал.** Executor создаёт файловый `Attachment` (`image/png`) и
  несёт его вместе с исключением через `FailureAttachments`; `DefaultScenarioRunner` вкладывает его в
  `StepEvent` именно того шага, который упал. Файл ложится в `<stand.test.ui.artifacts.dir>` и живёт
  под правилами каталога артефактов (SEC-09); путь внутри каталога прогона проверяет приёмник.
- **Best-effort (план §17).** Браузер уже закрыт, каталог не создаётся, скриншот сорвался — это WARN
  и прогон без картинки. Срыв снятия артефакта **не подменяет** исходный отказ шага и не превращает
  снятие в причину красного результата.
- **Чувствительные зоны закрываются ДО снятия (SEC-05, UITG-S017).** Элементы, помеченные
  `UiLocator.asSensitive()`, закрашиваются поверх непрозрачным блоком до того, как сделан скриншот, так
  что введённый пароль не попадает на артефакт. Зоны упавшего шага — это его собственный локатор и его
  capture-локаторы, помеченные `sensitive`, плюс поля формы логина (`ui.login`): форма видит пароль в
  строке, а отчёт — нет. Порядок «заклеить → снять» и ветка «маскирование упало → артефакт не
  снимается вовсе» закреплены тестами (секьюрити-контракт: отсутствие скриншота безопаснее скриншота с
  секретом); число закрытых зон попадает в диагностику прогона (`ui.masked.zones`). Маска живёт ровно на
  тот артефакт, ради которого была запрошена: последующий снимок того же драйвера не наследует её — это
  защищает будущий `S016` (несколько артефактов подряд) от чужой маски (UITG-T005).

### Трейс: тяжёлый артефакт, выключенный по умолчанию (UITG-S016)

Помимо скриншота упавший шаг может оставить **Playwright-трейс** (ZIP, открывается [Trace Viewer’ом](https://playwright.dev/java/docs/trace-viewer)) —
но только там, где приложение в реестре объявило `trace: on-failure`. Это самый тяжёлый из артефактов,
поэтому он **по умолчанию выключен**: пока в `ui-applications.<alias>.trace` не стоит `on-failure`,
`tracing().start()` не запускается и оверхед прогона нулевой. Видео в этом срезе **не снимается вообще**.

- **Флаг — это свойство реестра, не сценария.** Сценарий не выражает адрес, вьюпорт или браузер; точно
  так же он не выбирает, снимать ли трейс. Решение принимает владелец приложения в одном месте.
- **Порядок «заклеить → снять» (SEC-05, UITG-S017) соблюдается.** Трейс снимается строго после того, как
  чувствительные зоны упавшего шага замаскированы (для скриншота): тест порядка «маскирование → скриншот →
  трейс» это закрепляет. У трейса выключены и скриншоты, и снапшоты (`screenshots: false`,
  `snapshots: false`), поэтому ни кадр экрана, ни DOM-клон кадра в ZIP не попадают.
- **Что в трейсе есть и чего в нём нет — замерено, а не предположено (UITG-F004).** Есть: лента действий,
  их call log и консоль страницы. **Нет: вкладка Network — она пустая**, потому что сетевые записи живут в
  том же снапшот-потоке, который выключен ради SEC-05. То есть **трейс не является сетевым артефактом**:
  сетевую историю упавшего шага несёт текстовое вложение `ui-network` (UITG-S015), и потому эти два
  артефакта не дублируют друг друга. Закреплено браузерным тестом
  `exportedTraceCarriesNoDomCloneAndNoNetworkStory`: включение `snapshots: true` роняет его (и заодно
  тест секрета — в DOM-клоне оказывается введённый пароль).
- **Вход в трейс не попадает — и это не украшение, а SEC-05.** Трейс пишет не только экран, но и
  **параметры действий**, а параметр `fill` — это введённое значение. Пока запись не разрывалась, прогон с
  `trace: on-failure` запечатывал пароль техучётки в `trace.trace` внутри ZIP, который потом уезжает в
  отчёт; ни `asSensitive()` (он про маску скриншота), ни `UiSecrets` (он про текст исключения), ни маскер
  отчёта (он про текстовый канал, а ZIP — файловый) туда не дотягиваются. Поэтому `ui.login` берёт свои
  `fill` в скобки `suspendTracing()`/`resumeTracing()`: пока набираются креденшелы, не открыт ни один
  чанк записи. **Цена, которую надо знать:** вместе с логином отбрасывается и то, что записано до него —
  в UI-ветке вход стоит первым шагом, так что теряется навигация на форму входа, а прогон после входа
  сохраняется целиком. Закреплено браузерным тестом, который проверяет обе половины: секрета в ZIP нет,
  и работа после входа в ZIP есть (пустой трейс — не починка).
- **Если запись не удалось разорвать — трейс не выгружается вовсе.** Fail-closed: потерянный трейс стоит
  одной отладочной сессии, утёкший пароль — ротации учётки.
- **Best-effort, как и скриншот.** Сорвавшийся трейс — WARN, и исходный отказ шага не подменяется.
  ZIP живёт под правилами срока жизни артефактов (SEC-09, `UITG-S018`).

### Консоль браузера: текстовое вложение на отказе (UITG-S014)

Третий артефакт падения — **логи консоли**, собранные с момента открытия страницы. Фронтенд-ошибка часто
заявляет о себе в консоли раньше, чем что-то ломается на экране, поэтому упавший шаг прикладывает то, что
страница логгировала. В отличие от скриншота и трейса это **текстовый** канал: упавший шаг несёт
`Attachment("ui-console", "text/plain", …)`, и текстовая ветка отчёта проходит маскер секретов (`SEC-05`) —
секрет, который страница случайно залогировала, маскируется так же, как краснеет текст исключения.

- **Собираются все уровни** — `error`, `warn` и остальные — в порядке появления, пока страница открыта.
  Драйвер регистрирует слушатель консоли в момент создания страницы, и executor читает его на ветке отказа.
- **Лог ограничен, и обрезка не молчит.** Хранятся последние **1000** записей, одна запись — не длиннее
  **1000** символов; страница, логгирующая в цикле отрисовки, иначе решала бы за прогон, сколько он держит
  памяти и какого размера вложение получит ревьюер. Если что-то отброшено, лог **первой же строкой**
  говорит сколько, а обрезанная запись говорит это в своём конце: читатель обязан отличать полный лог от
  хвоста. Остаются **новейшие** записи — отказ объясняет то, что случилось прямо перед ним.
- **Пустая консоль → вложение не прикладывается.** «Сообщений нет» — честный «логгировать нечего», а
  не пустой блок в отчёте. Драйвер возвращает пустой список вместо `null`, и executor просто пропускает
  вложение, когда нечего приложить.
- **Best-effort, как и остальные артефакты.** Лог, который не удалось прочитать, — WARN; исходный отказ
  шага не подменяется.

### Сетевые запросы: метод/путь/статус как текстовое вложение (UITG-S015)

Четвёртый артефакт падения — **сетевые запросы страницы**, собранные с момента открытия страницы. Первое,
что надо понять по красному UI-шагу, — дошёл ли запрос до backend и с каким кодом, и упавший шаг прикладывает
метод, путь и статус каждого обмена. Как и консоль, это **текстовый** канал: упавший шаг несёт
`Attachment("ui-network", "text/plain", …)`, и текстовая ветка отчёта проходит маскер секретов (`SEC-05`).

- **Только наблюдение, без перехвата.** Драйвер слушает `page.onResponse` и записывает `METHOD путь статус`;
  никакого `route`/intercept — подмена ответов вне области волны 1 (BR-33). Запись начинается с момента
  создания страницы, executor читает её на ветке отказа.
- **Одни method/path/status.** Тела запросов и ответов **не сохраняются вовсе** (`neg` из карточки):
  тело может нести ПД, поэтому красный прогон честно показывает «дошёл и получил 500», не копируя, что
  ушло/пришло. Из URL выброшен query- и fragment-суффикс — там может быть одноразовый токен.
- **Credential-заголовки не попадают в запись.** `Authorization` и `Cookie` маскируются на драйвере до
  записи — имя и значение не достигают отчёта даже до маскера (SEC-05).
- **Пустой список → вложение не прикладывается.** Страница без запросов — честный «запросов не было», а
  не пустой блок; драйвер возвращает пустой список вместо `null`.
- **Best-effort, как и остальные артефакты.** Сеть, которую не удалось прочитать, — WARN; исходный отказ
  шага не подменяется.
- **Тот же ограничитель, что у консоли.** Последние **1000** обменов, запись — не длиннее **1000**
  символов; отброшенное объявляется первой строкой лога. Страница, опрашивающая эндпоинт каждые сто
  миллисекунд, — обычный фронтенд, а не патология, и вложение не должно расти вместе с ней.

### Срок жизни артефактов (UITG-S018, SEC-09)

Артефакты падения не копятся на раннере и на машине инженера: **первый прогон, который реально открыл
браузер, выметает** из каталога артефактов всё, что старше настраиваемого срока хранения. Одной строкой —
свой `stand.test.ui.artifacts.retention.days` (дней, по умолчанию `7`, «не дольше срока хранения отчётов CI»).

- **Только файлы, только по времени.** Сметаются обычные файлы, чья `last-modified` старше среза; структура
  из вложенных артефактов (сейчас их нет — скриншот и трейс ложатся прямо в корень) остаётся на будущее и
  ничего не требует.
- **`storage-state` выметанию не подчиняется.** Каталог `storage-state` — это живые сессии (секрет SEC-05),
  у них свой жизненный цикл, и ретенция артефактов до них не дотрагивается, сколько бы ни лежал файл —
  это проверено тестом, а не обещанием.
- **Best-effort, как снятие.** Каталога нет, файл не читается, удаление сорвалось — это WARN; прогон,
  который не смог вычистить свою историю, обязан **стартовать, а не падать**. Ошибка ретенции никогда не
  подменяет исходный отказ шага и не красит зелёный прогон в красный.
- **Один прогон за JVM.** Executor — синглтон на JVM, каталог общий для всех прогонов процесса, поэтому
  выметание выполняется один раз — первым открывшим сессию — и не сканирует историю параллельному прогону.
- **Ретенция на стороне CI — за скобками.** Хранение и вычистка отчётов самого CI (`X003`) — конфигурация
  раннера, не этого модуля.

Реализовано по [ADR-UI-006](../docs/ui-test-generation/adr/ADR-UI-006-authentication-and-account-pool.md).

```java
UiStep.login("client-portal").id("login").role("client").withinSeconds(20).build();
```

**Вход — отдельный шаг, а не побочный эффект открытия сессии.** У него свой номер и свой слой в отчёте
(`Step [1/6] 'login' (ui.login)`), своя классификация отказа и своя длительность. Ставить его нужно
**до** первого `ui.open` того же приложения: сохранённую сессию можно подставить только в момент
создания браузерного контекста, поэтому поздний `ui.login` не переиспользует её — и говорит об этом,
а не молча уходит на долгий путь.

### Три ожидания шага и их бюджеты

| Ожидание | Чем ограничено | Умолчание |
|---|---|---|
| свободной учётки в пуле | `accountTimeout(...)` | 60 с |
| «жива ли восстановленная сессия» | **таймаутом действия** (`stand.test.ui.action.timeout.millis`), но не больше `within(...)` | 10 с |
| самого входа: форма и появление `signed-in-locator` | `within(...)` | 30 с |

Бюджеты **раздельные, а не общие**, и это осознанно: проверка живости сессии — ожидание масштаба
действия, а не бизнес-ожидание. Если бы она тратила бюджет входа, то протухшая сессия съедала бы его
целиком и на повторный вход формой не оставалось бы ничего — то есть механизм, ради которого
`STORAGE_STATE` и существует, ломался бы ровно в том случае, для которого он написан. Практическое
следствие: худший случай шага — сумма трёх ограниченных ожиданий, а не `within(...)`.

### Схемы входа

| Схема | Что делает |
|---|---|
| `NONE` | приложение без входа; `ui.login` на нём — ошибка конфигурации |
| `FORM` | заполняет форму логина **каждый раз**; на диске ничего не остаётся |
| `STORAGE_STATE` | восстанавливает сохранённую сессию учётки, проверяет её живость и только при провале входит формой (если она объявлена) и пересохраняет состояние |
| `SSO` | значение реестра есть, реализации нет — говорящий отказ (волна 2, после G-1) |

`STORAGE_STATE` — это путь для приложений, где форма недоступна автоматизации: сессию готовит человек
или внешний процесс один раз, SDK её только использует. Приложение с `STORAGE_STATE`, объявившее и
локаторы формы, само себя загружает: первый прогон входит формой и сохраняет сессию, последующие
переиспользуют её.

### Пул учёток

`credentials-pool-ref` указывает на переменную окружения, содержащую **реестр учёток** — не учётку:

```
CLIENT_PORTAL_TEST_USERS="portal-client-1:client;portal-client-2:client;portal-manager-1:manager"
```

Запись — это `<id>:<роль>` (имена переменных с учётными данными выводятся из id: `PORTAL_CLIENT_1_USERNAME`
/ `PORTAL_CLIENT_1_PASSWORD`) либо `<id>:<роль>:<переменная-логина>:<переменная-пароля>`. Плейсхолдеры
`${VAR}` в реестре не принимаются: поля разделяет `:`, и значение по умолчанию сделало бы запись
неоднозначной. **На обоих уровнях только имена — ни логина, ни пароля.**

#### Одна учётка: пара вместо реестра (version 4; value-твин с версии 5)

Реестр оправдан там, где учёток несколько. Приложение с одной называет её прямо, и пара **исключает**
`credentials-pool-ref`:

```yaml
auth:
  scheme: STORAGE_STATE
  credentials-username: CLIENT_PORTAL_USERNAME   # ИМЯ переменной окружения
  credentials-password: CLIENT_PORTAL_PASSWORD
  roles: [admin, operator]                       # пара отвечает на ЛЮБУЮ объявленную роль
```

Три следствия, которые видно не сразу:

- **пара покрывает все объявленные роли** — выбирать не из чего, поэтому `role("admin")` и
  `role("operator")` получают одну и ту же учётку; роль, которой в `roles` нет, по-прежнему отвергается;
- **у каждой роли свой `accountId`** (`<алиас>-<роль>`), а значит и свой файл сессии, — иначе прогон,
  держащий пару как `admin`, блокировал бы её же как `operator`;
- **параллельность такого приложения равна 1 на роль**: второй прогон встаёт в очередь, а не падает.

**Написание зависит от версии формата, и это единственное место реестра, где значение КЛЮЧА
менялось, а не добавлялось.**

- **Версия 4:** оба поля — ссылки, голое слово это имя переменной. Спеллинг `${web_username:tks_Admin}`
  работает только на ФАЙЛОВОМ фронтенде, где плейсхолдер резолвит сам SDK; на Spring-стартере Spring
  раскрывает его раньше, SDK получает `tks_Admin` и ищет переменную с таким именем — отсюда отказ
  «variable 'tks_Admin' is not set», выглядящий как ошибка конфигурации, а не как несовместимость.
- **С версии 5:** пара стала value-твином, как `base-url` и всё остальное в реестре, а ссылка переехала
  в `credentials-username-ref` / `credentials-password-ref`. Тогда `${web_username:tks_Admin}` работает
  ОДИНАКОВО на обоих фронтендах: значение — значит значение.

```yaml
version: 5
...
auth:
  scheme: STORAGE_STATE
  credentials-username: ${web_username:tks_Admin}   # ЗНАЧЕНИЕ (Spring раскроет плейсхолдер)
  credentials-password-ref: CLIENT_PORTAL_PASSWORD  # ССЫЛКА: секрет не идёт через Spring Environment
  roles: [admin]
```

Почему перевернули ключ, а не завели третий: на стартере значение и имя переменной приходят
неразличимыми строками, поэтому два смысла не помещаются в один ключ — а конвенция реестра уже говорит,
какой из них чей. Документ, объявивший версию 4, сохраняет прежний смысл навсегда; документ версии 5,
у которого в поле-значении лежит нечто вида `TAKSA_ADMIN_USERNAME`, **отвергается** с указанием на
`*-ref`, потому что войти под литералом «имя переменной» — единственная ошибка, которую этот переворот
мог бы вызвать молча.

**Цена value-твина названа там, где её платят:** значение живёт в Spring Environment всё время жизни
контекста (actuator `/env`, дамп кучи, отчёт о контексте), а дефолт, записанный в файл, остаётся в
истории git и после ротации. Для ПАРОЛЯ это настоящая экспозиция, и `*-ref` остаётся правильным
написанием; для логина обычно приемлемо. SDK даёт оба и не решает за потребителя — но гейт
безопасности кита решает: пароль-значением в документе реестра он объявляет блокирующей находкой.

Это второе осознанное ослабление `ADR-UI-006 §5` (первым была сама пара в версии 4): до неё значение
учётных данных было невыразимо в реестре вовсе.

| Свойство | Значение |
|---|---|
| Выдача | по роли; при объявленных `roles` шаг **обязан** назвать одну — «любая учётка» невыразима |
| Эксклюзивность | пока аренда открыта, ту же учётку не получит никто; это и есть изоляция параллельных прогонов |
| Возврат | через `ResourceScope` раннера, в `finally` — на зелёном, на красном и на упавшем прогоне |
| Ожидание | ограничено `accountTimeout(...)`, умолчание 60 с, потолок — общий `MAX_TIMEOUT_MILLIS` |
| Исчерпание | `StandTestException` (BROKEN) с приложением, ролью, размером пула и таймаутом |
| Роль вне пула | отказ **сразу**, без сжигания таймаута: это ошибка конфигурации, а не борьба за ресурс |
| Область | пул — один на JVM, на пару (среда, приложение, реестр); иначе обещание эксклюзивности пустое |

Потолок параллельности набора равен размеру пула. Это параметр, который SDK не контролирует;
диагностика `ui.account.waitMillis` в `StepResult` показывает, стал ли пул узким местом.

`discovery-account-ref` — учётка разведки, **вне** пула (SEC-10). Конфигурация, в которой она же
лежит в рабочем пуле, отвергается при чтении реестра.

### Сессия браузера

Состояние сессии хранится **по учётке, а не по набору**:

```
<stand.test.ui.artifacts.dir>/storage-state/<environment>/<application>/<accountId>.json
```

Среда входит в путь потому, что по ней же ключуется пул: один и тот же `accountId` в `ift` и в `dev` —
две независимо арендуемые учётки на двух стендах, и общий файл сессии означал бы, что прогон на DEV
восстанавливает куку IFT.

Два прогона с разными учётками читают и пишут разные файлы и сессий друг друга не видят — иначе
переиспользование сессии противоречило бы изоляции прогонов (BR-29). Файл содержит живые куки, то
есть **фактически секрет**: он никогда не прикладывается к отчёту, не логируется и не печатается; в
диагностику попадает только путь. Файл, который не читается, пуст или не является JSON-объектом,
удаляется и считается отсутствующим — кэш не должен стоить прогона. Проверить содержимое глубже
модуль не может (JSON-парсера у него нет, а единственная библиотека, которая умеет, заперта в пакете
драйвера), поэтому последнее слово за браузером: файл, который тот отверг при создании контекста,
тоже удаляется, и прогон входит формой — иначе одна недописанная сессия ломала бы все последующие
прогоны этой учётки одинаково, пока файл не удалят руками. Протухшая, но корректная сессия
обнаруживается проверкой `signed-in-locator` и приводит к повторному входу формой либо, если формы
нет, к говорящему `BROKEN` с путём, куда положить подготовленную сессию.

### MFA / OTP / КАПЧА — гейт G-1, а не фича

Универсального обхода второго фактора в SDK **нет и не будет**: можно ли и как ослаблять второй фактор
для техучёток — организационное решение владельцев фактора, а обход, встроенный в тестовый SDK, был бы
постоянным приглашением ослабить настоящий. Приложение объявляет препятствие (`challenge: mfa | otp |
captcha`), и дальше есть два пути:

- реализовать `UiLoginChallengeHandler` и зарегистрировать его в
  `META-INF/services/ru.alfa.stand.test.ui.UiLoginChallengeHandler` на тестовом classpath — обработчик
  получает браузер, роль и id учётки, **но не учётные данные**, и обязан уложиться в остаток таймаута
  шага;
- перевести приложение на `STORAGE_STATE` и готовить сессию вне SDK.

Если ни того, ни другого нет, `ui.login` отказывается **до** резолва учётных данных, называя гейт и
альтернативу, вместо того чтобы заполнить форму и упереться в экран, который всё равно не пройти.

### Секреты

| Место | Что видно |
|---|---|
| Реестр сред | имя переменной с реестром учёток |
| Реестр учёток | id, роли, имена переменных |
| Лог | приложение, роль, id учётки |
| Диагностика шага | схема, роль, id учётки, ожидание аренды, путь к файлу сессии |
| Сообщение об отказе входа | id учётки и **имена** переменных с учётными данными |

Локаторы полей логина и пароля помечаются `sensitive()` автоматически. Отдельно закрыт случай, который
разметкой не закрывается: если сам драйвер браузера вернёт ошибку, содержащую введённое значение, это
исключение **не пробрасывается и не прикрепляется причиной** — вместо него поднимается санированное
`StandTestException`, называющее действие и тип исходной ошибки. Потерянный стек стоит одного разбора,
утёкший пароль — ротации.

Поле реестра `password-locator` — единственное место, куда пароль можно вписать по невнимательности,
поэтому core требует у локаторов префикс `<стратегия>=`: голый пароль не проходит проверку формы при
чтении реестра. Отвергнутое значение **никогда не печатается** в сообщении — оно могло быть секретом.

### Отказ входа: что чем является

| Что произошло | Классификация |
|---|---|
| учётные данные отвергнуты (не появился `signed-in-locator`) | `StandTestAssertionError` → FAILED |
| пул исчерпан за отведённое время | `StandTestException` → BROKEN |
| роль не объявлена / не названа | отказ **валидатора до прогона** (`UI_LOGIN_ROLE_UNKNOWN` / `UI_LOGIN_ROLE_REQUIRED`) |
| переменная с учётными данными не задана | `StandTestException` → BROKEN, с именем переменной |
| объявлен challenge, обработчика нет | `StandTestException` → BROKEN, с гейтом G-1 |
| схема `SSO` | `StandTestException` → BROKEN, «не реализовано в этой версии» |
| протухшая сессия, формы нет | `StandTestException` → BROKEN, с путём к файлу сессии |

## Конфигурация

| Системное свойство | Умолчание | Что делает |
|---|---|---|
| `stand.test.ui.headless` | `true` | headless (CI) / headed (локальная отладка) |
| `stand.test.ui.browser` | `chromium` | `chromium` \| `firefox` \| `webkit` |
| `stand.test.ui.action.timeout.millis` | `10000` | предел одного клика/ввода |
| `stand.test.ui.navigation.timeout.millis` | `30000` | предел одной навигации |
| `stand.test.ui.artifacts.dir` | `build/stand-test-ui` | каталог артефактов прогона; там же лежат сохранённые сессии браузера (SEC-09) |
| `stand.test.ui.artifacts.retention.days` | `7` | срок жизни артефактов падения (SEC-09); `storage-state` не выметается |

`injectCorrelationId()` добавляет SDK-овый correlationId заголовком `X-Correlation-Id` ко всем
запросам страницы (у UI-приложения в реестре пока нет своей секции `correlation`, поэтому имя
заголовка — константа модуля). Флаг применяется на **каждом** шаге, который его просит, а не только на
том, который открыл сессию.

Вьюпорт берётся из профиля реестра (`ui-applications.<alias>.default-viewport`). **В `Scenario` не
появилось ни одного UI-поля** — это проверяется тестом `scenarioHasNoUiFields`.

## Тесты модуля

```bash
./gradlew :stand-test-ui:test                        # браузер не нужен
./gradlew :stand-test-ui:installPlaywrightBrowsers   # один раз: скачать Chromium
./gradlew :stand-test-ui:browserTest                 # против настоящего Chromium
./gradlew :stand-test-ui:browserTest -Dstand.test.ui.headless=false   # посмотреть глазами
./gradlew :stand-test-ui:browserTest -Pstand.test.ui.browser.parallelism=4   # если машина позволяет
```

Оба набора идут **параллельно по классам** (см. [Параллельность набора](#параллельность-набора)).

`test` и `browserTest` разделены намеренно: `test` обязан проходить там, где браузера нет, а тест с
тегом `browser`, который «зеленеет» из-за отсутствия браузера, был бы хуже отсутствующего. Поэтому
`browserTest` **не** входит в `check`, а пакет `…ui.playwright` исключён из порога покрытия JaCoCo
(его покрывает именно `browserTest`).

> Это утверждение до 2026-08-02 было **неверным**, хотя и записанным: корневой `subprojects` вешает
> JaCoCo-задачи на `dependsOn(tasks.withType<Test>())`, а `check` — на JaCoCo-верификацию, и
> `withType<Test>()` захватывал `browserTest`. То есть `./gradlew build` требовал браузер — молча
> проходя на машине, где Chromium установлен, и падая ровно на том CI-образе, ради которого разделение
> и делалось. Теперь обе JaCoCo-задачи модуля сужены до `test`; граф проверяется командой
> `./gradlew :stand-test-ui:check --dry-run`, в нём не должно быть `browserTest`.

Браузерные тесты поднимают локальное веб-приложение на `com.sun.net.httpserver` — JDK, без новых
зависимостей.

`installPlaywrightBrowsers` скачивает **только сборку браузера** (без `--with-deps`: на Linux этот флаг
идёт в системный пакетный менеджер и требует root, то есть падал бы ровно на тех агентах, которым он
нужнее всего). Системные библиотеки Chromium — забота образа CI.

## Закрытый контур

Разбор и замеры — [`docs/ui-test-generation/planning/32-playwright-closed-contour-spike.md`](../docs/ui-test-generation/planning/32-playwright-closed-contour-spike.md)
(задача `UITG-SP002`). Короткое содержание, потому что оно меняет то, что здесь было написано:

**Через интернет едут только сборки браузера.** Драйвер (`driver-bundle`, 192 МБ — бинарники Node
для пяти платформ) — обычная Maven-зависимость и приезжает через Artifactory. На Linux x64
`install chromium` тянет три архива на **293,5 МиБ** (Chrome for Testing 177,0 + headless shell
114,2 + FFmpeg 2,3), которые распаковываются в ~539 МБ.

**Адрес не один.** Chromium идёт с `cdn.playwright.dev/builds/cft/…`, который отвечает **307** и
переадресует на `storage.googleapis.com/chrome-for-testing-public/…`; FFmpeg — с
`cdn.playwright.dev/dbazure/download/playwright/builds/ffmpeg/…`. Разрешить в firewall один
`cdn.playwright.dev` **недостаточно**. `PLAYWRIGHT_DOWNLOAD_HOST` заменяет только префикс хоста и
дописывает путь дословно, поэтому внутреннее зеркало обязано отдавать обе формы — `builds/cft/…` и
`builds/ffmpeg/…`. Публичного отката при этом нет: заданный хост вытесняет список публичных зеркал
целиком, и недоступное зеркало роняет установку, а не уводит её в интернет.

> **`browserTest` без браузеров не падает — он их скачивает.** Это утверждение здесь и в
> `build.gradle.kts` было **неверным**: Java-клиент доустанавливает браузеры сам, при первом
> `Playwright.create()`, и берёт все пять наборов по умолчанию — измерено **1,1 ГБ**, включая Firefox
> и WebKit, которых этот модуль не водит. Выключатель — **`PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1`**; с
> ним прогон падает громко (24 из 24, ноль скачанного) и с верной классификацией — `StandTestException`
> → BROKEN, с полным путём к отсутствующему файлу. В закрытом контуре эта переменная обязательна:
> без неё «браузеры в образе» молча превращаются в «браузеры из интернета, если до него дотянемся».
>
> Подсказка внутри отказа приходит от самого Playwright и предлагает **Maven**-команду — в этом
> репозитории она никуда не ведёт. Правильная: `./gradlew :stand-test-ui:installPlaywrightBrowsers`.

Ещё одно, если проверяете доставку руками: расположение браузеров **не является входом задачи**
Gradle. Прогон `browserTest` с изменённым `PLAYWRIGHT_BROWSERS_PATH` вернёт `UP-TO-DATE` и не
запустит ни одного браузера — проверять надо с `--rerun-tasks`.

## Параллельность набора

Модель одна на весь SDK и следует из инварианта «один прогон сценария = один поток»: **классы
параллельно, методы внутри класса — на одном потоке**. Сценарии распараллеливаются; шаги одного
сценария — никогда.

```properties
# src/test/resources/junit-platform.properties — именно в КОРНЕ тестовых ресурсов:
# копия под src/test/java не применяется молча, и этот репозиторий уже на этом обжигался
junit.jupiter.execution.parallel.enabled=true
junit.jupiter.execution.parallel.mode.classes.default=concurrent
junit.jupiter.execution.parallel.mode.default=same_thread
junit.jupiter.execution.parallel.config.strategy=fixed
junit.jupiter.execution.parallel.config.fixed.parallelism=4
```

Адаптер под эту модель и построен: **сессия браузера и аренда учётки живут в `ResourceScope` прогона**,
а не в полях executor'а — executor создаётся `ServiceLoader`'ом один раз и раздаётся всем прогонам
сразу. `UiParallelSuiteTest` гоняет один executor из восьми потоков и проверяет, что параллельный
прогон даёт тот же результат, что последовательный, и что ни один прогон не увидел данных другого.

| Правило | Почему |
|---|---|
| потоки в **одной** JVM: `maxParallelForks = 1` | пул учёток — in-process; вторая JVM заведёт свой и выдаст ту же учётку второму прогону, то есть ровно то, ради чего пул существует |
| потолок параллельности = **размер пула** | это параметр, который SDK не контролирует; выше потолка прогоны **ждут** — но ждут ограниченно (см. арифметику ниже) |
| `fixed`, а не `dynamic.factor` | на агенте с 1–2 vCPU динамическая стратегия схлопывается в 1, и параллельный путь не исполняется вовсе — то есть проверяется вакуум |
| браузерный набор — своё число | поток здесь стоит Chromium плюс процесс драйвера; в этом модуле `browserTest` понижает параллельность до 2 (поднять: `-Pstand.test.ui.browser.parallelism=4`) |

Что параллельность **не** ломает: свои куки и storage у каждого прогона (`BrowserContext`), свой
`VariableStore`, своя учётка на время прогона, свой файл сохранённой сессии (ключ — учётка). Что она
ломает, если нарушить правила выше: две JVM делят пул; `dynamic` на маленьком агенте делает проверки
вакуумными.

**Арифметика потолка — её стоит посчитать до, а не после.** «Прогоны ждут, а не падают» верно **в
пределах `accountTimeout`**, и это не формальность: при параллельности `P`, пуле размера `N` и
длительности сценария `T` последний в очереди ждёт примерно `T × (P/N − 1)`. При `P=8`, `N=2` и `T=45 с`
это ≈ 135 с — то есть умолчание в 60 с не выдержит, и прогон упадёт как `BROKEN`. Варианта три:
поднять `accountTimeout(...)`, увеличить пул или снизить параллельность. Диагностика
`ui.account.waitMillis` в `StepResult` показывает фактический простой — начинайте с неё, а не с догадки.

**Осиротевшие процессы.** `UiParallelSuiteBrowserTest` (`@Isolated`) считает живых потомков JVM до и
после набора реальных браузерных прогонов и требует, чтобы разница вернулась к нулю; пик во время
прогона проверяется отдельно, иначе набор, не запустивший ни одного браузера, проходил бы «утечек
нет» вакуумно. Проверено падающим на искусственной утечке (`UiSession.close()` без закрытия драйвера).
