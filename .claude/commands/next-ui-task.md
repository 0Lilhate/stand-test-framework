# Next UI task

Берёт следующую готовую задачу из бэклога агентной генерации UI-автотестов, выполняет её по карточке
и закрывает в бэклоге. Статусы бэклога сняты на коммите `46d3cfb` — команда перепроверяет их фактами,
а не верит на слово.

## Usage

`/next-ui-task` — взять следующую по приоритету и критическому пути
`/next-ui-task UITG-S025` — взять конкретную задачу по ID (всё равно проверяется готовность)

---

Ты работаешь в корне репозитория `stand-test-sdk`. Возьми следующую актуальную задачу из бэклога
UI-линии и выполни её целиком.

## 1. Определи актуальную задачу

Прочитай в указанном порядке:
- `docs/ui-test-generation/planning/23-execution-queue.md` — очередь NOW/NEXT/LATER/BLOCKED;
- `docs/ui-test-generation/planning/21-task-backlog.yaml` — полные карточки всех задач;
- `docs/ui-test-generation/planning/22-task-dependency-matrix.md` — зависимости и критический путь.

**Статусы в YAML сняты на коммите `46d3cfb` и могут устареть — перепроверь их фактами, а не верь
на слово:**
- `git status --short` и `git log --oneline -15` — что уже сели в git с тех пор;
- `git ls-files stand-test-ui | head` — пусто ли ещё (порции посадки `UITG-S001`…`S009`);
- статус ADR в `docs/ui-test-generation/adr/*.md` — `Proposed` или `Accepted`;
- существование артефактов, которые задача обещает создать.

Если факт противоречит статусу в YAML — верь факту, скажи об этом и поправь YAML.

**Правило выбора:** бери задачу, у которой (а) все входящие `depends_on`, `adr_dependencies` и
`external_dependencies` фактически закрыты, (б) наивысший `priority`, (в) при равенстве —
стоящую на критическом пути, затем — разблокирующую больше других.

**Никогда не бери** задачи в статусе `BLOCKED`, `DEFERRED` или `DISCOVERY_REQUIRED`. Если ни одна
задача не готова — не выдумывай работу: назови цепочку блокировок, кто её владелец и какое
конкретное действие её снимает, и на этом остановись.

Если задача принадлежит типу `ADR` или `EXTERNAL` — её исполняют люди, а не сессия. Скажи об этом,
подготовь материал для решения (варианты, последствия, рекомендацию) и переходи к следующей
готовой задаче типа `STORY`, `TASK` или `SPIKE`.

Прежде чем начать, скажи одной строкой: какую задачу берёшь, почему именно её и что она разблокирует.

## 2. Выполни задачу по её карточке

Карточка в `21-task-backlog.yaml` — это ТЗ. Обязательны к исполнению:
`acceptance_criteria`, `negative_scenarios`, `test_requirements`, `security_requirements`,
`observability_requirements`, `documentation_changes`, `definition_of_done`.
Поле `out_of_scope` — жёсткая граница: за неё не выходи, даже если рядом видно что-то улучшаемое.

Работай в отдельной ветке от текущей. Если задача размера `L` — сначала разбей её так, как
предписывает `implementation_notes`, и выполняй по одной части.

## 3. Инварианты репозитория (нарушение = падение сборки)

- `stand-test-core` не получает зависимостей на Playwright, IO, Spring, Allure и YAML;
- `Scenario` не получает UI-полей (браузер, вьюпорт, локатор) — держится `scenarioHasNoUiFields`;
- Playwright только в пакете `ru.alfa.stand.test.ui.playwright`;
- на `stand-test-ui` не ссылается ни один модуль (пересмотр — только через ADR-UI-008);
- единственное ожидание — `Awaiter`; `Thread.sleep` запрещён;
- адрес приложения только алиасом реестра, литеральный URL невыразим;
- секреты только через `*-ref`, никаких значений в коде и конфигурации;
- AssertJ вместо `org.junit.jupiter.api.Assertions`; JetBrains-аннотации вместо прочих `@NotNull`;
- исходники Java 17 (`--release 17`): без Sequenced Collections, `Math.clamp`, record-patterns;
- checkstyle `maxWarnings = 0`, JaCoCo ≥80% INSTRUCTION.

Полный список — `docs/ui-test-generation/planning/01-current-architecture.md` §6–§7 и `CLAUDE.md`.

## 4. Definition of Done

Задача не считается выполненной, пока не выполнено всё:
- `./gradlew build --console=plain` зелёный;
- полный регресс зелёный (на момент планирования — 1481 тест, 0 падений, 1 намеренный пропуск);
- если трогал драйвер или браузерные сценарии — `./gradlew :stand-test-ui:browserTest` зелёный;
- если трогал кит или набор — `./gradlew :stand-test-ai-schema:test` зелёный;
- новый код имеет тест, который **падал бы до него**;
- документация обновлена в том же изменении, а не отдельной задачей;
- нет `TODO`, переносящих обязательную часть задачи;
- все `acceptance_criteria` карточки подтверждены.

Прогоняй проверки сам и показывай фактический вывод. Если что-то падает — скажи прямо и покажи
вывод, не описывай результат словами.

## 5. Закрой задачу в бэклоге

В `21-task-backlog.yaml` переведи задачу в `IN_REVIEW` и запиши `status_reason` с фактом
(что сделано, чем подтверждено). **Не ставь `DONE` сам**: по DoD он требует завершённого ревью
человеком. Если работа разблокировала другие задачи — переведи их из `BLOCKED` в `READY` и
поправь `status_reason`. Синхронно поправь сводки в `20-task-backlog.md` §12 и очередь в
`23-execution-queue.md`.

Коммит не создавай и не пуш — оставь изменения в рабочем дереве, если не попросят обратного.

## 6. В конце ответа покажи

1. какую задачу выполнил и её ID;
2. вывод проверок (build, регресс, специфичные для задачи);
3. какие `acceptance_criteria` закрыты и чем подтверждены;
4. что задача разблокировала;
5. какая задача становится следующей актуальной;
6. что осталось незакрытым и почему — если осталось.

Отвечай по-русски; код, идентификаторы, Javadoc и коммит-сообщения — по-английски.
